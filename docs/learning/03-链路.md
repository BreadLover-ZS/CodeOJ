## 2. 必读：执行状态、用户 verdict 与平台错误

目标：解释为什么 WA 也是执行完成、平台错误不属于用户答案错误。

1. [`ExecutionStatus`](../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/reliability/ExecutionStatus.java)、`JudgeVerdict`、`SandboxOutcome`、`ExecuteCodeResponse`。
2. J [`judge.ReliableJudgeWorker#process`](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/ReliableJudgeWorker.java) → `SandboxResultMapper#userVerdict` → `JudgeManager` → `JavaLanguageJudgeStrategy#doJudge`。
3. Q [`submission.ExecutionCommands#complete/fail`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java) → `SubmissionStatusController#get`，看结果不可变、旧表兼容投影和详情可见性。

| 层 | 代表状态 | 决策 |
| --- | --- | --- |
| 执行工作流 | QUEUED / RUNNING / RETRY_WAIT / COMPLETED / NEEDS_ATTENTION | 决定谁能执行、是否恢复及是否需要人工处理 |
| 沙箱协议 | EXECUTED、CE/RE/TLE/MLE/OUTPUT_LIMIT、PLATFORM_ERROR/REJECTED | 明确用户执行结果或平台失败；检查 status/outcome 一致性 |
| 用户结果 | AC / WA / CE / RE / TLE / MLE / OUTPUT_LIMIT | EXECUTED 再比较输出；已明确的用户错误直接映射 |

COMPLETED 不等于 AC。执行返回、资源观测或协议缺失不能推断成功；平台失败走 fail 的有限恢复。`question_submit.status` 是兼容显示，不承载完整租约、重试及人工处理语义。

闭卷成果测试：分别解释 CE、沙箱不可达、输出正确但 memory=null、WA、完成结果响应丢失；画出它们进入 complete/fail 的路径。

通过标准：正确区分五种情况；能指出缺失指标拒绝判定、同 token 同结果完成回放、冲突摘要拒绝。核对 JV07/JV19 与 SandboxResultMapperTest、JavaNativeCodeSandboxTest、ReliableExecutionTest。

## 3. 必读：Outbox、消费与租约恢复

目标：按具体故障窗口解释幂等，不能只背组件名称。

1. Q [`submission.outbox.OutboxRelay#tick`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxRelay.java) → `OutboxStore#claim` → `OutboxDelivery#publish` → `OutboxStore#record`，看 publication token、publish_attempt、Confirm/Return/UNKNOWN。
2. J [`rabbitmq.ReliableJudgeConsumer#receive`](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/rabbitmq/ReliableJudgeConsumer.java) → `ReliableJudgeWorker#process` → Feign 内部 claim/heartbeat/complete/fail。
3. Q `ExecutionCommands#claim/heartbeat/owned`，看行锁、数据库时间、dispatchGeneration/eventId、attemptNo/token、租约/attempt deadline/recovery deadline。
4. Q [`submission.ExecutionRecovery#tick`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRecovery.java) → `ExecutionCommands#recover/manualRetry`，看重派发代次、退避、次数和期限、expectedVersion 与审计。

| 故障窗口 | 当前机制 | 仍需区分 |
| --- | --- | --- |
| DB 提交后、发布前崩溃 | Outbox 后续扫描 | 不依赖 API 线程继续存活 |
| Broker 接收后 Confirm 丢失 | 每次发布留痕并保留 UNKNOWN，允许后续恢复与重复投递 | UNKNOWN 不是明确未发送 |
| 两消费者同时领取 | 权威行锁内检查状态、代次与事件身份 | 不是旧版先查再普通更新 |
| worker 运行中被杀 | 租约到期、预算内重派发；写回校验 token 和期限 | DB 执行权失效不自动杀掉物理进程，另看路径四 |
| 结果事务提交后 ACK 丢失 | 完成结果/事件持久化，重投不能再取得执行权 | Consumer ACK 不代替业务完成 |
| 自动恢复耗尽 | NEEDS_ATTENTION；管理员带版本、理由和有限预算处理 | 不无限重试，也不任意修改既有结果 |

格式错误消息进入显式隔离队列；无法证明业务持久处理的可恢复异常退避后重投。正常消费 ACK 表示本次投递已得到持久处理，也可能是过期消息、已完成或已持久转入重试，不只代表“本次执行 AC”。

闭卷成果测试：给消息中的代次/事件 ID、DB 当前 token、旧 worker 回写各标注身份。解释在什么条件下拒绝旧结果；区分用户请求幂等、发布身份、执行身份和计分回执。

通过标准：能从源码指出检查条件及事务边界；不得承诺网络环境下执行恰好一次。核对 JV03—JV06/JV19—JV21，ReliableJudgeWorkerTest、OutboxRelayTest、ReliableExecutionTest。

4. 回到 registry 的结果持久化、清理确认、REAP_PENDING、启动/周期 recover 与 OWNER_LOST；再看 DurableExecutionRegistryTest 和 [check-isolation.py](../../scripts/local/check-isolation.py)中的独立 JVM/双管理器探针。

编译按 attempt 隔离，测试用例各用新容器/可写空间，产物只读；用户无网络、宿主目录、socket 或服务凭据，UID/GID10000 且 capabilities 清空。受信监督器与用户进程分离，按绝对期限终止 PID namespace 后代并写私有收据。内存取整个用例 cgroup 的 peak/events，CPU/PID 用内核约束；指标不等于 Java 堆。

管理器共用同一 daemon 和专用持久本地目录，先 journal+fsync 再创建物理资源。相同 token 同内容在有限窗口内回放结果，异内容拒绝；同 JVM 的 Semaphore 不能代表跨管理器物理容量。只有确认容器/卷删除后才释放 slot；清理失败保留占用。管理器消失时监督器仍限制期限，后继管理器回收残留并令旧 token 返回 OWNER_LOST。

通过标准：同时解释物理与逻辑约束、POSIX 文件锁问题、清理失败保留容量、有限结果缓存；说清单 daemon/本地共享目录边界。核对 JV08/JV25，15 项完整探针与 CPU/PID 两项内核补验。

## 5. 扩展：赛事报名的未知状态如何处理

源码顺序：Q [`contest.RegistrationService#register`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) → `RedisRegistrationLedger#reserve` → [`contest-registration.lua`](../../codeoj-backend/codeoj-backend-question-service/src/main/resources/lua/contest-registration.lua) → `RegistrationTransactions#persist` + Outbox → `RegistrationMessaging`/`RegistrationConsumer` → `confirmRegistration` → `synchronize`；恢复看 `RegistrationMaintenance`、`recover/reconcile`。

Redis 原子预留负责快速准入，MySQL 确认才产生参赛资格。预留后 API 崩溃或 DB/MQ 响应未知，不能马上加回库存；保存原预留身份，由补建、确认和对账解决。FAILED/CANCELLED 等持久终态后才按原身份释放；epoch/revision 隔离旧闸门和旧确认。账本丢失/时钟偏差进入暂停与核对，不根据不完整缓存放行。

补充阅读顺序：先看 [V005](../../codeoj-backend/mysql-init/migrations/V005__registration_recovery_fence.sql) 的 reservationSequence 唯一约束，再读 `RegistrationTransactions#settings/persist`、`RedisRegistrationLedger#check/reserve`，最后追 Lua 的 `anchored`、`apply` 与 `repair`。旧账本升级追 `reconcile` → `assignLegacySequences` → Lua `upgrade`。

| 场景 | 必须解释的恢复依据 | 继续定位 |
| --- | --- | --- |
| Redis 中 A 未落库，数据库中 B 已确认，两侧各一条 | 条数不是身份完整证明；数据库最大持久序号阻止旧快照放行 | `settings`、Lua `anchored`、`RegistrationMaintenance#maintain` |
| 查询最大序号后，另一个请求才提交数据库 | 单次查询不能覆盖并发窗口，数据库唯一序号约束仍要拦截身份复用 | `persist`、V005、`staleDatabaseSampleCannotReuseADurablyAssignedOrdinal` |
| 已扣库存、尚未写用户映射就报错 | 映射不存在不能证明未扣减；扣减前已保存完整 mutation 意图 | Lua `apply/repair`、`RegistrationService#recoverUnknown` |
| 执行成功但响应丢失 | 重新查询并落盘原 request/event/key，不能返回新造的请求 ID | `lostSuccessfulResponseReturnsTheOriginalRequestInsteadOfAllocatingAgain` |
| 数据库已 RELEASED，Redis 回退到 PROCESSING | 根据数据库终态重放原 Redis 标记，目标值修复不能重复退款 | `maintain`、`synchronize`、Lua `finish/repair` |
| 小容量比赛累计出现 10000 个不同身份 | 已释放身份也占累计账本条数；新用户拒绝，原身份仍可查询重试 | Lua `reserve`、`MAX_LEDGER_ENTRIES`、`ledgerLimitCountsReleasedIdentitiesAndStillAllowsOriginalRetries` |

初始化、预留及完成/释放先写原操作意图，报错后只按经核验的精确目标值恢复；证据冲突则保留原数据并暂停。新建容量和累计账本均限 10000。旧账本必须关闸核对身份及容量后升级，不能清空库存重来。细节与兼容边界见[报名恢复修复](../contest/registration-recovery.md)。

闭卷成果测试：解释“Redis 扣库存后、用户映射写入前报错”与“执行成功但响应丢失”的差异，再构造数据库与 Redis 条数相同但身份不同的旧快照。8 人争 2 名额，插入“预留成功、DB 写入前崩溃”“已确认但 Redis 标记失败”“取消后旧确认到达”。每一步标明 Redis、MySQL、资格及待回收状态。

通过标准：不把 PROCESSING 当资格、不按超时直接回滚；能区分序号检查与唯一约束、意图恢复与盲目退款，说明旧账本升级和累计上限。必须解释 R1 原反例为何最终资格没有超额，却仍破坏预留保障并暂停整场。核对历史 JV09—JV13/JV22—JV24/JV28，以及本轮 RegistrationRedisIntegrationTest 的 48 项真实 Redis/H2 测试、7 项消息契约和[真实依赖故障证据](../../outputs/validation/registration-fix-20261022/report.md)；不能把 mock 消息测试当成 Broker 验收。

## 6. 扩展：乱序结果、排名与最终结算

源码顺序：Q `ExecutionCommands#complete` 写 JUDGE_RESULT → `scoreboard.ScoreboardMessaging.Relay` → `ScoreboardConsumer` → [`ScoreboardTransactions#project`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) → [`ScoreboardService#page`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java)；结算看 `ContestLifecycle#tick` 与 `rebuild/finish`。

结果与快照是事实，榜单是可重建投影。去重回执与投影更新同事务，按受理时刻 acceptedAt 确定最早 AC；晚到的更早 AC 可改 achievedAt。排名为严格领先人数+1，分页稳定排序使用 userId 兜底，不把兜底字段变成破坏并列的排名条件。零分已确认用户也占榜单位置。

页面缓存只存 entries，版本/新鲜度元数据由 DB 决定，key 包含 projectionVersion/revision/cacheEpoch/分页信息。重建产生新版本，校验后切换；最终修订保留旧版本。FINALIZING 不能仅因时钟到点立即 FINISHED，还要处理待定业务、投影与最终版本。

闭卷成果测试：手算四人两题的并列和更早 AC 晚到情形；解释缓存旧页为何不能与新版本元数据混用；列出结算前两个 pending 计数。

通过标准：不使用消费时间计分、不重复加分、不忽略零分用户，能解释 1、1、3 的并列规则、版本切换与粗粒度比赛锁的吞吐限制。核对 JV16—JV18/JV26/JV27，ScoreboardTest、ScoreboardMessagingTest、ScoreboardCacheTest。

## 7. 选读：旧会话撤权与内部调用

源码顺序：`UserServiceImpl#userLogin` → `UserFeignClient#getLoginUser` → [`SessionUserResolver`](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/auth/SessionUserResolver.java) → `AuthInterceptor#doInterceptor` → `FeignInnerAuthConfig`/`InnerApiAuthFilter`；Redis 故障看 `SessionAvailabilityFilter`。

Session 只提供身份 ID，角色、删除及封禁状态来自当前账号；查询失败不能回退 Session 中的旧管理员。Feign default 方法本地执行，但现在会通过带 HTTP 映射的按 ID 查询刷新账号，不能笼统说“getLoginUser 全程没有网络”。内部鉴权密钥、业务账号权限和用户代码隔离各管不同边界。

闭卷成果测试：复用同一 Cookie，依次撤销管理员、封禁、删除账号，再令账号服务或 Redis 不可用；解释为何分别不能沿用旧权限或伪装普通未登录。

通过标准：能定位 F03 修复入口和 53 项真实权限回归；区分 Redis 会话不可用的 503 与账号不存在/无权限。证据见[权限修复](../contest/fix-current-permissions.md)和当前隔离复验。
