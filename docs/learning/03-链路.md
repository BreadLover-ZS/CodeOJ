# 03 链路：按业务问题读源码

每节按“业务过程 → 源码顺序 → 关键原因 → 自测”阅读。先脱稿回答自测，再回源码核对；模块细节见[模块索引](02-模块/README.md)，测试与环境结论见[项目状态](../status.md)。测试对照用于阅读断言；实际执行按[脚本索引](../../scripts/README.md)选择入口，Redis 与隔离测试有各自的环境条件。

## 1. 一次提交如何受理

用户提交 Java 代码后先拿到提交 ID，判题在后台执行。

按顺序读：

1. [`QuestionSubmitServiceImpl.doQuestionSubmit`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/service/impl/QuestionSubmitServiceImpl.java)：找到可靠判题的开关分支。
2. [`ReliableSubmissionService.accept`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ReliableSubmissionService.java)：参数检查、事务外有限重试、唯一键冲突后的回读。
3. [`SubmissionAcceptance.accept/write/freezeSpec`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java)：同事务保存提交、固定规格、执行记录和 Outbox。
4. [`ContestTransactions.submit`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)：对照比赛提交额外检查的资格、时间和发布快照。

`requestKey` 标识一次请求，内容 hash 防止同一个 key 被用来提交不同代码。同键同内容返回原 ID，改内容则冲突。`judgeSpecHash` 引用受理时固定的用例、限制和比较规则，后续改题不改变这次提交。

事务里不调用 MQ、Feign 或沙箱。这样受理成功后，即使 API 进程立即退出，数据库仍保留可继续派发的事件。

**自测：** 提交成功但响应丢失，为什么重试不能换 key？受理后改题，worker 从哪里取得旧规格？

**通过标准：** 指出请求唯一约束、hash 检查、`judge_spec` 和 Outbox；不能回答成“消息只发送一次”。

**测试对照：** [ReliableExecutionTest](../../codeoj-backend/codeoj-backend-question-service/src/test/java/com/codeoj/codeojbackendquestionservice/submission/ReliableExecutionTest.java)。

## 2. 完成判题为什么不等于 AC

按顺序读 [`ExecutionStatus`](../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/reliability/ExecutionStatus.java)、[`SandboxResultMapper.userVerdict`](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/SandboxResultMapper.java)、[`JavaLanguageJudgeStrategy.doJudge`](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/strategy/JavaLanguageJudgeStrategy.java)。

| 层次 | 回答的问题 | 例子 |
| --- | --- | --- |
| 执行状态 | 任务处于哪个阶段 | QUEUED、RUNNING、COMPLETED、NEEDS_ATTENTION |
| 沙箱结果 | 代码是否正常执行，或为什么终止 | EXECUTED、CE、TLE、PLATFORM_ERROR |
| 用户判定 | 答案是否正确，或代码有什么错误 | AC、WA、CE、RE、TLE、MLE、OUTPUT_LIMIT |

正常执行还要比较输出，才能得到 AC 或 WA。编译失败、资源超限有明确的用户判定；沙箱不可达、协议或必要指标缺失属于平台失败，进入恢复流程。WA 也可以是一次已完成的判题。

输出比较见 [`TextOutputComparator`](../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/codesandbox/TextOutputComparator.java)：CRLF 转 LF，只忽略末尾一个换行，保留其他空白，不能直接对两边 `trim()`。

**自测：** 区分 WA、编译错误、沙箱超时未响应、输出正确但缺少内存指标，分别走哪个分支？

**通过标准：** 区分平台失败与用户错误，不把 `question_submit.status` 当成完整执行状态。

**测试对照：** [SandboxResultMapperTest](../../codeoj-backend/codeoj-backend-judge-service/src/test/java/com/codeoj/codeojbackendjudgeservice/judge/SandboxResultMapperTest.java)。

## 3. 消息重复或进程崩溃后如何恢复

按顺序读：

1. [`OutboxRelay.tick`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxRelay.java) → [`OutboxStore.claim`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxStore.java) → [`OutboxDelivery.publish`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxDelivery.java) → `OutboxStore.record`：看发送租约与每次发布记录。
2. [`ReliableJudgeConsumer.receive`](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/rabbitmq/ReliableJudgeConsumer.java) → [`ReliableJudgeWorker.process`](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/ReliableJudgeWorker.java)：看领取、续租、执行和确认消息的顺序。
3. [`ExecutionCommands.claim/heartbeat/complete/fail/recover`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java) → [`ExecutionRecovery.tick`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRecovery.java)：找到状态检查与恢复预算。

Outbox 是和业务记录一起落库的待发布事件，发布器在事务外把它发给 MQ。

先分清三种身份：`requestKey` 防止重复受理；`dispatchGeneration/eventId` 区分派发代次；`attemptNo/executionToken` 区分执行尝试。租约限定执行权有效期，写结果时仍要校验 token 与期限。

| 故障窗口 | 恢复依据 |
| --- | --- |
| DB 提交后、发布前退出 | Outbox 扫描补发 |
| Broker 已接收，Confirm 丢失 | 保留 UNKNOWN，允许重发；消费端仍须幂等 |
| 两个消费者处理同一事件 | 数据库行锁内检查状态、代次和事件，再授予执行权 |
| worker 被杀 | 租约到期后，在次数与期限预算内重派发；旧 token 不能写回 |
| 结果写库后、Consumer ACK 前退出 | 重投读取持久状态，不能再次取得执行权或重复计分 |
| 自动恢复耗尽 | 进入 NEEDS_ATTENTION，管理员带版本、原因和有限预算处理 |

Confirm 是发布确认，Return 是路由失败，Consumer ACK 结束本次投递。ACK 也可能对应过期消息或已持久转入恢复的任务，不能用它证明 AC。

**自测：** 画出“旧 worker 仍运行，新 worker 已接管”的时间线，指出旧结果在哪被拒绝。

**通过标准：** 说出权威检查条件和事务边界；不承诺网络下只投递或只物理执行一次。

**测试对照：** [OutboxRelayTest](../../codeoj-backend/codeoj-backend-question-service/src/test/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxRelayTest.java)。

## 4. 数据库租约失效后，谁停止用户代码

按顺序读 [`JavaIsolatedCodeSandbox.executeCode`](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java) → [`DurableExecutionRegistry`](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java) → [`DockerIsolationEngine`](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DockerIsolationEngine.java) → [`supervisor.py`](../../codeoj-backend/codeoj-backend-codesandbox/isolation/supervisor.py)。

slot 是同时执行的容量名额。数据库 token 决定谁能写有效结果，不能直接停止已经运行的容器。编译按执行尝试隔离，每个用例再使用新容器；容器内监督器按绝对期限结束用户进程及其后代。

管理器先持久登记 token、slot 和期限，再创建执行对象。清理确认后才释放 slot；删除失败保留 `REAP_PENDING`。新管理器通过登记和文件锁回收旧对象，不因 HTTP 断开或租约过期就假定物理资源已消失。

共享容量限定于同一 Docker daemon、同一持久本地目录。具体资源与文件边界见[沙箱模块](02-模块/05-代码沙箱.md)。

**自测：** 管理器被 SIGKILL 后，谁限制运行期限？为什么不能马上归还 slot？

**通过标准：** 同时解释数据库执行权、容器内期限、持久登记与物理清理。

**测试对照：** [DurableExecutionRegistryTest](../../codeoj-backend/codeoj-backend-codesandbox/src/test/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistryTest.java)。

## 5. 秒杀报名如何从预留变成资格

按顺序读：

1. [`RegistrationService.register`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) → [`RedisRegistrationLedger`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RedisRegistrationLedger.java) → [`contest-registration.lua`](../../codeoj-backend/codeoj-backend-question-service/src/main/resources/lua/contest-registration.lua)：校验窗口、用户、库存并保存原预留身份。
2. [`RegistrationTransactions.persist`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java) 写请求与 Outbox → `RegistrationMessaging` 发布 → [`RegistrationConsumer.receive`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationConsumer.java) → `RegistrationTransactions.confirm`：消费后由 MySQL 确认资格。
3. 自动维护读 [`RegistrationMaintenance.maintain`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationMaintenance.java) 和 `recover/synchronize`；管理员对账读 `RegistrationService.reconcile`。分别看未决请求补建、终态标记重放和账本核对。

`PROCESSING` 表示确认中，`CONFIRMED` 是参赛资格的前提；提交时仍检查比赛状态、资格数据是否可用和当前账号。MySQL 条件扣容量与唯一约束是最终防线；Redis 的预留库存与数据库尚未确认容量不是同一数字，页面显示的是“已确认人数 / 总名额”。

| 问题 | 处理依据 |
| --- | --- |
| 预留成功，DB 落库前退出 | 按 Redis 原 request/event/key 补建请求和事件 |
| Lua 扣库存后、写映射前报错 | 报错不自动回滚；先写 mutation 意图，再按确定目标值 repair |
| 超时或 MQ 结果未知 | 不能直接退款；达到恢复预算也先转人工核查 |
| 明确失败或取消 | 先提交可回收的数据库终态，再幂等释放；已确认资格不走普通退款 |
| Redis 恢复到旧快照 | 检查已落库的序号高水位，并以 V005 唯一约束阻止序号绑定其他身份 |
| 旧对账或旧错误晚到 | 只使用本次 revision；`issueIfCurrent` 核对原 epoch/revision，不能暂停新恢复 |

这里的 epoch 是报名账本代次，revision 是管理状态版本，与判题派发代次不是同一字段。

新建容量和累计账本均限制为 10000；已释放身份仍计入累计数，不能删除幂等记录来继续准入。旧格式账本需要关闸核对后升级，细节见[报名恢复](../contest/registration-recovery.md)。

**自测：** 2 个名额，A 已预留未落库、B 已确认、C 新报名，应该依据什么分配？为什么两侧记录数相等不能证明身份齐全？

**通过标准：** 分清预留和资格、未知和失败；再解释“新对账成功后旧请求报错”为何不能全场暂停。

**测试对照：** [RegistrationRedisIntegrationTest](../../codeoj-backend/codeoj-backend-question-service/src/test/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationRedisIntegrationTest.java)。

## 6. 乱序结果如何计分，榜单如何重建

按顺序读 [`ExecutionCommands.complete`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java) 写结果事件 → [`ScoreboardConsumer`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardConsumer.java) → [`ScoreboardTransactions.project/rebuild/finish`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) → [`ScoreboardService.page`](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java)。

每题取最早 AC 的**提交受理时间 acceptedAt**，不是消费时间。同题多次 AC 只算一题；总题数相同时，达到该题数的时间更早者靠前。同分同时间并列，名次为“严格领先人数 + 1”，已确认的零分用户也入榜。

例：U1 的 A/B 首次 AC 受理于第 10/20 分钟，U2 为 15/20 分钟，两人并列。随后 U1 一次受理于第 12 分钟的 B 提交返回 AC，U1 的达成时间改为第 12 分钟，排到 U2 前面。

去重回执与投影更新同事务。缓存 key 带投影版本、修订号及缓存代次；重建写新版本，校验后切换。比赛到结束时间先进入 FINALIZING，待提交、报名及回收状态收敛，核对事实和重建结果后才 FINISHED。

**自测：** 同一结果重投会重复加分吗？旧缓存页为什么不能混进新榜单？

**通过标准：** 能手算上述例子，指出业务回执、版本切换和结算前的未决检查。

**测试对照：** [ScoreboardTest](../../codeoj-backend/codeoj-backend-question-service/src/test/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTest.java)。

## 7. 旧 Cookie 为什么不能保留旧权限

按顺序读 [`UserFeignClient.getLoginUser`](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/service/UserFeignClient.java) → [`SessionUserResolver`](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/auth/SessionUserResolver.java) → [`AuthInterceptor`](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/aop/AuthInterceptor.java)。

Session 只提供用户 ID；角色、删除和封禁状态重新查当前账号。`getLoginUser` 是本地 default 方法，但有效 Session 会触发 `getById` 的 Feign 查询；查询失败不回退旧角色。Redis 会话不可用与普通未登录也必须区分。

内部密钥只证明调用方持有服务凭据，不能替代管理员或参赛资格检查。前端隐藏按钮同样不代替后端授权。

**自测：** 保留同一 Cookie，把管理员降为普通用户，再调用管理接口，应在哪一步拒绝？

**通过标准：** 定位账号刷新和权限检查；能区分登录身份、业务权限与内部调用鉴权。

**测试对照：** [CurrentAccountAuthorizationTest](../../codeoj-backend/codeoj-backend-service-client/src/test/java/com/codeoj/codeojbackendserviceclient/auth/CurrentAccountAuthorizationTest.java)。
