## Part A：RabbitMQ —— 判题任务的"快递线"

### A1. 拓扑 [InitRabbitMqBean.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/rabbitmq/InitRabbitMqBean.java)

判题服务启动时（`@PostConstruct`）声明：

```text
direct exchange: code_exchange
        |
        | routing key: my_routingKey
        v
durable queue:  code_queue
```

- `queueDeclare(code_queue, true, ...)`：**持久化队列**（`durable=true`），RabbitMQ 重启不丢队列定义。
- 生产端在题目服务，消费端在判题服务，中间通过 exchange + routingKey + queue 绑定打通。

### A2. 消费者 [MyMessageConsumer.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/rabbitmq/MyMessageConsumer.java)

```java
@RabbitListener(queues = {"code_queue"}, ackMode = "MANUAL")
public void receiveMessage(String message, Channel channel, @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag) {
    long questionSubmitId = Long.parseLong(message);
    try {
        judgeService.doJudge(questionSubmitId);
        channel.basicAck(deliveryTag, false);        // 成功 → 确认
    } catch (Exception e) {
        log.error("判题失败，questionSubmitId = {}", questionSubmitId, e);
        QuestionSubmit current = questionFeignClient.getQuestionSubmitById(questionSubmitId);
        boolean isFinal = current != null && (status == SUCCEED || status == FAILED);
        if (!isFinal) {
            // 记录还停在判题中 → 回滚为 FAILED，避免永久卡死
            // 更新 status = FAILED 并记录日志
        } else {
            // 已有终态（可能结果写回后 ack 前崩溃导致消息重投）→ 不覆盖，直接丢弃
        }
        channel.basicNack(deliveryTag, false, false); // 失败 → 不重投（requeue=false）
    }
}
```

三个关键理解点：

1. **MANUAL + basicAck/basicNack**：手动确认。只有业务处理成功才 ack；异常时 nack 且 **requeue=false**（不重回队列，防止坏消息反复消费）。
2. **终态判断 + 回滚**：catch 里先查当前状态，若还在 RUNNING 则强制置 FAILED；若已是 SUCCEED/FAILED（典型场景：结果写库成功但 ack 前进程崩溃，消息被重投），则不覆盖结果、直接丢消息——**这正是手动 ACK 背景下"幂等丢弃终态"的兜底**。
3. 手动 ACK **不等于"恰好一次"**：重复投递仍然可能发生，项目用"查库判终态"缓解，但没有完整幂等/死信/重试闭环（更多见审计向文档）。

## Part B：判题编排（JudgeServiceImpl · 读三遍）

### B1. 主流程 [JudgeServiceImpl#doJudge](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/JudgeServiceImpl.java)

```java
@Override
public QuestionSubmit doJudge(long questionSubmitId) {
    // 1) 取提交记录（Feign 调题目服务）
    QuestionSubmit questionSubmit = questionFeignClient.getQuestionSubmitById(questionSubmitId);
    if (questionSubmit == null) throw new BusinessException(NOT_FOUND_ERROR, "提交信息不存在");

    // 2) 取题目（含测试用例 judgeCase、judgeConfig）
    Question question = questionFeignClient.getQuestionById(questionSubmit.getQuestionId());
    if (question == null) throw new BusinessException(NOT_FOUND_ERROR, "题目不存在");

    // 3) 幂等保护：只有 WAITING 状态才允许判，防止重复执行
    if (!status.equals(WAITING)) throw new BusinessException(OPERATION_ERROR, "题目正在判题中");

    // 4) 状态置为 RUNNING（防重复），失败则报错
    QuestionSubmit questionSubmitUpdate = new QuestionSubmit();
    questionSubmitUpdate.setId(questionSubmitId);
    questionSubmitUpdate.setStatus(RUNNING);
    boolean update = questionFeignClient.updateQuestionSubmitById(questionSubmitUpdate);
    if (!update) throw new BusinessException(SYSTEM_ERROR, "题目状态更新错误");

    // 5) 通过工厂创建沙箱（remote/example/thirdParty），并用代理包装
    CodeSandbox codeSandbox = codeSandboxFactory.newInstance(type);   // type = codesandbox.type
    codeSandbox = new CodeSandboxProxy(codeSandbox);

    // 6) 组装 ExecuteCodeRequest：code + language + inputList（用例的输入）
    List<JudgeCase> judgeCaseList = JSONUtil.toList(question.getJudgeCase(), JudgeCase.class);
    List<String> inputList = judgeCaseList.stream().map(JudgeCase::getInput).collect(Collectors.toList());
    ExecuteCodeResponse response = codeSandbox.executeCode(executeCodeRequest);

    // 7) 组装 JudgeContext，交给 JudgeManager（策略模式）判题
    JudgeInfo judgeInfo = judgeManager.doJudge(judgeContext);

    // 8) 回写 status=SUCCEED + judgeInfo(JSON)，存库
    // 9) 若 Accepted，累加题目通过数（updateQuestionStats，失败仅 warning）
    // 10) 返回最新提交记录
}
```

### B2. 双状态理解

- `status = SUCCEED`：**只代表判题流程跑完**，不代表答案正确。
- `judgeInfo.message`：真正的判题结论（`ACCEPTED` / `WRONG_ANSWER` / `TIME_LIMIT_EXCEEDED` / `MEMORY_LIMIT_EXCEEDED` / `COMPILE_ERROR` 等）。

### B3. Feign 调用的边界

判题服务本身**不连数据库**，一切数据通过 `QuestionFeignClient`（题目服务）读写：查题目、查提交、改提交、累加统计。这是"按业务拆分服务"的体现——判题服务只关心"判"，存取都委托题目服务。

## Part C：判题策略（策略模式）

### C1. 入口 [JudgeManager.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/JudgeManager.java)

```java
JudgeInfo doJudge(JudgeContext judgeContext) {
    JudgeStrategy judgeStrategy = new DefaultJudgeStrategy();
    if ("java".equals(language)) {
        judgeStrategy = new JavaLanguageJudgeStrategy();   // 按语言选择策略
    }
    return judgeStrategy.doJudge(judgeContext);
}
```

### C2. Java 策略 [JavaLanguageJudgeStrategy.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/strategy/JavaLanguageJudgeStrategy.java)

判题顺序（代码逐行对应）：

1. 取 judgeInfo 的 time / memory，若无则为 0。
2. 输出数量 != 输入数量 → `WRONG_ANSWER`（用例都没跑齐）。
3. 逐个用例比对 `judgeCase.output` 与沙箱实际输出 → 不等 → `WRONG_ANSWER`。
4. `memory > memoryLimit` → `MEMORY_LIMIT_EXCEEDED`。
5. `time - 10000L > timeLimit` → `TIME_LIMIT_EXCEEDED`（注释："Java 程序本身需要额外执行 10 秒"——这条规则从原版项目继承，含义是给 Java 虚拟机启动留缓冲；本沙箱记录的是进程实际耗时，若要更准确需要测试校准，审计向文档已提示）。
6. 全部通过 → `ACCEPTED`。

### C3. 默认策略 [DefaultJudgeStrategy.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/strategy/DefaultJudgeStrategy.java)

与 Java 策略几乎一致，只是**没有 Java 的 10 秒缓冲**。

### C4. 策略模式收益

新增一种语言（如 go/cpp 已有枚举）：

- 实现一个 `XxxLanguageJudgeStrategy implements JudgeStrategy`；
- 在 `JudgeManager` 里加一个分支；
- 若沙箱语言不同，再扩展 `ExecuteCodeController` 对应执行器。
- 不会动到 `doJudge` 主流程——这就是把"判什么"和"怎么判"解耦。
