## Part A：数据库设计（一份表地图）

来自 [create_table.sql](file:///e:/gitStore/ZSOJ/codeoj-backend/mysql-init/create_table.sql)：

| 表 | 关键字段 | 用途 / 注意点 |
|---|---|---|
| `user` | userAccount、userPassword(bcrypt)、userRole | 账号密码；role: user/admin/ban；`idx_userAccount` 索引 |
| `question` | title、content、tags(json)、answer、submitNum、acceptedNum、judgeCase(json)、judgeConfig(json)、userId | `judgeCase` 存测试用例数组，`judgeConfig` 存 timeLimit/memoryLimit/stackLimit——都是 JSON 文本列 |
| `question_submit` | language、code、judgeInfo(json)、status、questionId、userId | `status` 0 待判题/1 判题中/2 成功/3 失败；`idx_questionId_status` 组合索引 |
| `post`、`post_thumb`、`post_favour` | 论坛功能 | 本项目业务主线外，可略读 |

设计要点（面试可讲）：

- 判题用例和限制以 **JSON 字符串**存库（text 列），读取时用 Gson/JSONUtil 反序列化。好处是扩展字段灵活，坏处是无法对用例做 SQL 级查询/约束。
- `question_submit` 有 `idx_questionId_status` 组合索引：按题目查提交、按题目+状态过滤（判题服务 `status = WAITING` 抢任务的常见查询）都能命中索引。

## Part B：部署拓扑（Docker Compose 两套）

### B1. 基础设施 [docker-compose.env.yml](file:///e:/gitStore/ZSOJ/codeoj-backend/docker-compose.env.yml)

MySQL、Redis、RabbitMQ、Nacos 一套起，配好初始密码。首次部署后在 RabbitMQ 里初始化交换机/队列：

```bash
# 声明 code_exchange(direct) + code_queue(durable) + 绑定 my_routingKey
docker exec codeoj-rabbitmq rabbitmqadmin ... declare exchange name=code_exchange type=direct durable=true
docker exec codeoj-rabbitmq rabbitmqadmin ... declare queue name=code_queue durable=true
docker exec codeoj-rabbitmq rabbitmqadmin ... declare binding source=code_exchange destination=code_queue routing_key=my_routingKey
```

（也可运行判题服务 `InitRabbitMq#main` 自动声明。）

### B2. 业务服务 [docker-compose.service.yml](file:///e:/gitStore/ZSOJ/codeoj-backend/docker-compose.service.yml)

五个服务都编在 `mynetwork`：

- **网关 8101 对外发布**（`ports: 8101:8101`）。
- 用户/题目/判题服务只 `expose` 内部端口（8102/8103/8104），**不发布到宿主机**——外网只能走网关。
- 沙箱 8090 **也不对外发布**，只允许内网判题服务访问（安全考虑：跑任意代码的服务绝不能暴露）。
- 环境变量注入：数据库/Redis/Nacos/RabbitMQ 地址密码、`INNER_AUTH_SECRET`、`CODESANDBOX_SECRET`、沙箱超时等，默认值仅本地开发用。

> 完整启动：先 `docker compose -f docker-compose.env.yml up -d`，再 `docker-compose.service.yml up -d`，最后起前端 `npm run serve`（:8000）。

### B3. 关键环境变量（生产必覆盖）

## Part C：常见面试题（按项目分层整理）

### C1. 架构与设计

1. **为什么用微服务拆分？** 解耦 + 独立扩展。判题是 CPU/沙箱密集，可独立扩容；网关统一入口收敛跨域与鉴权。
2. **服务间怎么通信？** OpenFeign（同步查询数据）+ RabbitMQ（异步判题任务）。判题服务不连库，数据全靠 Feign 取。
3. **网关在架构里的角色？** 统一入口、路由分发（lb://）、CORS、拦截 `/inner/**` 内部接口第一道防线。
4. **怎么保证 `/inner/**` 安全？** 双层：网关 GlobalAuthFilter + 服务内 InnerApiAuthFilter 都校验 `X-Inner-Secret`；同时业务服务端口不对外发布。

### C2. 登录与权限

5. **登录态存哪？为什么各服务都有？** Spring Session + Redis。登录把 `User` 放入 session，session 序列化到 Redis；带同一 JSESSIONID 的请求在各服务都能反序列化出同一用户。
6. **`@AuthCheck` 怎么实现？** AOP 切面（AuthInterceptor，`@Around`），从 `RequestContextHolder` 拿 request → session → User → 校验 mustRole/封号。注解在 common，切面在 service-client，所以各服务可用。
7. **自己调自己为什么 `@AuthCheck` 失效？** AOP 代理只拦外部调用，同类 `this.method()` 是内部直调不走代理。

### C3. 判题链路（高频）

8. **完整链路？** 前端提 → 网关 → 题目服务存 WAITING+发 MQ → 判题服务消费 → Feign 取题/提交 → 置 RUNNING → 沙箱执行 → 策略判题 → 回写 SUCCEED+judgeInfo → Accepted 时累加统计。
9. **MQ 里放什么？** 只放 `questionSubmitId`。小消息 + 以库为准；代价是强依赖题目服务可用性、存在结果与提交时快照不一致风险。
10. **消费失败怎么处理？** 手动 ACK；catch 中先查当前状态：非终态 → 置 FAILED 防卡死；终态（结果已写但 ack 前崩）→ 不覆盖；最后 `basicNack(requeue=false)` 丢弃。
11. **状态机？** `WAITING(0) → RUNNING(1) → SUCCEED(2)/FAILED(3)`。SUCCEED 只表示流程完成，对错看 `judgeInfo.message`。
12. **判题怎么防重复执行？** 消费侧先查 `status == WAITING` 才继续并置 RUNNING——但"先查后改"在并发下仍可能重复，真正的原子抢占需要条件更新（`update ... where id=? and status=WAITING`）。（诚实讲清当前局限，比背答案加分。）

### C4. 沙箱

13. **沙箱怎么执行代码？** javac 编译临时目录 → 每个用例独立 java 子进程，stdin 喂入、stdout 采集 → 超时强杀 → finally 清理目录。
14. **有哪些防护、缺什么？** 有：auth 头、代码 256KiB/输出 64KiB 限制、编译 15s/运行 5s 超时、临时目录清理。缺：容器级隔离、CPU/内存/进程数限制、禁网、只读 FS、非 root 运行、真实内存采集。
15. **为什么沙箱服务不能对外暴露端口？** 它执行任意用户代码，一旦暴露等于给攻击者一台可执行任意程序的机器，只能让判题服务内网调用并做密钥鉴权。

### C5. 可扩展性问题（加分）

16. **加一种判题语言要改什么？** 沙箱执行器（JavaNativeCodeSandbox 类似物）+ `QuestionSubmitLanguageEnum` + `JudgeManager` 里加策略分支（策略模式）。
17. **判题吞吐怎么提升？** 沙箱服务多实例扩展（它是进程级执行，天然可横向扩）；MQ 消费并发提高（注意先解决并发抢任务的原子性问题）。
18. **订阅数/通过数统计可靠吗？** 当前累加是"尽力而为"（失败仅 warning），统计不精准但主流程不受影响。

## Part D：学习路线总结（一份心智模型）

```text
读代码就围绕一条主线：一条提交记录的一生
  QuestionController.doQuestionSubmit
  → QuestionSubmitServiceImpl.doQuestionSubmit   save + sendMessage
  → MyMessageProducer → code_exchange/code_queue
  → MyMessageConsumer(receiveMessage, MANUAL ack)
  → JudgeServiceImpl.doJudge
  → CodeSandboxFactory/Proxy/RemoteCodeSandbox
  → sandbox ExecuteCodeController → JavaNativeCodeSandbox
  → JudgeManager → 策略 → judgeInfo
  → 回写 status/judgeInfo → 前端轮询展示
```
