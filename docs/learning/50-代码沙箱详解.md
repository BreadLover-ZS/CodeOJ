## Part A：判题服务侧的沙箱抽象

### A1. 接口与工厂

[JudgeService 侧] 判题服务不直接依赖某个沙箱实现，而是通过接口 + 工厂切换：

- [CodeSandbox.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandbox.java)：接口，就一个方法 `ExecuteCodeResponse executeCode(ExecuteCodeRequest)`。
- [CodeSandboxFactory.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxFactory.java)：`newInstance(type)` 按 `codesandbox.type`（默认 `remote`）返回：
  - `example`：本地假沙箱（不真跑代码）
  - `remote`：远程 HTTP 沙箱（生产用）
  - `thirdParty`：第三方沙箱桩
- [CodeSandboxProxy.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxProxy.java)：包装类（静态代理），调用前打印完整请求、调用后打印完整响应（便于排查问题，注意也会把用户代码/用例打进日志）。

> 注意：判题服务 factory 默认 `codesandbox.type` 读 `application.yml`，值是 `remote` → 真正跑到 `codeoj-codesandbox:8090`。

### A2. 远程调用 [RemoteCodeSandbox.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/impl/RemoteCodeSandbox.java)

```java
@Value("${codesandbox.remote.url:http://localhost:8090/executeCode}")
private String url;
@Value("${codesandbox.remote.auth-secret:secretKey}")
private String authSecret;

String json = JSONUtil.toJsonStr(executeCodeRequest);
String responseStr = HttpUtil.createPost(url)
        .header(AUTH_REQUEST_HEADER, authSecret)   // 请求头 auth = 密钥
        .body(json).execute().body();
return JSONUtil.toBean(responseStr, ExecuteCodeResponse.class);
```

要点：地址和密钥都走配置注入（生产用 `CODESANDBOX_URL` / `CODESANDBOX_SECRET` 覆盖），不再硬编码。

## Part B：沙箱服务端（codesandbox，:8090）

### B1. 入口 [ExecuteCodeController.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/controller/ExecuteCodeController.java)

```java
@PostMapping("/executeCode")
public ExecuteCodeResponse executeCode(@RequestBody ExecuteCodeRequest req,
                                       @RequestHeader(value = "auth", required = false) String auth) {
    codeSandboxService.checkAuth(auth);          // ① 鉴权
    return codeSandboxService.executeCode(req);  // ② 执行
}
```

只有带正确 `auth` 头的请求才能执行代码，防止任何人直连 8090 端口跑任意代码。

### B2. 核心实现 [JavaNativeCodeSandbox.java](file:///e:/gitStore/ZSOJ/codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaNativeCodeSandbox.java)

逐步骤（对照源码读）：

1. **入参校验**：代码非空、长度 ≤ `MAX_CODE_LENGTH = 256KiB`。
2. **提取类名**：正则 `public\s+class\s+(\w+)` 取主类名，没有则默认 `Main`。
3. **写临时目录**：`Files.createTempDirectory("codeoj-sandbox-")`，写入 `{ClassName}.java`。
4. **编译**：`javac -encoding UTF-8`，编译超时 `compile-timeout-ms`（默认 15s），失败返回"编译错误……"（截断 500 字），超时 `destroyForcibly()` 返回"编译超时"。
5. **逐用例运行**：每个用例单独 `java -cp 工作目录 类名` 子进程，用 stdin 喂入 sample 输入，读 stdout 作为输出；单用例运行超时 `run-timeout-ms`（默认 5s），超时强杀。
6. **资源统计**：记录最大耗时 `maxCostMs`；内存固定 0（当前不采集真实内存）。
7. **归一化输出**：`replace("\r\n","\n")` + `trim()`，避免判等受平台换行/首尾空白干扰。
8. **清理**：`finally` 里递归删除临时目录。

关键防护常量（面试常问）：

```java
MAX_OUTPUT_LENGTH = 64 * 1024;   // 单个用例最多收集 64KiB 输出，防刷屏
MAX_CODE_LENGTH   = 256 * 1024;  // 代码最大 256KiB
runTimeoutMs      = 5000;        // 单用例运行超时
compileTimeoutMs  = 15000;       // 编译超时
```

### B3. 返回结构

成功 `status=1` + outputList + judgeInfo(time)；失败 `status=2` + message（编译错误/运行错误/超时/非法请求等），由上层判题策略据此给出 WRONG_ANSWER / CE 等结论。

## Part C：这条链路的完整串联（重点回顾）

```text
判题服务 JudgeServiceImpl#doJudge
  -> CodeSandboxFactory.newInstance("remote") -> CodeSandboxProxy
  -> RemoteCodeSandbox.executeCode()
        POST http://codeoj-codesandbox:8090/executeCode
        Header: auth = CODESANDBOX_SECRET
  -> sandbox: ExecuteCodeController # checkAuth
  -> JavaNativeCodeSandbox.executeCode()
        javac 编译 -> java 逐用例运行（stdin/stdout）-> 收集输出+耗时
  -> ExecuteCodeResponse 原样回传
  -> JudgeManager + 策略给出 Accepted / WA / TLE / MLE / CE
```

## Part D：安全边界（务必清楚"防住了什么、没防住什么"）

**已防住**：

- 接口鉴权（auth 头）
- 代码/输出大小限制
- 编译/运行超时
- 独立临时目录 + 结束后清理

**尚未防住（进程级沙箱本质）**：

- 用户代码与沙箱进程共享同一容器权限/网络/文件系统——没有每次提交的容器隔离、CPU/内存限制、禁网、只读根文件系统、非 root 运行。
- stdout/stderr 读取发生在 waitFor 之前，超时控制可能不精确；`destroyForcibly` 未等待子进程及其后代退出。
- 不采集真实内存，MLE 判定缺乏数据基础。

> 结论：当前可称为"演示级/进程级沙箱"。生产场景建议部署在独立容器/独立宿主，配合资源限额与网络隔离（README 已注明）。
