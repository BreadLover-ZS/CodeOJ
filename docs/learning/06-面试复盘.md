# 面试复盘：沿业务阶段解释项目

本篇用于检验阅读结果。每次选一题，先用自己的话讲“业务问题 → 当前实现 → 一个场景 → 取舍或边界”，再看提纲和源码核对。实现与个人贡献分开表达，只讲自己能解释、能复现的部分。

## 1. 从一次提交讲清项目

### 1.1 怎样介绍项目，并讲完一次普通判题

CodeOJ 是 Java 在线判题与赛事平台。用户提交代码，题目服务保存提交、固定规则和执行记录，后台通过消息通知判题服务；后者领取任务，调用沙箱运行，由策略形成判定，再交题目服务保存。赛事在此基础上增加发布快照、限额报名、参赛资格和成绩榜单。

介绍主链时分清三个节点：接口返回 202 和提交 ID 表示受理；沙箱 EXECUTED 表示完成运行；COMPLETED 表示用户判定已保存，可以是 AC、WA、CE 等。标准输出留在判题端，只有代码、输入、限制等执行材料发给沙箱。普通页面另发列表查询取得结果。

**追问：为什么异步？** 编译运行可能较慢且需要受限环境，不能让受理事务一直等待。代价是状态查询、通知交接、失联恢复等额外工作；worker 仍依赖题目服务领取和写回，不是完全消除了服务依赖。

### 1.2 用户重试，怎样避免创建两份提交

`Idempotency-Key` 标识一次待确认请求，后端按用户和 key 查询，再用内容摘要核对题目、语言和代码。同 key 同内容返回原 S1，内容不同则冲突；新 key 可以发起新的提交，即使代码相同。

并发时两次查询都可能为空，数据库唯一约束兜底。冲突事务先退出回滚，外层再回读并核对；暂态异常则在旧事务结束后重试整次受理。

**追问：只禁用按钮够吗？** 只能防本页连点，不能覆盖丢响应和并发请求。画出“数据库已提交、响应丢失、同 key 重试”的过程再解释。

### 1.3 为什么受理时要保存固定判题依据

任务可能排队，题库在此期间又可能修改。受理组件把用例、资源限制、比较规则及版本保存为固定规格 H1，S1 引用它，执行时校验并按该规格判题。比赛固定时点更早，在发布时保存快照，提交引用已发布版本。

**追问：摘要能替代权限吗？** 摘要用来引用和核对内容，规格仍含私有用例；材料合法性、访问权限要分别检查。

### 1.4 通知怎样可靠交接，为什么仍可能重复

Outbox 是与提交一起写入本地事务的待发送事件。数据库提交后，即使进程未发 MQ 就退出，后台也能扫描补发。Broker 已接收而确认丢失时，补发仍可能重复，因此消费与执行还要校验业务身份。

| 信号 | 回答时要区分的含义 |
| --- | --- |
| Confirm | Broker 对发布的确认；有效发布确认还要排除 Return |
| Return | mandatory 消息无法路由，被退回发布方 |
| Consumer ACK | 结束这次投递；当前直接条件是 worker.process 正常返回，不能推出 AC |

**追问：把 MQ 调用放进事务就行吗？** 本地数据库事务不能撤销 Broker 已收到的消息。当前网络发送在发布领取事务之外；数据库保存发送意图，不提供跨系统的大事务。

### 1.5 两个消费者收到同一通知，谁能执行

题目服务的执行命令锁定 S1，检查当前派发身份、QUEUED 状态、时间和预算。第一个领取后保存 RUNNING 与本次 attempt/token；竞争者随后再检查，就不能重复领取。锁在领取事务结束时释放，沙箱运行在事务外。

| 标识 | 保护什么 |
| --- | --- |
| 代次与事件 ID | 当前是哪轮派发，拒绝旧通知 |
| attempt 与 executionToken | 当前是哪次获权执行，拒绝旧执行者操作 |
| 租约与尝试期限 | 失联后可接手，同时限制持续续租 |
| 发布 token | 同一事件的哪次网络发送，与执行 token 不同 |

**追问：有行锁为何还要 token？** 锁不覆盖远程执行全过程。任务可能失联并被新尝试接手，旧结果仍可能晚到，写回时必须重查身份与期限。本地 Semaphore 只限制本进程容量。

### 1.6 失联和完成后重投分别怎样处理

失联后，由执行恢复组件扫描候选，在行锁内重查。预算允许时结束旧尝试、换代并创建新事件；下一次领取才增加 attempt、生成新 token。自动恢复受次数和总期限限制，耗尽转 NEEDS_ATTENTION，管理重试要带期望版本、原因和有限预算。

若结果已经提交，消息重投后 claim 看见 COMPLETED，不再授予执行权。同 token、同规范化结果重放 complete，按摘要回放，不重复增加通过提交数或结果事件；异内容则拒绝。

**追问：所有 false 都会 NACK 吗？** 当前 worker 对 complete/fail 的明确 false 不统一抛异常；RPC 异常另走错误处理。不要把 ACK 当作本次结果写入成功的证明。

## 2. 解释用户程序怎样运行和被清理

### 2.1 从代码到输出，为什么分编译和逐用例运行

沙箱接收请求后，先登记 token、期限和物理名额，再进入执行器。Java 隔离执行器先编译一次，取得 class 和入口信息，之后每个用例使用独立运行容器。产物只读，可写环境不在用例间复用，减少状态污染。

stdin 传输入，stdout 返回待比较输出；编译收据与监督器控制结果走独立的受保护通道。判题端先校验响应，再比较答案：明确编译失败可形成 CE，正常运行还要核对资源与输出，正常执行缺指标或 HTTP 超时属于平台失败。

**追问：remote 和 isolated 有什么关系？** 前者是判题端调用沙箱的方式，后者是沙箱内部运行程序的方式，可以同时成立。

### 2.2 除了容器，还需要哪些限制

回答应落到当前约束：用户进程降权、禁网、只读挂载、可写空间边界、CPU/内存/PID、输出上限与执行期限。cgroup 约束整个用例环境，不只是 Java 堆；监督器负责期限和后代进程清理，用户 stdout 不能充当可信控制收据。

**追问：隔离的代价是什么？** 需要镜像、Linux/cgroup、容器与卷管理及额外启动开销；当前实现和测试范围不能外推成绝对安全或内核逃逸认证。

### 2.3 执行权过期或管理器退出，资源怎样回收

数据库 token 决定结果能否生效；停止真实用户进程依赖监督器，物理对象清理由持久登记组件跟踪。管理器退出后，后继管理器根据日志和对象信息恢复清理。

删除失败时保持 REAP_PENDING 并占用 slot，确认容器和卷清理后才释放容量。物理清理成功不会把数据库任务自动判为 AC；两边是不同状态机。

**追问：容量能覆盖任意机器吗？** 当前共享约束依赖同一 Docker daemon、同一持久本地目录和一致配置，不等于多宿主全局容量。

**源码核对：** [JavaIsolatedCodeSandbox.executeOnce](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java) 编排编译与用例；[DockerIsolationEngine](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DockerIsolationEngine.java) 创建受限对象；[supervisor.py](../../codeoj-backend/codeoj-backend-codesandbox/isolation/supervisor.py) 管理程序期限与收据；[DurableExecutionRegistry](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java) 的 run/recover/reap 管理登记与收尾。判题响应分界见 [SandboxResultMapper](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/SandboxResultMapper.java)、[JavaLanguageJudgeStrategy](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/strategy/JavaLanguageJudgeStrategy.java)。

## 3. 解释比赛怎样发布、报名和参赛

### 3.1 比赛提交比普通练习多哪些前置条件

发布时保存比赛题目快照与固定规格，形成发布版本；普通练习则在受理时固定规则。比赛提交还要检查当前账号、已确认资格、比赛状态与 ready、时间窗口、发布版本和快照归属，然后把比赛上下文写入可靠执行记录，再复用判题链。

**追问：结束后才完成的判题能计入吗？** 要区分受理时间和完成时间；合法受理的比赛提交可能在结束后完成，最终结算必须等待相关事实收敛。

### 3.2 报名为什么分预留与确认

先说明当前场次采用 DB_SYNC 还是 Redis 预留模式。Redis 模式下，Lua 预留名额并保存请求身份，数据库把请求与待确认事件一起持久化，消费者再由 MySQL 事务确认参赛资格。PROCESSING 或 Redis RESERVED 都不等于已确认资格。

Redis 可以吸收入口竞争，但增加了预留、数据库确认与收尾同步的维护成本；数据库仍负责最终资格与容量约束。

**追问：已经预留，为什么不能直接参赛？** 比赛提交查数据库确认事实。响应丢失也必须沿原 key、请求和事件恢复，不能换身份再次分配。

### 3.3 Lua 报错或请求超时，为什么不能立即退名额

Lua 执行不被其他命令穿插，但运行时异常不会自动撤销此前写入。mutation 保存恢复所需的原身份、库存和目标，repair 校验允许的中间状态后写确定目标，重放不能再次扣减或释放。

超时表示未知，可能已经预留或确认。明确失败/取消需先提交数据库可回收终态，再按原身份幂等释放；数据库已确认而 Redis 标记失败，只补确认标记。维护器补 persist 也只保存请求，确认仍由确认事务完成。

**追问：已确认人数和剩余可预留名额为何对不上？** 部分名额可能仍被 Redis 请求预留，两者不是同一指标。

### 3.4 Redis 旧快照与迟到对账分别怎样防护

旧快照可能数量相同但身份缺失，需要核对原身份、数据库持久序号高水位和序号唯一约束，不能只比较库存或记录数。对账还要保留自己原来的 epoch/revision，失败仅在该版本仍有效时暂停，不能取得新版本去覆盖更新的恢复。

**追问：直接按数据库余量重建 Redis 行吗？** 可能遗漏未落库预留，需关闸并完整核验身份。累计账本有 10000 条边界，释放记录也不能随意删除。

**源码核对：** [ContestTransactions](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java) 的 publish/submit 固定发布与参赛条件；[RegistrationService](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) 的 register/recoverUnknown/synchronize/reconcile 组织预留与收尾；[RegistrationTransactions](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java) 的 persist/confirm/review/recover/settings/issueIfCurrent 控制数据库事实与版本；[Lua 脚本](../../codeoj-backend/codeoj-backend-question-service/src/main/resources/lua/contest-registration.lua) 核对 apply/repair；[V005](../../codeoj-backend/mysql-init/migrations/V005__registration_recovery_fence.sql) 核对恢复约束。

## 4. 解释成绩怎样更新与最终结算

### 4.1 更早的正确提交晚完成，为什么能修正成绩

当前规则每用户每题取最早 AC 的 acceptedAt；解题数是不同题数，achievedAt 是各题首次 AC 时间的最大值。更早提交的 AC 晚到会修正该题时间，同题多次 AC 不多加题。确认参赛但尚未解题的用户也以零分入榜。

结果回执与投影更新在同一事务提交，避免事件重复应用。按严格领先人数加一给名次，并列者名次相同，页面稳定排序与名次计算分开。

**追问：收到 AC 给分数加一行吗？** 会重复计算同题多次 AC，也无法修正乱序时间。用同一题两次提交的受理/完成时间现场手算。

### 4.2 为什么既有成绩表，又有 Redis 缓存

成绩表是从提交结果计算的查询投影；Redis 只缓存分页 entries。缓存 key 含投影版本、revision、cacheEpoch 和分页，当前命中前仍取数据库元数据快照并锁比赛行，并非纯 Redis 查询。

从结果事实重建新投影版本，核验后再切换，旧版本保留。这方便复核和恢复，代价是额外存储、锁、版本与缓存维护；不能把投影或缓存当成新的判题事实。

**追问：哪里可能有瓶颈？** 当前数据库快照和同场比赛锁、同步重建等都值得测量；先找实际负载证据，再讨论减少锁或改架构。

### 4.3 到结束时间后，最终榜单会自动生成吗

定时生命周期任务让到期比赛进入 FINALIZING。重建和结束由管理员分别调用，不是继续等待就自动 FINISHED。结束前要检查报名、提交等事实已收敛，核对资格与容量，并确认成绩投影一致。

重建负责从事实生成并切换新版本；结束负责核验后发布最终状态。未决的 NEEDS_ATTENTION 不能默默算成用户 WA 或零分。

**追问：为什么分两个管理命令？** 两个命令目的、前置条件和失败恢复不同，版本检查及审计能阻止旧操作覆盖新状态。

## 5. 应对权限与验证追问

### 5.1 旧会话怎样失去管理员权限

Spring Session 通过 Redis 共享会话，Session 内保存的 User 只提供身份 ID。当前账号解析组件再次查询数据库账号、角色、删除或封禁状态，权限检查使用本次查询结果；关键写入事务还会复查当前条件。

Client 是服务间 HTTP 契约，内部 Controller 是提供方入口。服务凭据验证服务调用方，不能替代用户权限，也不能替代任务执行身份。`UserFeignClient.getLoginUser` 的 default 方法本地执行，其中传入的 getById 才通过 Feign 远程查询。

**追问：账号查询失败可否回退会话角色？** 不能，否则失效权限会重新生效。用同一 Cookie 在管理员降权前后推演一次管理请求。

**源码核对：** [SessionUserResolver](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/auth/SessionUserResolver.java) 解析当前账号；[UserFeignClient](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/service/UserFeignClient.java) 连接本地解析与远程查询；[AuthInterceptor](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/aop/AuthInterceptor.java) 校验业务权限。需要细读时回[登录与权限导读](01-登录与权限链路.md)。

### 5.2 怎样说明验证结果与当前限制

回答按实际证据区分：构建/组件测试、H2 或服务替身、真实依赖专项、MySQL/MQ/HTTP/浏览器链，以及 Linux/cgroup 故障回收。说明所用版本和夹具；历史基线通过不自动覆盖后续源码。

已有证据与未验收范围以[项目状态](../status.md)为准。没有压测不报 QPS，容器测试不等于逃逸认证，真实 Nacos、目标部署与长期稳定性也不能从本机结果推断。

**追问：下一步怎样优化？** 先选一个可测问题，例如同场锁竞争、同步重建耗时、沙箱容量或查询频率；给出测量和故障观测方案，再解释改动对幂等、执行权或收敛条件的影响。

### 5.3 怎样判断自己真正掌握了

每题先不看提纲讲 60—90 秒，再接一个追问，最后打开对应方法核对。下一次换数据或故障时点，不重复背同一段话。

| 检查 | 达标表现 |
| --- | --- |
| 业务与交接 | 能说清调用方、输入、已保存的事实和下一步触发者 |
| 源码与机制 | 能指出关键方法的职责、条件与事务/网络边界 |
| 故障与恢复 | 能推演丢响应、重复、迟到或失联，以及何时停止自动推进 |
| 设计取舍 | 能解释所解决的问题、引入的成本和当前实现范围 |
| 个人贡献与证据 | 不把读懂当亲自开发，不把替身结果当部署或压测结论 |
