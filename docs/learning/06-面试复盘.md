# 面试复盘：按五条链路组织回答

本篇用于读懂后的复习。先完成[五条链路的阅读成果检查](README.md#6-学完以后怎样检查)，再练下列问题。每道题按“业务问题 → 当前实现 → 一个具体场景 → 适用边界”展开，第一遍不要求背出所有类名，但必须能回到源码解释。

参考回答描述仓库实现。介绍个人贡献时，只使用自己实际参与、能够讲清并复现的内容；学习过某段实现不等于亲自完成了该段开发。

## 1. 怎样用两分钟介绍项目

**参考回答：** CodeOJ 是基于课程基础继续扩展的 Java 在线判题与赛事平台，使用 Spring Cloud、MySQL、Redis、RabbitMQ 和 Vue。用户提交 Java 代码后，题目服务先保存代码、固定判题规格和执行记录，异步交给判题服务，再由沙箱编译运行、策略比较答案并写回结果。赛事侧在这条链上增加发布快照、限额报名、资格和榜单。

可靠性重点是用 Outbox 保留待派发事实，用数据库执行状态、token 和租约管理执行权，并为失联任务做有限恢复。沙箱侧有隔离、期限和持久回收。报名把预留与资格分开，榜单按受理时间处理乱序 AC，并能从事实重建。

**追问与核对：** “你最熟悉哪部分？”选一条自己掌握的链，用具体失败场景展开，不能把上面所有词再念一次。两分钟介绍只需讲清产品、架构、两三个重点。

**源码依据：** [SubmissionAcceptance](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java)、[ReliableJudgeWorker](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/ReliableJudgeWorker.java)。

## 2. 一次提交从按钮到结果经过哪些步骤

**参考回答：** 页面携带题目、代码、语言和请求 key。Gateway 转到题目服务，Controller 获取当前用户；可靠受理事务保存提交、固定规格、执行状态与 Outbox，返回 202 和 ID。后台发布消息，worker 领取执行权和判题材料，调用沙箱。沙箱返回运行结果，策略生成 AC/WA 等判定，再通过内部接口写回。页面用提交 ID 查询结果。

**追问与核对：** “代码、测试输入、标准答案分别在哪？”代码存提交记录，固定用例存 judge_spec；领取响应含用例，发给沙箱的只有输入，标准答案在判题端比较。

**源码依据：** [QuestionController.doQuestionSubmit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/controller/QuestionController.java)、[完整时序](02-提交与判题链路.md)。先能画出这个流程，再谈细节。

## 3. 为什么异步判题，不直接等沙箱返回

**参考回答：** 编译运行比数据库操作慢，可能持续到资源期限。先受理再后台执行，避免把浏览器提交请求一直占到运行结束，也让执行能力独立安排。代价是用户需要查询状态，系统必须处理消息交付、重复、任务失联和结果一致性。

**追问与核对：** “用了 MQ 就解耦了吗？”只是分开受理和执行的时机；当前 worker 仍通过 Feign 依赖题目服务领取和写回，业务契约与可用性依赖仍存在。

**源码依据：** [可靠受理](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ReliableSubmissionService.java)、[worker](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/ReliableJudgeWorker.java)。不凭异步结构推断已有高 QPS。

## 4. 为什么提交返回成功，却还可能 WA 或 CE

**参考回答：** 提交成功表示受理，不表示答案正确。执行状态记录任务阶段，沙箱 outcome 表示编译运行结果，verdict 表示用户判定。正常运行后输出不匹配就是 WA；编译失败就是 CE；二者成功保存后都可处于 COMPLETED。

**追问与核对：** “沙箱 HTTP 超时是不是 TLE？”不是，传输结果未知属于平台失败；用户 TLE 要有执行层超限依据。答案正确却缺少必要指标也不能直接 AC。

**源码依据：** [SandboxResultMapper](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/SandboxResultMapper.java)、[JavaLanguageJudgeStrategy](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/strategy/JavaLanguageJudgeStrategy.java)。

## 5. 重试同一次提交，如何不多生成一份记录

**参考回答：** 用户与 requestKey 形成唯一请求范围，requestHash 固定题目、语言和代码等内容。同 key 同内容回读原 ID，同 key 改内容报冲突。并发时先查不足以保证唯一，由数据库唯一约束兜底；冲突事务完全回滚后再回读。

**追问与核对：** “代码相同就不许新提交吗？”不是，用户可以用新 key 发起新的业务请求；幂等保护同一次请求，不按相同代码永久去重。

**源码依据：** [SubmissionAcceptance.requestHash/replay](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java)、[V001 唯一约束](../../codeoj-backend/mysql-init/migrations/V001__reliable_judging.sql)。

## 6. 为什么要固定 judge_spec

**参考回答：** 判题可能排队。如果受理后管理员改了题，worker 读取最新题目就会改变本次判题依据。当前把用例、资源限制和比较规则版本组合保存为固定 payload，以 hash 引用并校验。普通练习在受理时固定；比赛在发布时固定快照，提交引用该发布版本。

**追问与核对：** “hash 能保证题目安全吗？”不能，它用于内容引用和完整性核对，权限和规则合法性还需单独检查。

**源码依据：** [freezeSpec](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java)、[ContestTransactions.publish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)。

## 7. Outbox 解决什么问题，为什么还会重复消息

**参考回答：** 普通“先写 DB 再发 MQ”有提交成功但未发送就退出的窗口。Outbox 把业务记录与待发布意图放在同一个数据库事务里，后台可以补发。但 DB 与 Broker 仍是两个系统，Broker 接收而 Confirm 丢失时，重发可能重复，所以消费端仍要检查业务身份和状态。

**追问与核对：** “把 MQ 放进 @Transactional 不就行了？”本地数据库事务不能撤销已被 Broker 接收的消息，也不应长时间等待网络。当前只保证数据库内事实一起提交。

**源码依据：** [SubmissionAcceptance.write](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java)、[OutboxStore](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxStore.java)。不承诺 exactly-once 交付。

## 8. Confirm、Return、Consumer ACK 有什么区别

**参考回答：** Confirm 是发布方观察 Broker 的接收确认，Return 表示路由失败，Consumer ACK 结束消费投递。当前发布方只有 ACK 且没有 Return 才认为发布确认；消费端则要完成或持久处理任务后才正常 ACK。

**追问与核对：** “ACK 能说明 AC 吗？”不能，旧消息、已完成消息、持久 defer 也可能正常 ACK。发布确认与消费确认相互独立，见 [RabbitMQ 官方说明](https://www.rabbitmq.com/docs/confirms)。

**源码依据：** [OutboxDelivery.publish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxDelivery.java)、[ReliableJudgeConsumer.receive](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/rabbitmq/ReliableJudgeConsumer.java)。

## 9. 两个消费者为什么不能同时领取同一任务

**参考回答：** 领取在题目服务数据库事务里进行，对执行记录 SELECT FOR UPDATE，检查 QUEUED、当前代次/事件、到期条件和预算。第一个成功后保存 RUNNING、attempt/token，后一个再读就不满足领取条件。保存还带 stateVersion 条件检查。

**追问与核对：** “本地 synchronized 或 Semaphore 行不行？”只能控制同一进程，多个 worker 之间仍需共享数据库权威。本项目已有行锁加版本检查，不能只概括成 Java 锁或单一 CAS。

**源码依据：** [ExecutionCommands.claim](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)、[ExecutionRepository.find/save](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRepository.java)。

## 10. 代次、attempt、token、租约各解决什么

**参考回答：** generation/eventId 区分派发，防旧消息领取；attempt/token 区分一次执行，防旧执行续租或写回；租约限制执行权有效期，绝对尝试期限和总恢复期限防止无限续租。写结果时仍重新验证身份和时间。

**追问与核对：** “锁住了为什么还要 token？”数据库事务锁不会跨越整个远程沙箱运行。锁释放后 worker 可能失联，新尝试接管，旧结果仍可能晚到，token 用来拒绝它。

**源码依据：** [currentMessage/sameToken/owned](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)。自己画一条 T1 过期、T2 接管、T1 晚回的时间线。

## 11. worker 被杀以后由谁恢复

**参考回答：** 数据库中保留 RUNNING、token、租约和预算。ExecutionRecovery 扫描候选，recover 在行锁内重新检查；租约过期且预算允许时结束旧 attempt，递增代次、产生新事件，之后由新 worker 领取。耗尽后进入 NEEDS_ATTENTION，需管理员带版本、原因和明确预算处理。

**追问与核对：** “为什么不无限重试？”持续故障会反复消耗执行资源；任务需要明确停止自动恢复的边界，并保留可诊断历史。

**源码依据：** [ExecutionRecovery](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRecovery.java)、[recover/manualRetry](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)。

## 12. 结果已写 DB，但 ACK 前崩溃，会重复计分吗

**参考回答：** 重投后 claim 看到持久 COMPLETED，不再授予执行权。同 token 的重复 complete 会比较结果摘要，不再重复生成完成事件。榜单消费端还用业务回执与投影同事务保护，避免结果事件重投重复应用。

**追问与核对：** “只靠 messageId 去重是否足够？”不够；受理、执行完成、成绩投影是三个不同业务动作，各有身份和状态约束。

**源码依据：** [ExecutionCommands.complete](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)、[ScoreboardTransactions.project](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

## 13. 沙箱怎么运行 Java，为什么使用独立用例容器

**参考回答：** 请求通过鉴权后登记 token、期限和 slot，先由编译容器产出 class 与入口信息，再为每个用例创建新运行容器。输入经 stdin，stdout 作为待比较答案，监督器提供运行收据与资源结果。产物只读，可写空间不在用例间复用，降低用例间状态污染。

**追问与核对：** “remote 和 isolated 什么关系？”remote 是判题端的调用方式，isolated 是沙箱内部执行方式，可以同时成立。

**源码依据：** [JavaIsolatedCodeSandbox.executeOnce](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java)。

## 14. 为什么放在 Docker 里仍不足以说明安全

**参考回答：** 还要说明用户身份、网络、挂载、只读边界、资源、输出和期限。当前用户进程降权、禁网、不挂业务凭据或 Docker socket，资源受 cgroup 限制，监督器负责期限和后代清理。用户 stdout 与私有控制收据分离，不能打印一段 JSON 就假造成功。

**追问与核对：** “内存限制是 -Xmx 吗？”不只是堆大小，cgroup 约束并观测整个用例环境，包含 JVM、监督器和后代。

**源码依据：** [DockerIsolationEngine](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DockerIsolationEngine.java)、[supervisor.py](../../codeoj-backend/codeoj-backend-codesandbox/isolation/supervisor.py)。不声称容器绝对安全或已完成逃逸认证。

## 15. 数据库 token 过期，旧容器会自动消失吗

**参考回答：** 不会。数据库 token 决定结果有效性，监督器独立停止到期用户进程，registry 保存物理执行登记并回收容器和卷。管理器退出后由后继管理器恢复；删除失败保持 REAP_PENDING 和 slot 占用，确认清理后才归还容量。

**追问与核对：** “共享容量覆盖任意机器吗？”当前依赖同一 daemon、同一持久本地目录与一致配置，不能外推到多宿主全局容量。

**源码依据：** [DurableExecutionRegistry.run/recover/reap](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java)。

## 16. 当前报名相比常见秒杀模型多了什么

**参考回答：** 保留 Lua 预留、MQ、DB 确认的方向，但把预留身份和处理请求显式保存。Lua 除库存还维护用户映射、账本和 mutation；DB 请求与 Outbox 同事务。这样响应丢失、预留未落库、确认未知时，可以沿原 request/event/key 恢复，而非重新分配或直接退款。

**追问与核对：** “Lua 成功等于报名成功吗？”只代表预留，PROCESSING 还不是资格；最终由 MySQL 事务确认，比赛提交仍查资格与当前账号。

**源码依据：** [RegistrationService.register](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)、[RegistrationTransactions.persist/confirm](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。

## 17. Lua 是原子的，为什么还要 mutation 和 repair

**参考回答：** 脚本不被其他命令穿插，但运行时报错不会自动撤销之前的写入。先保存原身份、原库存和目标状态，repair 校验允许的中间值，再写确定目标。例如预留从 2 变 1，重放仍写 1；释放也不能重复加一。

**追问与核对：** “找不到映射是不是就没扣？”不能这样判断，可能在写库存后、写映射前失败；需要 mutation 与账本证据。证据矛盾时暂停核查。

**源码依据：** [contest-registration.lua 的 apply/repair](../../codeoj-backend/codeoj-backend-question-service/src/main/resources/lua/contest-registration.lua)。

## 18. 超时、失败、取消为什么不能统一退款

**参考回答：** 超时表示未知，预留或确认可能已经生效；先恢复原结果。明确失败或取消先提交数据库可回收终态，再按原身份幂等释放。DB 已确认但 Redis 标记失败，只补确认标记，不能退名额。已确认资格不能通过普通 review FAIL 释放。

**追问与核对：** “页面已确认 1/2，怎么新用户抢不到？”另一份可能在 Redis 预留中；已确认人数与可预留库存不是同一指标。

**源码依据：** [RegistrationService.synchronize/recoverUnknown](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)、[RegistrationTransactions.review/recover](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。

## 19. Redis 回到旧快照、旧对账晚到分别怎么办

**参考回答：** 旧快照可能数量相同但身份缺失，要核验原身份、DB 持久序号高水位及序号唯一约束，不能只比库存和条数。迟到对账则固定自己的 epoch/revision，失败只在该版本仍有效时暂停，不能重新取得新 revision 去破坏新恢复。

**追问与核对：** “直接按 DB 余量重建 Redis 行不行？”可能遗漏未落库预留，需关闸完整身份核验。累计账本有 10000 边界，释放记录也不能随意删除。

**源码依据：** [V005](../../codeoj-backend/mysql-init/migrations/V005__registration_recovery_fence.sql)、[RegistrationTransactions.settings/issueIfCurrent](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)、[reconcile](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)。

## 20. 比赛提交和普通练习有什么区别

**参考回答：** 比赛提交校验已确认资格、当前账号、比赛状态/ready、时间窗口、发布版本和快照归属，再把比赛上下文与固定规格写入可靠执行记录。之后复用 MQ、worker、沙箱；结果再进入成绩投影。比赛结束前合法受理的提交可能在结束后才完成。

**追问与核对：** “改题会影响已经发布的比赛吗？”比赛引用发布快照；普通练习按受理时固定规格，固定时点不同。

**源码依据：** [ContestTransactions.publish/submit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)。

## 21. 结果乱序为什么还能正确计分

**参考回答：** 每用户每题取最早 AC 的 acceptedAt，解题数为不同题数，achievedAt 为各题首次 AC 时间的最大值。更早提交的 AC 晚到会修正时间，同题重复 AC 不多加题。回执与投影同事务，零分确认用户也入榜。并列名次为严格领先人数加一。

**追问与核对：** “收到 AC 给分数加一行不行？”会把同题多次 AC 算成多题，也无法修正乱序时间。用[榜单例子](05-成绩榜单与结算链路.md)现场手算。

**源码依据：** [ScoreboardTransactions.project/snapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

## 22. Redis 缓存、重建和最终结算怎样配合

**参考回答：** DB 保存成绩投影和权威版本，Redis 缓存 entries，key 包含投影版本、revision、cacheEpoch 和分页。重建从完整结果事实生成新版本并核验后切换，旧版本保留。结束时间到后先 FINALIZING，等待提交与报名收敛，核对资格/容量并重建一致，最后 FINISHED。

**追问与核对：** “缓存命中是不是不访问 DB？”当前仍先读元数据。“有 NEEDS_ATTENTION 能不能结束？”不能把平台未决偷偷算 WA，需明确处理。

**源码依据：** [ScoreboardService.page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java)、[rebuild/finish/settledFacts](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

## 23. 跨服务怎么共享登录，旧 Cookie 怎样降权

**参考回答：** Spring Session 把会话放 Redis，多个服务使用一致配置。Session 中 User 对象只提供身份 ID，SessionUserResolver 再查询当前账号、角色、删除和封禁状态。降权后同 Cookie 也会在业务权限检查被拒绝；查询失败不回退旧角色。

**追问与核对：** “getLoginUser 是 default 方法，就不会远程调用吗？”方法本地执行，但传入的 getById 是 Feign 远程查询。内部密钥也不代表用户有管理员权限。当前登录不是已实现 JWT 统一鉴权。

**源码依据：** [SessionUserResolver](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/auth/SessionUserResolver.java)、[UserFeignClient](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/service/UserFeignClient.java)、[AuthInterceptor](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/aop/AuthInterceptor.java)。
