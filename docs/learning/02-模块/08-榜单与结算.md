# 榜单与结算：从判题事实得到可解释的排名

判题完成只回答“这份程序是什么结果”。比赛还需要回答“这个人解了几题、何时达到这个成绩、结果迟到后排名如何变化”。本篇从具体计分规则出发，跟到事件消费、数据库投影、缓存、重建和结算。

当前实现以数据库成绩投影为主体，Redis 缓存分页 entries。不要按常见教程直接把它介绍为 Redis ZSet 排名。

## 1. 先手算规则，再读代码

规则版本是 FIRST_AC_V1。对每个用户、每道比赛题，取其 AC 提交中最早的 acceptedAt；该用户解题数等于有 AC 的不同题数，achievedAt 等于这些首次 AC 时间的最大值。

这里的首次是**受理时间最早**，不是最早完成判题或最早消费的 AC。比赛结束前已受理、之后才完成的结果可以计入。

排名先比较解题数，更多者在前；同解题数比较 achievedAt，更早者在前；两者相同并列。userId 只稳定显示顺序，不打破业务并列。确认资格但没有 AC 的选手以零分入榜。

| 选手 | A 的最早 AC 受理时间 | B 的最早 AC 受理时间 | 解题数 | achievedAt |
| --- | --- | --- | --- | --- |
| U1 | 10 分钟 | 20 分钟 | 2 | 20 分钟 |
| U2 | 15 分钟 | 20 分钟 | 2 | 20 分钟 |
| U3 | 8 分钟 | 无 | 1 | 8 分钟 |
| U4 | 无 | 无 | 0 | null |

U1、U2 并列第 1，U3 第 3，U4 第 4。名次是“严格领先人数 + 1”，不是按列表下标连续编号。

现在 U1 一份第 12 分钟受理的 B 提交晚到并判 AC，B 的最早时间改成 12，achievedAt 从 20 变为 12，U1 排到 U2 前面。又来一份第 25 分钟受理的 B AC，不再改变解题数和最早时间。

## 2. 结果事件从哪里来

打开 [ExecutionCommands.complete](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)。它在同一事务中保存执行完成、兼容 judgeInfo、结果版本/摘要与 JUDGE_RESULT Outbox。

消息只含 submissionId、resultVersion 等引用；消费者还要查数据库事实，而不是信任一个客户端声称“此人 AC”就加分。

阅读顺序：[ScoreboardMessaging](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardMessaging.java) → [ScoreboardConsumer.receive](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardConsumer.java) → [ScoreboardTransactions.project](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

scoreboard 开关开启后，普通练习的结果也可能通过同类结果事件，但只登记处理回执，不改任何比赛成绩。比赛计分先要求执行上下文确实归属比赛。

## 3. 消费一条结果具体更新哪些表

结构见 [V004](../../../codeoj-backend/mysql-init/migrations/V004__contest_scoreboard.sql)。先记住事实与投影的区别：原提交、执行结果、资格和题目快照是重算依据；score 表是从这些依据计算出的查询结果。

| 表 | 负责什么 |
| --- | --- |
| `scoreboard_result_receipt` | 某个结果事件已经持久处理，防重复投影 |
| `contest_score_problem` | 某用户某题最早 AC 的受理时间 |
| `contest_score_user` | 某用户的解题数与 achievedAt |
| `contest_scoreboard_state` | 当前启用版本、revision、cacheEpoch、最终版本 |
| `contest_scoreboard_version` | 每个投影版本的状态、摘要与时间 |

project 正常流程：

1. 用 eventId、提交 ID、resultVersion 核验原 Outbox 事件与完成记录。
2. 锁比赛，检查是否已经有该事件回执。
3. 为确认选手补零分行；读取并核验该提交的比赛、快照、资格、受理时间、规格和结果摘要。
4. AC 时插入该题最早时间，或用更早的 acceptedAt 更新；非 AC 不增加解题数。
5. 按各题记录重新计算 COUNT 和 MAX，更新用户成绩并推进 revision。
6. 同事务插入事件回执，然后才由消费者 ACK。

当前实现有意用比赛锁串行化这一版的投影、重建与资格变化，并对用户成绩记录加锁。这样易于保证一致性，但可能限制同场并发，不应把它讲成已经验证的高吞吐榜单方案。

## 4. 去重为什么不能只说“收到过 messageId”

如果先保存回执，再更新成绩时失败，而两个操作不在同一事务，重投可能因“处理过”被丢弃，成绩永远缺失。反过来先改成绩，再保存回执失败，重投又可能重复应用。

当前回执和投影更新同事务，失败一起回滚。再加上每用户每题的最早 AC 聚合，同题多条 AC 不重复加题。

判题 complete 的结果幂等和榜单 project 的事件幂等分别保护不同动作：前者防重复完成，后者防重复投影。只讲“MQ 消息 ID 去重”不够。

如果 Outbox 发布已 CONFIRMED，但迟迟没有结果回执，`recoverPublications` 会按有限预算重新开启原事件发布。Broker 确认不能替代业务消费回执。

## 5. 查询和 Redis 缓存怎样配合

沿 [ScoreboardController.page](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardController.java) → [ScoreboardService.page](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java) → `ScoreboardTransactions.snapshot` 阅读。

查询先从 DB 取当前权威元数据，再尝试读取对应的 Redis entries。缓存未命中或不可用时查数据库，返回页面并尝试缓存，当前 TTL 为 15 秒。

缓存 key 的结构是：

```text
contest:scoreboard:{contestId}:projectionVersion:revision:cacheEpoch:page:pageSize
```

| 标识 | 为什么放进 key |
| --- | --- |
| projectionVersion | 重建后的新榜单不混入旧版本页 |
| revision | 同版本发生投影变化后使用新缓存 |
| cacheEpoch | 管理员清缓存时切到新命名空间 |
| page/pageSize | 不同分页内容分开 |

这是 key 结构示意，花括号包住实际 contestId。Redis 只缓存 entries，版本与新鲜度元数据来自 DB。查询不是完全绕开数据库，因此不能把缓存命中描述为整个请求零 SQL。

页面还返回 pendingCount、projectionPendingCount、asOf、final 等信息。排名暂时没变时，先区分“判题未完成”和“已完成但尚未投影”。

## 6. 为什么不能从旧榜单直接生成最终榜

旧投影可能存在丢行、聚合漂移或结果事件迟到。`rebuild` 从所有可验证的完成事实，重新计算每用户每题最早 AC，再生成每人总成绩，包括零分资格用户。

当前重建过程在数据库事务中创建新 projectionVersion、写新明细和汇总、核验新结果，再切换 activeVersion。中途失败回滚，旧版本仍可读取。它不是在原榜单上逐行清空重写，也不是无限规模的离线计算系统。

重建限定在 FINALIZING 的收敛条件下；结束后的更正走显式 final revision，保留原最终版本并审计。当前有 10000 位参与者、50000 份比赛提交等重建边界。

## 7. 到了结束时间，为什么还不能 FINISHED

比赛到 endAt 后先进入 FINALIZING。需要检查：

- 所有比赛提交已形成完整结果，没有 QUEUED、RUNNING、RETRY_WAIT 或 NEEDS_ATTENTION。
- 报名没有 PROCESSING、MANUAL_REVIEW，也没有未完成的标记/回收。
- 确认资格、容量、用户身份与发布上下文相互一致。
- Redis 模式在结束后完成关闸对账，不能存在未落库预留。
- 已重建，并且投影与权威事实一致。

最后 `finish` 才标记最终版本并写 FINISHED。不能将 NEEDS_ATTENTION 自动当作 WA 来让比赛结束，也不能只等 MQ 队列看起来为空。

注意重建可直接依据数据库事实恢复缺失投影，并不要求所有历史结果消息先按顺序消费。未决事实与投影传输延迟要分别判断。

## 8. 面试中如何讲这个设计

先手算一组乱序 AC，说明 acceptedAt 与完成时间的区别。然后解释“完成事实 → 结果事件 → 同事务回执与投影 → 版本化页面缓存 → 收敛后重建与最终结算”。最后补充比赛锁和有界重建的容量取舍。

不要说“收到 AC 就给 Redis 分数加一”。那无法解释同题重复、迟到更早 AC、并列名次、零分用户和最终核验。

## 9. 自测与核对

1. **两人都是 2 题，达成时间一样，谁第一？** 并列；userId 只影响显示顺序。
2. **同一题第二次 AC 会再加一题吗？** 不会，只可能把该题最早时间改得更早。
3. **比赛结束后才判完的提交能算吗？** 看 acceptedAt 是否在合法窗口，以及资格/快照/结果是否有效。
4. **删除所有投影后还能重建吗？** 在完整事实和收敛条件满足时可以，不能靠残缺的旧榜单作权威。
5. **缓存命中是否无需 DB？** 当前仍先读 DB 元数据，再按对应版本查缓存。

通过标准：手算第 1 节例子，定位 project 的去重事务、snapshot 的 rank SQL、rebuild/finish 的条件。测试对照：[ScoreboardTest](../../../codeoj-backend/codeoj-backend-question-service/src/test/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTest.java) 的 `handCalculatedTieAndEarlierAcDeliveredLastChangeAchievedAt`、`duplicateAndSameProblemAcNeverAddPoints`、`finishRequiresRebuildAndDriftCannotBeSilentlyFinalized`；缓存见 [ScoreboardCacheTest](../../../codeoj-backend/codeoj-backend-question-service/src/test/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardCacheTest.java)。
