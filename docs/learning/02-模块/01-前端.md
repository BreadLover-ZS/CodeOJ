# 前端与 API：把页面操作接到后端源码

读本篇的目的，是能从一个按钮找到后端入口，并解释请求重试、状态查询和权限展示。无需掌握全部 Vue 样式；先看 `<script setup>` 中的请求和状态变量。

前端使用 Vue 3、TypeScript、Arco Design 和 Monaco。页面负责发请求和展示状态，资格、计分和执行权由后端决定。

## 1. 从路由找到页面，再找到实际请求

依次打开 [routes.ts](../../../codeoj-frontend/src/router/routes.ts)、[access/index.ts](../../../codeoj-frontend/src/access/index.ts)、[store/user.ts](../../../codeoj-frontend/src/store/user.ts)。

路由配置把 URL 对应到页面组件，并用 `meta.access` 标记界面访问要求。进入页面前，路由守卫检查前端登录信息；尚未加载时调用 `user/getLoginUser` 查询后端。未登录跳转登录页，权限不足跳转无权限页。

这只控制页面导航。用户仍可绕开按钮直接请求 API，所以后端必须重新鉴权。前端 store 中的角色也可能比数据库旧。

## 2. 普通做题：从题目详情到提交列表

在 `ViewQuestionView.loadData` 中，`props.id` 传给题目 VO 查询。返回的数据给左侧题干和限制展示；右侧编辑器通过 `changeCode` 更新 `form.code`。

`doSubmit` 的正常过程是：

1. 防止提交中再次点击，读取当前题目、语言、代码。
2. 对请求内容计算 SHA-256 指纹，查找本次待确认请求身份。
3. 内容未变时沿用原 key；内容变化时生成新 key。
4. 请求体带 `requestKey`，请求头带同一 `Idempotency-Key`，调用普通提交 API。
5. 业务成功后清除待确认身份，跳转 `/question_submit`。

为什么页面需要保存 key？例如后端已经受理，但响应丢失。用户再点一次时，如果代码没变，原 key 可以让后端返回同一个提交 ID。页面禁止双击只能减少本页并发，不能处理网络重试和多端请求，最终仍靠后端唯一约束。

普通练习页面保存的是 `fingerprint + key`，并非源代码副本。若用户编辑了代码，它会按新内容生成新身份；因此“请保留当前代码重试”的提示有实际含义。

## 3. 两个页面怎样看到结果

| 场景 | 查询方式 | 当前轮询条件 |
| --- | --- | --- |
| 普通练习提交列表 | `listQuestionSubmitByPageUsingPost` | 当前页存在旧 status=0/1 时，每 3 秒刷新；没有待处理项或卸载时停止 |
| 比赛详情 | `submissionStatus(lastId)`，请求 `/api/submissions/{id}` | 每 2 秒调用 poll；存在 lastId 就查询，当前未按终态自动停止 |

提交接口与结果查询接口分离。普通列表主要用兼容 `status` 展示，可靠执行的完整状态还包括 RETRY_WAIT、NEEDS_ATTENTION 等。读后端时以 `executionStatus` 为准，不把旧 status=2 理解为 AC。

查询结果失败也不说明判题失败：可能是网络或会话暂时不可用。恢复查询应沿原提交 ID，而不是自动再交一份代码。

## 4. 比赛提交：待确认时保留整份原请求

比赛详情的 `submit` 会把比赛题目快照、发布版本、语言和代码装成 body，用 `stableKey` 取得 key，再存到 `pending`。`sendPending` 重发的就是这个原 body 和原 key。

例如第一次提交代码 A，响应未知；编辑器后来变成代码 B。点击“重试原请求”仍发送 A，不能把 B 填进原 key，否则后端会报内容冲突。此处比普通练习页多保留了一份内存中的原请求副本。

`stableKey` 在内存和 sessionStorage 中保存指纹与 key，源代码只保存在页面内存。刷新页面后不能只凭 key 恢复已丢失的源码。成功后 `clearKey`；确定的部分 4xx 也会结束页面中的 pending，具体以 `sendPending` 分支为准。

报名调用 `POST /api/contests/{id}/registrations`，返回 PROCESSING 时显示确认中，CONFIRMED 才表示取得资格。详情页周期 `load` 刷新比赛和本人报名状态。

## 5. 人数、榜单和管理页怎么理解

比赛列表和详情展示的是“已确认人数 / 总名额”，其中已确认人数为 `capacity - remainingCapacity`。有些名额正在 Redis 预留中，因此“已确认 0 / 1”不保证此刻还能抢到名额。

[ScoreboardPanel.vue](../../../codeoj-frontend/src/components/ScoreboardPanel.vue) 展示后端算出的名次及版本元数据，前端不自行累计 AC。[ManageContestsView.vue](../../../codeoj-frontend/src/views/contest/ManageContestsView.vue) 管理草稿、发布、取消等；[RegistrationOperations.vue](../../../codeoj-frontend/src/components/RegistrationOperations.vue) 提交版本和原因，调用报名运维接口。

管理页面中携带版本是为了防止旧页面覆盖新管理结果，不是用户权限凭据。后端仍要检查当前管理员角色。

## 6. 打开浏览器时怎样核对链路

启动方法见[运行篇](06-部署与运行.md)。运行后，在 Network 中核对：

1. 请求路径是否进入正确 API；请求是否携带会话 Cookie。
2. 同一未确认请求重试时 key 是否一致，body 是否为原内容。
3. 提交响应中是否拿到 ID；后续是否使用这个 ID 查询。
4. 区分 HTTP 202/409/503 与响应体 `code/data/message`，不能只看其中一个。

API 默认地址与启动代理以 `OpenAPI.ts`、`VUE_APP_API_BASE_URL` 和本轮启动脚本为准。重新生成客户端前先在临时目录比较差异，避免覆盖已有请求协议。

## 7. 自测与核对

- **题目：** 为什么按钮设置 loading 仍然需要幂等 key？
  **核对：** loading 只管本页点击，响应丢失、刷新、多端重试仍会到后端。
- **题目：** 普通列表不再轮询和比赛页还在轮询，是否说明判题流程不同？
  **核对：** 两者复用可靠判题，只是页面查询与停止条件不同。
- **题目：** 比赛请求响应未知后改了代码，重试原请求应该发什么？
  **核对：** `pending` 保存的原 body 与原 key；不能套用新编辑内容。

通过标准：能从页面函数定位一个请求、对应 Controller 和结果查询；能解释两个提交页面的重试差别。继续读[公共层与用户服务](02-公共层与用户服务.md)。
