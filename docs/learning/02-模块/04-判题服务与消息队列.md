# 判题服务与消息队列：事件、执行权和答案比较

前一篇完成了数据库受理。本篇从待发布事件继续往下读：它如何进入 MQ、worker 如何执行、为什么消息可能重复，以及谁来恢复失联任务。

先记住一句话：消息通知“有任务”，数据库决定“现在能否执行”，沙箱负责“实际运行”，判题策略决定“答案是否正确”。

## 1. 先认清三个容易混淆的对象

| 对象 | 源码 | 内容与作用 |
| --- | --- | --- |
| 派发消息 | [JudgeDispatch](../../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/reliability/JudgeDispatch.java) | 提交 ID、eventId、generation、协议版本等；通知 worker 尝试领取 |
| 领取响应 | [JudgeLease](../../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/reliability/JudgeLease.java) | 是否成功、代码、用例、限制、attempt/token、期限 |
| 写回命令 | [ExecutionCommand](../../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/reliability/ExecutionCommand.java) | 提交 ID、attempt/token，加结果或平台错误码 |

派发消息不放源码和隐藏用例。worker 不能收到消息就直接运行，必须领取成功。这样迟到或重复消息会在数据库权威检查处停止，不继续使用过期执行材料。

## 2. Outbox 如何变成 MQ 消息

阅读顺序：[OutboxRelay.tick](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxRelay.java) → [OutboxStore.due/claim](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxStore.java) → [OutboxDelivery.publish](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/outbox/OutboxDelivery.java) → `OutboxStore.record`。

### 先领取发布权，再在事务外发送

`due` 找到到期、PENDING 且没有有效发布租约的事件。`claim` 对事件加行锁，检查预算，生成发布 token，把这次发送先记为 UNKNOWN，保存发布租约。事务返回后才由 `publish` 调用 RabbitTemplate。

为什么发布也有 token？多个发布器可能扫描同一个事件，旧回调也可能晚到。发布 token 标识某一次发送，不是 worker 的执行 token。

### 发送之后记录什么

| 发布观测 | 记录与后续 |
| --- | --- |
| Confirm ACK 且无 Return | Outbox 标记 CONFIRMED |
| Confirm NACK | 记录明确否定，满足条件时安排重试 |
| Return | 路由失败，不能按发布成功处理 |
| 发送异常、确认未知或超时 | 保留 UNKNOWN 的证据，可能再次发布 |
| 发布预算耗尽 | ATTENTION，交由业务恢复或管理处理 |

一个事件可以有多条 `publish_attempt`。迟到失败只允许影响自己仍持有的发布租约，不能撤销其他尝试的成功确认。不能覆盖 UNKNOWN 历史来伪装“之前没发送过”。

这里解决的是可靠传输，业务是否完成还要看执行状态或业务回执。

## 3. 当前消息拓扑长什么样

打开 [ReliableJudgeTopology](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/rabbitmq/ReliableJudgeTopology.java)：

```text
codeoj.judge.v1.exchange -- routingKey=judge --> codeoj.judge.v1.queue
                                                    |
                                       reject / requeue=false
                                                    v
                         codeoj.judge.v1.dlx --> codeoj.judge.v1.quarantine
```

交换机、队列是 durable，消息按 persistent 发送。消息格式错误时进入隔离队列；暂时不可用的业务异常走退避重投。隔离队列不是所有业务失败的统一终点，用户 WA/CE 也不该进死信队列。

旧 `code_exchange/code_queue` 属于基础版消费者。不要使用它的消息体、类名和四态模型来解释上述新拓扑。

## 4. Consumer 如何把消息交给 worker

阅读 [ReliableJudgeConsumer.receive](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/rabbitmq/ReliableJudgeConsumer.java)。

它先限制消息大小，解析并校验 `JudgeDispatch`。格式错误 `basicReject(tag,false)`，不随便根据坏消息修改数据库。合法消息才进入 `worker.process`。

worker 正常返回后 `basicAck`。如果发生不能证明业务状态已经持久处理的异常，先保留未确认投递退避，再 `basicNack(...,true)` 要求重投。不能把每个异常都先 ACK，否则无法再靠 MQ 交付这次处理机会。

### 三种确认不要混在一起

- **Publisher Confirm：** 发布端观察 Broker 对发送的确认。
- **Return：** 发布消息无法按当前路由进入队列时的返回。
- **Consumer ACK：** 消费端结束当前投递，Broker 可以移除该投递。

它们没有证明用户程序 AC。RabbitMQ 对发布确认和消费确认的独立性见[官方说明](https://www.rabbitmq.com/docs/confirms)。本项目还要以业务持久状态判断是否已经完成处理。

## 5. worker 的正常执行顺序

打开 [ReliableJudgeWorker.process](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/ReliableJudgeWorker.java)，按下面几段阅读。

### 5.1 先限制本实例容量

`slots.tryAcquire` 使用 Semaphore 限制本实例同时处理的任务数。没有名额时，调用 `deferExecution` 把任务持久延后；延后结果未知则抛出异常，不能直接 ACK。

等待 worker 名额属于平台容量问题，不是用户代码执行超时，不判 TLE。

### 5.2 远程领取执行权

`questions.claimExecution(message)` 经 Feign 回到题目服务 `ExecutionCommands.claim`。领取失败可以是已完成、旧派发、尚未到期或已有有效执行者；明确 `claimed=false` 后直接返回，不调用沙箱。null/未知响应则抛异常。

领取成功后，题目服务生成 attempt/token，返回固定规格与期限。worker 不直接更新共享业务数据库。

### 5.3 领取后定期续租

worker 每 5 秒调用 heartbeat。题目服务只允许有效 owner 续租，并且租约不超过本次绝对期限。明确续租失败会标记 lost，worker 不再主动写回结果；续租网络异常本身只能说明未知，最终仍由数据库写回检查兜底。

当前领取默认租约约 15 秒，尝试绝对期限不超过 60 秒及总恢复期限；沙箱还会施加自己的更短预算。不要把“每次续租 15 秒”理解成可以无限运行。

### 5.4 调用沙箱，再决定用户判定

worker 从 lease 构建 ExecuteCodeRequest，交给 `CodeSandboxProxy(factory.newInstance(sandboxType))`。当前工厂只支持 `remote`。

[CodeSandboxFactory](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxFactory.java) 负责选择调用实现，[CodeSandboxProxy](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxProxy.java) 包装执行调用；[JudgeManager](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/JudgeManager.java) 按语言选择判题策略。这是代码中的工厂、代理、策略职责，不能据此说当前已支持所有语言或所有沙箱类型。

### 5.5 写回并释放本地名额

成功生成判定后调用 complete；平台异常调用 fail。如果 fail 也无法持久处理，异常到达 Consumer，当前投递不正常 ACK。finally 取消本地心跳并释放 Semaphore。

这里释放的是 worker 本地名额。沙箱物理 slot 由沙箱确认清理后释放，二者不是同一份容量。

## 6. 判题策略具体比较什么

先读 [SandboxResultMapper.userVerdict](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/SandboxResultMapper.java)。

| 沙箱结果 | 下一步 |
| --- | --- |
| 空响应、无 outcome、status/outcome 矛盾 | 平台协议异常 |
| PLATFORM_ERROR / REJECTED | 平台失败恢复 |
| CE / RE / TLE / MLE / OUTPUT_LIMIT | 生成对应用户判定 |
| EXECUTED | 返回 null，继续策略比较 |

这里的 null 代表“还要比较答案”，不是执行失败。继续读 [JavaLanguageJudgeStrategy.doJudge](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/strategy/JavaLanguageJudgeStrategy.java)：先检查必要指标、输出数量和限制，再按时间、内存、逐用例答案决定 TLE、MLE、WA 或 AC。

当前时间单位是 ms，内存是 KiB。比较器 [TextOutputComparator](../../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/codesandbox/TextOutputComparator.java) 只规范换行，不任意 trim 全部空白。`COMPLETED + WA` 是正常判题完成。

## 7. 恢复时为什么需要代次、token 和租约

```text
QUEUED --claim--> RUNNING --complete--> COMPLETED
   |                |
容量延后          平台失败 / 租约过期
   v                v
RETRY_WAIT --到期 recover--> QUEUED（新代次、新事件）
   └── 次数或总期限耗尽 --> NEEDS_ATTENTION
```

这是帮助理解的概览，实际 `recover` 还处理 QUEUED 长期未领取、全局期限和预算。入口是 [ExecutionRecovery.tick](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRecovery.java)，权威检查是 [ExecutionCommands.recover/owned](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)。

代次与 eventId 拒绝旧派发；attempt/token 拒绝旧执行；租约和绝对期限拒绝已经失效的 owner。恢复可能让同一提交发生多次物理尝试，但只允许符合当前身份与状态的结果生效。

DB 完成后未 ACK 的重复消息会在 claim 被挡住。旧 worker 晚到的结果会在 complete 的 owned 检查被挡住。两种重复发生位置不同，需要分别解释。

## 8. 三类事件的关系

| 事件 | 发布/消费归属 | 业务完成依据 |
| --- | --- | --- |
| JUDGE_DISPATCH | OutboxRelay / 判题服务 | 执行状态与结果 |
| REGISTRATION_CONFIRM | RegistrationMessaging / 报名消费者 | 请求与确认资格 |
| JUDGE_RESULT | ScoreboardMessaging / 榜单消费者 | 结果业务回执与投影 |

三者复用 Outbox 发送机制，但不能都交给判题 worker。成绩发布成功仍可能未投影，因此榜单有自己的回执与重放预算。

## 9. 自测与核对

1. **Confirm 成功、worker 还没收到，前端应显示 AC 吗？** 不能；它只确认发布环节，执行和答案比较尚未完成。
2. **重复消息进了 Consumer，是幂等失效吗？** 不是；幂等主要看能否重复授予执行权或重复写业务结果。
3. **沙箱 HTTP 超时和用户 TLE 有什么区别？** 前者是执行结果未知的平台异常，后者是执行层明确给出的用户超限判定。
4. **旧 token 写回位置在哪？** complete/heartbeat 的 owned；指出 attempt、token 和三个时间边界。
5. **worker 没容量为什么可以 ACK？** 只有持久 defer 成功，任务已交给恢复状态机时才可正常返回 ACK。
