# 02 模块 · 代码沙箱

## 0. 阅读目标与证据边界

---

## 1. 先看全景：谁调用谁

```text
JudgeServiceImpl#doJudge
  -> CodeSandboxFactory#newInstance
  -> CodeSandboxProxy#executeCode
  -> RemoteCodeSandbox#executeCode
  -> POST /executeCode
  -> ExecuteCodeController#executeCode
  -> JavaNativeCodeSandbox#checkAuth
  -> JavaNativeCodeSandbox#executeCode
```

这条路径跨越两个服务：

| 所在服务          | 代码                                                                                                                                                                           | 职责                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Judge Service | [`CodeSandbox`](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandbox.java)                  | 定义统一的执行接口                                |
| Judge Service | [`CodeSandboxFactory`](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxFactory.java)    | 根据配置选择 `example`、`remote` 或 `thirdParty` |
| Judge Service | [`CodeSandboxProxy`](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxProxy.java)        | 在调用前后记录完整请求与响应                           |
| Judge Service | [`RemoteCodeSandbox`](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/impl/RemoteCodeSandbox.java) | 把 Java 对象序列化为 HTTP 请求                    |
| Code Sandbox  | [`ExecuteCodeController`](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/controller/ExecuteCodeController.java)        | 校验调用密钥并进入执行服务                            |
| Code Sandbox  | [`JavaNativeCodeSandbox`](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaNativeCodeSandbox.java)      | 写源码、调用 `javac/java`、采集结果并清理              |

### 1.1 三种客户端实现并不等价

- `example`：把输入列表原样当作输出，并填入固定的耗时、内存和 Accepted 信息，只适合打通调用流程，不执行用户代码；
- `remote`：当前真实路径，通过 HTTP 调用独立沙箱服务；
- `thirdParty`：只有空桩实现，直接返回 `null`。

`CodeSandboxFactory` 对未知类型默认返回 `ExampleCodeSandbox`。这能避免工厂直接报错，却也可能让错误配置悄悄变成假执行结果。示例实现还把任务枚举的 `SUCCEED=2` 写入沙箱 `status`，而真实沙箱用 `1` 表示成功、`2` 表示失败，两者契约并不一致。排查时不能只看接口有返回，还要确认实际选中的类型和状态来源。

### 1.2 配置如何到达两端

Judge Service 读取：

```yaml
codesandbox:
  type: ${CODESANDBOX_TYPE:remote}
  remote:
    url: ${CODESANDBOX_REMOTE_URL:http://localhost:8090/executeCode}
    auth-secret: ${CODESANDBOX_REMOTE_AUTH_SECRET:secretKey}
```

沙箱服务读取：

```yaml
codesandbox:
  auth-secret: ${CODESANDBOX_REMOTE_AUTH_SECRET:secretKey}
  run-timeout-ms: ${CODESANDBOX_RUN_TIMEOUT_MS:5000}
  compile-timeout-ms: ${CODESANDBOX_COMPILE_TIMEOUT_MS:15000}
```

Compose 环境中，Judge Service 使用 `http://codeoj-codesandbox:8090/executeCode`，沙箱端口只通过 `expose` 暴露给内部网络，没有发布到宿主机端口。两端必须使用相同密钥。

这只说明默认部署拓扑，不能证明网络策略、密钥管理或沙箱隔离已经通过安全验证。

## 2. 先读契约，再读执行过程

### 2.1 请求结构

[`ExecuteCodeRequest`](../../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/codesandbox/ExecuteCodeRequest.java) 包含三个字段：

```json
{
  "inputList": ["1 2", "10 20"],
  "code": "public class Main { ... }",
  "language": "java"
}
```

| 字段          | 当前用途                | 需要注意                                   |
| ----------- | ------------------- | -------------------------------------- |
| `inputList` | 每个元素作为一次进程执行的 stdin | 每个用例都会启动一个新的 JVM；`null` 会被转为空列表        |
| `code`      | 写入临时 `.java` 文件     | 空白或 `String.length()` 超过 262,144 时返回失败 |
| `language`  | 从提交记录传入             | 沙箱端没有读取该字段，执行命令始终是 `javac` 和 `java`    |

### 2.2 响应结构

[`ExecuteCodeResponse`](../../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/codesandbox/ExecuteCodeResponse.java) 包含：

```json
{
  "outputList": ["3", "30"],
  "message": "ok",
  "status": 1,
  "judgeInfo": {
    "time": 42,
    "memory": 0,
    "message": null
  }
}
```

- `outputList`：按输入用例顺序保存标准输出；
- `message`：沙箱调用说明，成功时为 `ok`，失败时保存错误摘要；
- `status`：`JavaNativeCodeSandbox` 用 `1` 表示成功、`2` 表示失败；示例实现没有遵守这套值域；
- `judgeInfo.time`：所有用例中最大的墙钟耗时，不含编译耗时；
- `judgeInfo.memory`：当前固定为 `0L`，没有采集真实内存；
- `judgeInfo.message`：沙箱成功时没有设置，最终 verdict 由判题策略产生。

### 2.3 三层状态不能混用

| 层次   | 字段                           | 回答的问题                                   |
| ---- | ---------------------------- | --------------------------------------- |
| 提交任务 | `QuestionSubmit.status`      | 任务处于 WAITING、RUNNING、SUCCEED 还是 FAILED？ |
| 沙箱调用 | `ExecuteCodeResponse.status` | 本次编译运行是否由沙箱正常完成？                        |
| 判题结果 | `JudgeInfo.message`          | 用户答案是 Accepted、Wrong Answer、TLE 等哪种结果？  |

当前 `JudgeServiceImpl` 调用沙箱后，没有先检查 `ExecuteCodeResponse.status`，而是直接把 `judgeInfo` 交给判题策略。沙箱失败响应中的 `judgeInfo` 为 `null`，因此编译错误、运行错误或沙箱超时可能触发异常，随后由消息消费者把提交任务写成 `FAILED`。现有代码不能稳定地把这些情况映射为 CE、RE 或 TLE。

## 3. HTTP 入口与调用鉴权

[`ExecuteCodeController#executeCode`](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/controller/ExecuteCodeController.java) 的顺序很短：

```java
codeSandboxService.checkAuth(auth);
return codeSandboxService.executeCode(executeCodeRequest);
```

`checkAuth` 校验 `auth` 请求头是否与服务配置一致：

```java
if (StrUtil.isBlank(auth) || !authSecret.equals(auth)) {
    throw new SecurityException("无权限访问代码沙箱");
}
```

[`GlobalExceptionHandler`](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/exception/GlobalExceptionHandler.java) 会把该异常转换成 HTTP 401：

```json
{
  "status": 401,
  "message": "无权限访问代码沙箱"
}
```

这里要区分两个问题：

- 调用鉴权回答“哪个服务可以请求执行代码”；
- 沙箱隔离回答“获准执行的用户代码可以访问哪些资源”。

共享密钥只处理第一个问题。它不能限制用户代码读取文件、读取环境变量、访问网络、申请内存或创建子进程。

`RemoteCodeSandbox` 也没有检查 HTTP 状态码，只读取响应正文并反序列化。401 和 500 响应中的 `status`、`message` 字段可能被映射进 `ExecuteCodeResponse`，但下游仍没有对应的失败分支。

## 4. 核心源码：一次执行的真实时间线

本节按 [`JavaNativeCodeSandbox#executeCode`](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaNativeCodeSandbox.java) 的实际顺序阅读。

### 4.1 校验代码与输入

```java
String code = executeCodeRequest.getCode();
List<String> inputList = executeCodeRequest.getInputList();
if (StrUtil.isBlank(code) || code.length() > MAX_CODE_LENGTH) {
    return fail("代码为空或超过长度限制");
}
if (inputList == null) {
    inputList = new ArrayList<>();
}
```

- 代码长度使用 `String.length()`，限制的是 Java 字符单元数量，不是 HTTP 请求字节数；
- 没有限制用例数量和单个输入长度；
- `inputList=null` 会变成空列表，之后不启动任何用户进程，仍可能返回成功；
- `executeCodeRequest.getCode()` 位于方法的 `try` 之前，请求对象为 `null` 时异常不会被本方法的 catch 转换成 `fail()`，而会进入全局 500 处理。

### 4.2 提取主类名并写入临时目录

```java
workDir = Files.createTempDirectory("codeoj-sandbox-");
String className = resolveClassName(code);
Path sourceFile = workDir.resolve(className + ".java");
Files.write(sourceFile, code.getBytes(StandardCharsets.UTF_8));
```

类名正则是：

```java
public\s+class\s+([A-Za-z_]\w*)
```

能匹配 `public class Main`，匹配不到时默认文件名为 `Main.java`。这不是 Java 语法解析器，因此需要看到它的边界：

- `public final class Main` 不符合当前正则；
- 注释或字符串中的 `public class Xxx` 可能被提前匹配；
- 带 `package` 的源码仍只按简单类名启动；
- 请求里的 `language` 不影响文件后缀和命令。

积极的一点是，`ProcessBuilder` 接收分开的命令参数，没有把用户输入拼成 shell 命令；类名也只允许字母、数字和下划线。这里没有直接的 shell 字符串注入路径，但这不等于进程具备资源隔离。

### 4.3 启动编译进程

```java
Process compile = new ProcessBuilder(
        "javac", "-encoding", "UTF-8", sourceFile.toAbsolutePath().toString())
        .directory(workDir.toFile())
        .start();
String compileError = readOutput(compile.getErrorStream());
boolean compileFinished = compile.waitFor(compileTimeoutMs, TimeUnit.MILLISECONDS);
```

正常情况下，`javac` 在临时目录中生成 `.class` 文件。非零退出时，沙箱截取最多 500 个字符的编译错误并返回 `status=2`。

需要特别注意调用顺序：代码先同步读完 stderr，再执行带超时的 `waitFor`。`readOutput` 会一直读到 EOF 或达到 64 Ki 个字符；如果编译进程一直不关闭错误流，控制流可能到不了 `waitFor(15s)`。因此配置了编译超时，不等于整个编译阶段一定能在 15 秒内返回。

### 4.4 每个用例启动一个新 JVM

编译只执行一次，运行阶段遍历 `inputList`：

```java
for (String input : inputList) {
    Process run = new ProcessBuilder(
            "java", "-Dfile.encoding=UTF-8", "-XX:+UseSerialGC",
            "-cp", workDir.toAbsolutePath().toString(), className)
            .directory(workDir.toFile())
            .start();
    // 写 stdin -> 读 stdout -> waitFor -> 检查退出码 -> 必要时读 stderr
}
```

这意味着测试用例之间没有共享同一个用户 JVM 的静态变量和内存状态，但同一次请求的用例共享临时目录，所有请求共享沙箱服务所在容器和服务级系统资源。

### 4.5 写入 stdin，并关闭输入流

```java
try (BufferedWriter writer = new BufferedWriter(
        new OutputStreamWriter(run.getOutputStream(), StandardCharsets.UTF_8))) {
    if (StrUtil.isNotBlank(input)) {
        writer.write(input);
    }
    writer.flush();
}
```

`run.getOutputStream()` 实际连接子进程的标准输入。try-with-resources 结束时会关闭它，子进程才能收到 EOF。当前实现只写入 `StrUtil.isNotBlank(input)` 的输入，因此纯空白输入会被丢弃；其他输入原样写入且不自动补换行。用户程序怎样解析输入，取决于测试用例文本和用户代码。

### 4.6 先读 stdout，再等待进程

```java
String output = readOutput(run.getInputStream());
boolean runFinished = run.waitFor(runTimeoutMs, TimeUnit.MILLISECONDS);
if (!runFinished) {
    run.destroyForcibly();
    return fail("运行超时");
}
```

这一顺序是当前实现最关键的问题。`InputStream.read()` 在没有数据且未到 EOF 时会阻塞。如果用户程序不输出也不退出，父进程会停在 `readOutput`，根本到不了后面的 5 秒 `waitFor`。

```text
父进程：readOutput(stdout) ──────────────等待 EOF──────────────┐
                                                              │
子进程：while (true) {} ───────────────不退出、不关闭 stdout───┘

结果：waitFor(5s) 尚未执行，5 秒配置无法约束这段等待
```

### 4.7 检查退出码与 stderr

```java
if (run.exitValue() != 0) {
    String error = readOutput(run.getErrorStream());
    return fail("运行错误（退出码 " + run.exitValue() + "）：" + ...);
}
```

stderr 只在进程结束且退出码非零后读取。如果子进程在退出前持续写 stderr，管道缓冲区可能被填满，子进程因无法继续写入而阻塞；父进程此时仍在读 stdout 并等待 EOF，双方可能死锁。

```text
子进程：持续写 stderr -> stderr 管道填满 -> 等待父进程读取
父进程：同步读 stdout  -> 等待子进程退出 -> 尚未读取 stderr
```

Java 8 官方 `Process` 文档明确提醒：标准流缓冲区容量有限，父进程若未及时读写，子进程可能阻塞甚至死锁。当前实现需要并发消费 stdout/stderr，或显式合并、重定向这两条流，才能建立可靠的整体截止时间。

### 4.8 截断输出不等于限制输出资源

`readOutput` 最多保留 64 Ki 个 Java 字符：

```java
if (sb.length() > MAX_OUTPUT_LENGTH) {
    return sb.substring(0, MAX_OUTPUT_LENGTH);
}
```

它限制了当前方法保存在 `StringBuilder` 中并返回的文本长度，但没有形成完整的“输出超限”策略：

- 没有返回 Output Limit Exceeded；
- 达到上限后没有明确杀死并等待子进程退出；
- 没有限制 CPU、总运行时间、磁盘写入或其他文件描述符；
- 提前关闭管道后，子进程的具体行为仍依赖操作系统和 JVM。

因此准确说法是“采集结果最多保留 64 Ki 个字符”，不能说“用户程序的输出资源已被限制”。

### 4.9 归一化输出与耗时统计

成功用例执行：

```java
outputList.add(output.replace("\r\n", "\n").trim());
maxCostMs = Math.max(maxCostMs, cost);
```

- 只归一化实际输出，替换 Windows 换行并删除首尾空白；
- `trim()` 会改变输出语义，首尾空格本来可能是题目答案的一部分；
- `time` 取最慢单个用例的墙钟耗时，不是所有用例总和；
- 计时包含启动 JVM、写输入和读输出，不包含编译；
- `memory` 固定为 0，所以当前无法依据沙箱结果作出可信的 MLE 判断。

### 4.10 finally 清理临时目录

无论成功或失败，`finally` 都会调用 `cleanup(workDir)`，按路径深度逆序删除文件和目录。这体现了资源回收意图，但 `File.delete()` 的布尔返回值没有被检查；删除失败时可能残留文件，也不一定产生日志。

## 5. 失败语义：错误最终去了哪里

| 场景            | 沙箱侧当前行为                           | 返回或异常                           | Judge Service 当前后续                   |
| ------------- | --------------------------------- | ------------------------------- | ------------------------------------ |
| 缺少或错误的 `auth` | 抛 `SecurityException`             | HTTP 401，正文含 `status=401`       | 客户端不检查 HTTP 状态；即使反序列化成功，下游也没有 401 分支 |
| 请求对象为空        | 在方法 `try` 前触发异常                   | 全局处理为 HTTP 500                  | 可能得到字段不完整的响应或远程调用异常                  |
| 代码为空或过长       | 调用 `fail()`                       | `status=2`、空输出、`judgeInfo=null` | 仍进入判题策略，可能空指针                        |
| 编译错误          | 读取并截断 javac stderr                | 同上                              | 不能稳定形成 Compile Error verdict         |
| 编译超时          | 若能走到 `waitFor`，强杀编译进程             | 同上                              | 不能稳定形成 CE/TLE；读流阶段仍可能先阻塞             |
| 运行超时          | 若能走到 `waitFor`，强杀当前进程             | 同上                              | 不能稳定形成 TLE；未等待确认退出，也未处理进程树           |
| 非零退出          | 读取并截断 stderr                      | 同上                              | 不能稳定形成 Runtime Error verdict         |
| IO 或未知异常      | 本方法捕获并调用 `fail()`                 | `status=2`                      | 仍可能因空 `judgeInfo` 进入任务 FAILED        |
| 正常执行          | 返回输出和 `JudgeInfo(time, memory=0)` | `status=1`                      | 判题策略比较输出、时间和内存，生成 verdict            |
| HTTP 连接卡住     | 客户端没有显式连接/读取超时                    | 调用可能长时间不返回                      | 提交可持续停留在 RUNNING，需靠外部恢复机制处理          |

`destroyForcibly()` 也不是完整的回收证明。Java 8 文档说明调用后进程可能不会立即终止，通常还需要再次等待和确认；当前代码既没有等待被杀进程退出，也没有可靠处理其后代进程。

## 6. 安全边界：用户代码拥有什么能力

### 6.1 先定义信任边界

攻击者控制的是 `code` 和输入内容。该代码由沙箱服务通过 `java` 启动，工作目录被设置为本次临时目录，但仍继承沙箱服务的环境变量和操作系统身份权限。

Compose 确实把沙箱服务放进了独立容器，但所有提交仍在 **同一个长期运行的沙箱服务容器** 内执行，并不是每次提交创建一个独立隔离单元。当前 Dockerfile 没有声明非 root 用户；Compose 也没有看到提交级 CPU、内存、PID、只读文件系统、禁网、capability 收缩或定制 seccomp 策略。

### 6.2 当前已经存在的控制

| 控制                      | 能解决什么                     | 不能证明什么                  |
| ----------------------- | ------------------------- | ----------------------- |
| `auth` 共享密钥             | 限制普通外部调用者直接请求接口           | 不能限制获准执行的代码能力           |
| Compose 只 `expose` 8090 | 默认不把端口发布到宿主机              | 不能阻止同一内部网络中的访问          |
| 代码长度检查                  | 限制提交代码字符串大小               | 不能限制运行时资源消耗             |
| 输出采集上限                  | 限制返回字符串占用                 | 不能限制进程持续输出和其他资源         |
| 临时目录                    | 把本次源码和 class 放在独立路径       | 不是文件系统沙箱，代码仍可访问路径之外的文件  |
| 编译/运行超时参数               | 为正常到达 `waitFor` 的路径提供截止时间 | 不能覆盖此前的阻塞读流，也不能证明进程树已回收 |
| 服务容器                    | 相对宿主机增加一层边界               | 不是提交之间的隔离，也不是默认安全配置证明   |

### 6.3 用威胁场景检查边界

| 用户程序                   | 当前可能发生什么                  | 缺少的控制或证据                        |
| ---------------------- | ------------------------- | ------------------------------- |
| `while (true) {}` 且不输出 | 父进程可能阻塞在 stdout 读取，绕过后置超时 | 从启动时刻生效的整体 deadline；独立 watchdog |
| 无限写 stdout             | 采集到 64 Ki 字符后停止读取，进程结果不确定 | 输出超限 verdict；杀进程并确认退出           |
| 无限写 stderr             | stderr 管道可能填满，与父进程形成死锁    | 并发消费 stdout/stderr 或安全重定向       |
| 持续申请内存                 | 可能耗尽容器或影响其他提交             | 提交级内存/cgroup 限制与真实峰值采集          |
| 持续创建线程或进程              | 可能消耗 PID，并遗留后代进程          | PID 限制；进程组或提交级容器回收              |
| 读取文件和环境变量              | 可能读取应用文件、运行环境及沙箱密钥        | 最小权限用户、环境清洗、只读根文件系统、挂载白名单       |
| 发起网络请求                 | 可能访问同一 Docker 网络中的其他服务    | 默认禁网或严格出站白名单                    |
| 修改临时目录外文件              | 与沙箱服务权限一致时可能成功            | 每次执行的独立文件系统和只写临时空间              |

还有一个容易忽略的泄露面：`CodeSandboxProxy` 会记录完整 `ExecuteCodeRequest` 和 `ExecuteCodeResponse`。这会把用户代码、测试输入和输出写入日志。它方便调试，但正式环境需要脱敏、摘要和大小限制。

基于当前证据，准确定位是：**具备基础调用控制和编译运行能力的 Java 进程执行器**。要称为安全代码沙箱，需要实现并验证提交级资源、网络、文件系统、身份和进程生命周期隔离。

## 7. 二开顺序：先闭合语义，再加强隔离

以下是设计方向，不代表仓库已经实现。

### P0：统一执行结果契约

先区分三类结果：

1. 用户代码结果：CE、RE、TLE、MLE、OLE；
2. 沙箱系统错误：JDK 不可用、临时目录失败、执行器异常；
3. 远程调用错误：鉴权失败、连接失败、HTTP 超时、协议不兼容。

Judge Service 必须先检查沙箱状态，再决定进入判题策略、形成用户 verdict，还是把任务标记为可重试或系统失败。

### P0：重构进程执行器

- 从进程启动时就计算统一 deadline；
- 并发消费 stdout 和 stderr，并对两者分别设置有界缓冲；
- 输出超限时返回明确结果并终止执行；
- 超时后强杀、等待并确认进程退出；
- 在无法可靠管理进程树的 Java 8 环境中，优先考虑由外部执行单元承接整次提交生命周期；
- 清理时检查每个删除结果，并记录可定位的失败信息。

### P1：每次执行使用独立隔离单元

最小目标包括：非 root 用户、只读根文件系统、独立临时目录、禁网、CPU/内存/PID 限制、能力集收缩和执行完成后整体销毁。采用容器、微虚拟机或专用执行节点，需要结合启动开销、吞吐量和隔离强度实测选择。

### P1：建立可验证证据

| 层次       | 应验证什么                              |
| -------- | ---------------------------------- |
| 单元测试     | 类名解析、输出归一化、结果映射、边界参数               |
| JDK 集成测试 | 正常输出、编译失败、非零退出、超时、stdout/stderr 超限 |
| 隔离实验     | 内存、PID、文件、环境变量、网络和子进程边界            |
| 故障实验     | 沙箱宕机、HTTP 超时、清理失败、Judge Service 重启 |
| 压力测试     | 并发提交下的队列等待、启动开销、资源争用和尾延迟           |

只有对应层次的测试通过后，才能把设计目标升级为实现或运行证据。

### 8.2 闭卷测试

1. 画出 Judge Service 到沙箱服务的调用图，并标出 HTTP 边界；

5. 分别推演编译错误、运行异常、鉴权失败和 HTTP 卡住所经过的返回路径；
6. 对无限循环、无限 stdout、无限 stderr、持续申请内存、读取环境变量和创建子进程六种代码，填写“当前行为—缺口—验证方法”；
7. 给出二开顺序，并说明为什么结果契约和进程生命周期应先于多语言扩展。

### 8.3 通过标准

- 不看源码也能按顺序说出“临时目录 → javac → 每用例新 JVM → stdin → stdout → waitFor → exit code/stderr → 清理”；
- 能准确指出 timeout 位于阻塞读流之后，而不是笼统说“超时有 bug”；
- 能区分接口鉴权、容器边界和提交级隔离；
- 不把 `status=1`、任务 `SUCCEED` 和 `Accepted` 当成同一个状态；
- 不把静态审计结论说成已完成修复或生产验证；
- 能为每个改造目标给出相应测试，而不是只列技术名词。

> 安全场景应先写成测试设计；在没有提交级隔离的环境中，不要直接运行内存耗尽、进程炸弹、文件探测或内网访问代码。
