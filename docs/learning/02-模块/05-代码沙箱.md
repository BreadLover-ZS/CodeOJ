# 02 模块 · 代码沙箱

## Part A：判题服务侧的沙箱抽象

### A1. 接口与工厂

[JudgeService 侧] 判题服务不直接依赖某个沙箱实现，而是通过接口 + 工厂切换：

- [CodeSandbox.java](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandbox.java)：接口，就一个方法 `ExecuteCodeResponse executeCode(ExecuteCodeRequest)`。
- [CodeSandboxFactory.java](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxFactory.java)：`newInstance(type)` 按 `codesandbox.type`（默认 `remote`）返回：
  - `example`：本地假沙箱（不真跑代码）
  - `remote`：远程 HTTP 沙箱；配置中的默认选项，不等于已具备生产级隔离
  - `thirdParty`：第三方沙箱桩
- [CodeSandboxProxy.java](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxProxy.java)：包装类（静态代理），调用前打印完整请求、调用后打印完整响应（便于排查问题，注意也会把用户代码/用例打进日志）。

> 判题服务 `application.yml` 默认 `CODESANDBOX_TYPE=remote`；`JudgeServiceImpl` 的注解默认值是 `example`，只有缺少该配置时才会用到。远程地址在 Compose 环境里指向 `codeoj-codesandbox:8090`，本机默认则是 localhost。

### A2. 远程调用 [RemoteCodeSandbox.java](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/impl/RemoteCodeSandbox.java)

```java
@Value("${codesandbox.remote.url:http://localhost:8090/executeCode}")
private String url;
@Value("${codesandbox.remote.auth-secret:secretKey}")
private String authSecret;

String json = JSONUtil.toJsonStr(executeCodeRequest);
String responseStr = HttpUtil.createPost(url)
        .header(AUTH_REQUEST_HEADER, authSecret)   // 请求头 auth = 密钥
        .body(json).execute().body();
return JSONUtil.toBean(responseStr, ExecuteCodeResponse.class);
```

地址和密钥通过配置注入；Compose 把 `CODESANDBOX_URL` / `CODESANDBOX_SECRET` 映射成判题服务实际读取的 `CODESANDBOX_REMOTE_URL` / `CODESANDBOX_REMOTE_AUTH_SECRET`。该 HTTP 调用代码中没有显式设置连接/读取超时，不能把沙箱内部的运行超时当作远程调用超时。

## Part B：沙箱服务端（codesandbox，:8090）

### B1. 入口 [ExecuteCodeController.java](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/controller/ExecuteCodeController.java)

```java
@PostMapping("/executeCode")
public ExecuteCodeResponse executeCode(@RequestBody ExecuteCodeRequest req,
                                       @RequestHeader(value = "auth", required = false) String auth) {
    codeSandboxService.checkAuth(auth);          // ① 鉴权
    return codeSandboxService.executeCode(req);  // ② 执行
}
```

控制器先校验 `auth` 头再执行代码。这控制“谁能调用接口”，不限制已经被允许执行的用户代码访问哪些文件、进程或网络。

### B2. 核心实现 [JavaNativeCodeSandbox.java](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaNativeCodeSandbox.java)

逐步骤（对照源码读）：

1. **入参校验**：代码非空、长度 ≤ `MAX_CODE_LENGTH = 256KiB`。
2. **提取类名**：正则 `public\s+class\s+(\w+)` 取主类名，没有则默认 `Main`。
3. **写临时目录**：`Files.createTempDirectory("codeoj-sandbox-")`，写入 `{ClassName}.java`。
4. **编译**：`javac -encoding UTF-8`，编译超时 `compile-timeout-ms`（默认 15s），失败返回"编译错误……"（截断 500 字），超时 `destroyForcibly()` 返回"编译超时"。
5. **逐用例运行**：每个用例单独启动 `java` 子进程，用 stdin 喂入输入，再读取 stdout；`run-timeout-ms` 默认 5s。但代码在 `waitFor(timeout)` **之前**同步读 stdout：不退出且不输出的程序可能让读操作一直等待，执行不到超时判断。
6. **资源统计**：记录最大耗时 `maxCostMs`；内存固定 0（当前不采集真实内存）。
7. **归一化输出**：`replace("\r\n","\n")` + `trim()`，避免判等受平台换行/首尾空白干扰。
8. **清理**：`finally` 里递归删除临时目录。

关键防护常量（面试常问）：

```java
MAX_OUTPUT_LENGTH = 64 * 1024;   // 返回文本最多保留约 64K 字符
MAX_CODE_LENGTH   = 256 * 1024;  // 使用 String.length() 判断字符数
runTimeoutMs      = 5000;        // 单用例运行超时
compileTimeoutMs  = 15000;       // 编译超时
```

### B3. 返回结构

成功返回 `status=1`、`outputList` 和 `judgeInfo(time, memory=0)`；`fail(...)` 返回 `status=2` 与错误消息，`judgeInfo` 为空。当前判题服务未先处理 `status=2`，因此不能说它会稳定转换成 CE、RE 或 TLE。

## Part C：模块边界与返回契约

判题服务侧只负责选实现、包装代理、组装请求和发起 HTTP 调用；代码沙箱服务负责检查调用密钥、创建临时目录、启动 `javac/java` 并返回 `ExecuteCodeResponse`。判题策略位于判题服务，不在沙箱服务内部。跨服务的完整顺序及异常时间线见[链路篇](../03-链路.md)。

## Part D：安全边界（务必清楚"防住了什么、没防住什么"）

**当前实现有这些控制**：

- 接口鉴权（auth 头）
- 代码长度检查与返回文本截断；截断不等于限制子进程总输出量
- 编译/运行的超时参数；同步读输出可能阻塞在超时判断之前
- 独立临时目录 + 结束后清理

**尚未防住（进程级沙箱本质）**：

- 用户代码与沙箱进程共享同一容器权限/网络/文件系统——没有每次提交的容器隔离、CPU/内存限制、禁网、只读根文件系统、非 root 运行。
- stdout/stderr 读取发生在 waitFor 之前，超时控制可能不精确；`destroyForcibly` 未等待子进程及其后代退出。
- 不采集真实内存，MLE 判定缺乏数据基础。

> 结论：当前是演示级 Java 进程执行器。即使服务本身运行在容器里，也不等于对每次用户提交做了独立隔离；真正的资源、网络和文件系统约束需要实现并验证。

## 关键问题

1. `remote` 从哪项配置选中？远程地址、`auth` 密钥分别由谁提供和校验？
2. 不输出且不结束的 Java 程序，为什么可能绕过当前 `waitFor(timeout)`？
3. `MAX_OUTPUT_LENGTH` 截断的是哪部分数据？它能否约束子进程持续输出？
4. `memory=0` 和 `judgeInfo=null` 分别让哪些判题结论无法成立？
