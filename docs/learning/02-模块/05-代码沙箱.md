# 代码沙箱：用户程序如何运行、受限并被回收

判题服务知道标准答案，但不能把用户代码当作自己的业务代码直接执行。沙箱把“编译运行不可信程序”独立出来，控制资源和文件边界，并返回可校验的运行结果。

本篇先讲一次正常执行，再讲容器和回收。读完应能回答：编译了什么、输入从哪里进入、输出怎样返回、超时谁负责、管理器退出后谁收尾。

## 1. 先把两层配置分清

| 配置 | 所在一端 | 表示什么 |
| --- | --- | --- |
| `codesandbox.type=remote` | 判题服务 | 使用 HTTP 客户端调用沙箱 |
| `codesandbox.mode=isolated` | 沙箱服务 | 在 Linux 隔离容器中运行程序，默认模式 |
| `codesandbox.mode=native` | 沙箱服务 | 在宿主进程环境中运行，仅用于显式可信样例 |

remote 与 isolated 可以同时成立：判题服务远程调用沙箱，沙箱内部使用容器。不是三个相互排斥的执行类型。

[CodeSandboxFactory](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxFactory.java) 当前仅选择 remote；沙箱服务再由条件 Bean 选择本地执行器。

## 2. 请求里为什么有输入，却没有标准答案

阅读 [ExecuteCodeRequest](../../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/codesandbox/ExecuteCodeRequest.java) 和 [ExecuteCodeResponse](../../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/codesandbox/ExecuteCodeResponse.java)。

| 请求内容 | 用途 |
| --- | --- |
| code、language | 要编译的程序 |
| inputList | 每个用例通过 stdin 输入的数据 |
| runTimeLimitMs、memoryLimitKiB | 每用例时间与内存限制 |
| executionToken | 本次尝试的执行身份 |
| executionDeadlineEpochMs | 绝对执行截止时间 |

响应包含 outcome、status、outputList、judgeInfo 与诊断字段。沙箱把实际输出交给判题服务，后者用固定规格中的期望输出比较。把标准答案留在判题端，可以让执行层专注编译、运行与资源结果。

例如求和程序收到 `1 2`，stdout 为 `3`。这只能说明本用例运行得到 `3`；全部用例正确、资源合格、协议有效后，判题策略才能生成 AC。

## 3. 从 HTTP 调用跟到执行器

阅读顺序：

1. [RemoteCodeSandbox.executeCode](../../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/impl/RemoteCodeSandbox.java)：有界 HTTP 请求。
2. [ExecuteCodeController.executeCode](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/controller/ExecuteCodeController.java)：检查 `auth` 请求头，再调用执行服务。
3. [JavaIsolatedCodeSandbox.executeCode/executeOnce](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java)：校验请求、经 registry 管理一次执行。
4. [DurableExecutionRegistry.execute/run](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java)：执行身份、容量、持久登记和清理。
5. [DockerIsolationEngine.create/start/removeExecution](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DockerIsolationEngine.java)：真正创建和删除容器、卷。
6. [supervisor.py](../../../codeoj-backend/codeoj-backend-codesandbox/isolation/supervisor.py)：容器内执行用户程序、期限和可信收据。

远程客户端同时限制连接、读取、总调用时间、响应大小及并发，不做透明的自动执行重试。HTTP 超时只表示调用方没有拿到可信结果，不直接映射为用户 TLE，也不能证明远程程序已经停止。

## 4. 一份 Java 代码怎样执行

### 4.1 创建前先登记与占位

`JavaIsolatedCodeSandbox.executeCode` 校验语言、源码大小、用例数量、输入预算和资源参数，然后进入 registry。registry 进一步检查 token 与绝对期限，计算内容摘要，申请可用 slot，持久写入执行登记。

slot 是物理并发名额。例如容量为 2 时，第三个请求不能随意再启动一组容器。登记在创建物理对象前完成，让管理器崩溃后仍能知道需要回收哪个执行。

### 4.2 编译一次

`executeOnce` 建立 token 专属工作目录，把源代码写成 `Submission.java`。独立编译容器执行受信的 `NativeCompiler`，产出 class 文件和入口类收据。不能只靠 javac 的 stdout 判断是否编译成功，还要校验受信收据及随机 nonce。

如果确认是用户语法错误，返回 CE；编译阶段的预算或平台异常不能都冒充 CE。

### 4.3 每个用例创建新的运行容器

编译产物以只读方式提供给运行容器，每个输入用例创建新容器，运行受信的 `IsolatedLauncher`，将输入经 stdin 交给用户入口，收集 stdout/stderr 与运行指标。

```text
token T1
 ├─ 编译容器 → class 产物
 ├─ case-0 新容器：输入 1 2 → 输出 3
 ├─ case-1 新容器：输入 5 8 → 输出 13
 └─ 清理属于 T1 的容器、卷与工作文件
```

代码编译一次，但可写空间不在用例间复用。这样前一个用例写入的文件和残留进程不会成为下一个用例的初始状态。

### 4.4 汇总结果并清理

执行器根据受信结果区分 MLE、TLE、OUTPUT_LIMIT、RE、EXECUTED 和平台异常。当前汇总的 time、memory 使用用例观测的最大值；时间包含 JVM 启动，内存是用例 cgroup 的观测值，包含 JVM、监督器和后代，不等于 Java 堆大小。

执行工作返回后，registry 清理物理对象。清理成功保存 COMPLETED 并归还 slot；删除失败保存 REAP_PENDING，保留占用，不能假装资源已释放。

## 5. 限制具体落在哪一层

| 风险 | 当前机制 | 从哪里验证 |
| --- | --- | --- |
| 用户以高权限运行 | 用户进程降为 UID/GID 10000，清空 capabilities | supervisor 的 `unprivileged` 与 Docker 参数 |
| 访问外网 | 用户容器 `--network none` | `DockerIsolationEngine.create` |
| 写宿主业务文件 | 不挂业务目录、凭据或 Docker socket；根文件系统与运行产物只读 | create 的 mount 与 read-only 参数 |
| 内存、CPU、进程过多 | cgroup 限制 memory、cpus、pids | Docker 参数与内核观测 |
| 临时文件过大 | 有界 tmpfs、文件限制、独立可写区域 | create 的 tmpfs/ulimit |
| stdout/stderr 持续输出 | 有界读取与输出预算 | `BoundedProcessRunner` 及执行结果处理 |
| 死循环或派生进程 | 阶段预算、总期限，监督器清理后代 | supervisor 与绝对 deadline |
| 假造“运行成功” | 用户输出与私有控制收据分离 | `trustedResult`、`/receipt/result.json` |

“在 Docker 里”本身不能完整回答安全问题；应指出限制参数、执行用户、可信控制面和清理机制。当前证据也不等于完成内核逃逸认证。

## 6. 为什么需要容器里的监督器

如果超时只由 Java HTTP 调用方控制，调用方退出后，用户死循环可能继续运行。supervisor 与用户进程同处隔离执行环境，但负责独立期限和结果收据。

它把执行时间限制为“阶段预算”和“绝对截止时间”二者中的更早者，降权启动用户程序，并在结束时清理 namespace 中的用户后代，包括重新派生、脱离原会话的进程。

因此数据库租约控制**结果能否生效**，监督器控制**用户代码何时停止**，registry 控制**物理对象何时清掉、名额何时归还**。三个职责需要配合。

## 7. 管理器退出以后怎样恢复

先打开 `DurableExecutionRegistry.Record`，认识 token、hash、state、deadline、slot、response，再阅读 execute、run、recover、reap。

| 情形 | 当前处理 |
| --- | --- |
| 同 token、同内容再请求 | 在有限保留窗口内等待或回放已有结果，不随意再运行 |
| 同 token、不同内容 | 内容冲突，拒绝 |
| 身份或期限无效 | 不创建新执行 |
| 管理器被杀 | 后继管理器按持久登记和文件锁恢复并回收 |
| 清理失败 | REAP_PENDING，slot 继续占用，后续重试清理 |
| 登记损坏 | 保守拒绝/保留，不据此释放可能仍被占用的资源 |

执行锁、slot 记录和 token 记录共同保护共享容量。JVM 内按文件共享锁通道，不能随意删除锁文件来“重置”运行中状态。

共享容量只覆盖同一 Docker daemon、同一持久本地目录。没有证据可以把它描述为任意多宿主机的全局容量管理。有限保留窗口过去后，不能宣称沙箱为任意旧 token 永久提供 exactly-once。

## 8. native 模式适合学什么

[JavaNativeCodeSandbox](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaNativeCodeSandbox.java) 和 [BoundedProcessRunner](../../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/BoundedProcessRunner.java) 可以帮助理解文件、编译、stdin、双流读取、等待退出和时间预算。

native 有有界 I/O、执行预算与资源观测，但没有 isolated 的 Linux 容器边界。只跑可信教学样例。理解进程调用后，应回到 isolated 阅读当前主实现，不能把 native 演示结果当作隔离验收。

isolated 依赖 Linux/cgroup v2、固定镜像、专用持久目录等条件。条件不足时拒绝启动，不自动降级为 native。具体操作见[隔离说明](../../contest/isolated-sandbox.md)。

## 9. 自测与核对

1. **为什么沙箱返回 EXECUTED 仍可能 WA？** 运行完成和答案正确分属执行层与判题策略。
2. **HTTP 超时后能否马上换 token 重试？** 不能在客户端透明重跑，旧执行可能仍存在；由数据库恢复状态机决定新的尝试。
3. **数据库拒绝 T1 结果后谁停 T1 进程？** 监督器执行期限，registry/engine 负责物理回收，数据库 token 不直接杀容器。
4. **结果已经返回，删除失败，可否归还 slot？** 不可，继续 REAP_PENDING，确认清理后才释放。
5. **两个管理器怎样共享 2 个名额？** 同 daemon、同持久目录与一致配置，文件锁加持久 slot；不是各建一个 Semaphore 就相加。
