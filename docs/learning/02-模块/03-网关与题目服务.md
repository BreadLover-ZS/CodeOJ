# 网关与题目服务：从题库 CRUD 到可靠受理

本篇把你熟悉的 Controller → Service → 数据库，与当前的可靠判题连接起来。读完应能解释：请求怎样到达服务、题目如何保存、受理事务写了什么，以及为什么执行状态由题目服务管理。

## 1. 请求是怎样路由的

打开 [Gateway application.yml](../../../codeoj-backend/codeoj-backend-gateway/src/main/resources/application.yml)。普通题目请求 `/api/question/**` 转发到题目服务。赛事 API 对外使用更短的路径，网关再改写给题目服务。

| 浏览器请求 | 网关处理后进入题目服务的路径 |
| --- | --- |
| `/api/question/question_submit/do` | 原路径，匹配 `QuestionController` |
| `/api/contests/{id}/submissions` | `/api/question/contests/{id}/submissions` |
| `/api/submissions/{id}` | `/api/question/submissions/{id}` |

题目服务的 context-path 是 `/api/question`，Controller 上的 `@RequestMapping` 再拼子路径。定位接口时要把两者结合，不能因为源码里没有 `/api/contests` 就判断前端路径错误。

`lb://codeoj-backend-question-service` 表示按服务名寻址。配置保留 Nacos，完整本机启动使用静态服务发现；这两种寻址来源不能混为同一次验证结果。

## 2. 先读熟悉的题目管理

阅读 [QuestionController](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/controller/QuestionController.java) 的 `addQuestion`、`getQuestionVOById`、`deleteQuestion`，再读 [QuestionServiceImpl.validQuestion/getQuestionVO](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/service/impl/QuestionServiceImpl.java)。

### 创建一题保存哪些内容

`addQuestion` 接收 DTO，把标题、题干等复制到 `Question`，把 tags、judgeCase、judgeConfig 序列化为 JSON 字符串，检查参数，读取登录用户并保存创建人和题目记录。

| 字段 | 例子 | 用途 |
| --- | --- | --- |
| `title/content` | 两数之和 / 题干 | 页面展示 |
| `judgeCase` | 输入 `1 2`，输出 `3` | 隐藏判题依据 |
| `judgeConfig` | 时间 ms、内存 KiB | 资源限制 |
| `submitNum/acceptedNum` | 提交次数 / 通过次数 | 题目统计 |
| `userId/isDelete` | 创建人 / 逻辑删除 | 权限与可见性 |

普通 `/get/vo` 返回展示用 VO，隐藏用例不在该 VO 中；完整 `/get` 会核验本人或管理员。删除也检查本人或管理员，再执行逻辑删除。不要凭“管理题目”这个页面名称就推断所有增删接口都有相同的角色注解，逐个读实际检查。

这一段属于常规分层业务，重点是认识判题数据来自哪里，以及为什么要做脱敏，不必逐个背重复分页代码。

## 3. 提交入口为什么分成两条路线

[QuestionSubmitServiceImpl.doQuestionSubmit](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/service/impl/QuestionSubmitServiceImpl.java) 首先检查 `reliableEnabled`。开启时进入可靠受理；关闭时走基础版 MQ 流程。

当前重点按下面顺序打开：

| 顺序 | 方法 | 输入 → 输出 | 本步要看懂的内容 |
| --- | --- | --- | --- |
| 1 | `QuestionController.doQuestionSubmit` | 请求与当前用户 → 提交 ID | header/body key 一致，202 受理 |
| 2 | [ReliableSubmissionService.accept](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ReliableSubmissionService.java) | 参数与 User → 同一个提交 ID | 限定 Java、长度/key 校验、事务外有限重试 |
| 3 | [SubmissionAcceptance.accept](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java) | 请求 → 持久受理结果 | 幂等回读、当前账号、读取题目规格 |
| 4 | `SubmissionAcceptance.freezeSpec/write` | 规格与代码 → 多张事实记录 | 固定判题依据、执行记录、Outbox |

旧类仍存在，不代表新版会调用它。理解基础版可读[历史图解](../../history/legacy-judge-walkthrough.md)，再返回此处，不要在两套状态中来回混读。

## 4. 幂等：响应丢失后为什么还是同一份提交

假设 U7 用 key K1 提交代码 A，数据库成功但响应丢失。重试 K1+A 应返回原 ID，而不是新增一次提交；K1+B 则应冲突，否则同一个身份可能指向两份程序。

当前有两层检查：

- `requestHash` 对请求内容生成摘要，`replay` 检查同 key 是否同内容。
- V001 的唯一索引 `UNIQUE(userId, requestKey)` 防止两个并发请求同时创建执行记录。

单独“先查不存在再插入”不够，因为并发都可能查不到。唯一键冲突会使原事务回滚；`ReliableSubmissionService` 在外层回读已存在记录，再比较 hash。同 key 不同用户属于不同请求范围。

普通练习 hash 包含类型 PRACTICE、questionId、language、code；比赛提交还包含比赛、快照和发布版本。不能只按代码文本相同就去重，用户可能本来要发起新的提交。

## 5. 固定规格：为什么受理后不能读取最新题目判旧代码

假设用户 10:00 提交，管理员 10:01 修改隐藏用例，worker 10:02 才执行。如果直接查最新 `question`，本次提交会在用户不知道的条件下换一套规则。

`freezeSpec` 把版本、TEXT_V1、时间/内存、用例组合成 payload，计算 SHA-256 并保存 `judge_spec`。执行记录只保存 `judgeSpecHash`，领取时按 hash 找回固定 payload，并校验完整性和支持的版本。

因此 hash 既用于引用内容，也用于一致性检查。它不能代替数据库访问权限，也不保证规则本身合理；规则校验仍由 `validateSpec` 执行。

比赛进一步在发布时固定标题、题干与规格引用，见[赛事篇](07-赛事与报名.md)。普通练习固定的是受理时规格，比赛固定的是发布快照，两者时点不同。

## 6. 一个受理事务为什么写这些表

阅读 [SubmissionAcceptance.write](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java) 和 [V001](../../../codeoj-backend/mysql-init/migrations/V001__reliable_judging.sql)。

```text
@Transactional accept
  ├─ 冻结或复用 judge_spec
  ├─ question_submit：保存用户代码
  ├─ submission_execution：保存 QUEUED、规格、派发身份与恢复预算
  ├─ reliable_outbox：保存 JUDGE_DISPATCH
  └─ 普通题目提交数更新
提交后：后台发布器才去调用 MQ
```

`write` 标注 MANDATORY，要求调用者已有事务；普通练习由 `accept` 提供，比赛由 `ContestTransactions.submit` 提供。同类内部调用不单独触发注解，但外层 accept 的事务已经覆盖内部写入。

这里“同事务”只包括数据库操作。MQ、Redis、Feign、沙箱网络请求不在这个受理事务中。如果远程调用放在事务里，会延长占锁时间，而且本地回滚无法撤销已发出的消息或已运行的代码。

### 哪些字段第一遍必须看

| 表 | 关键字段 | 读它时回答什么 |
| --- | --- | --- |
| `question_submit` | code、userId、questionId、judgeInfo、status | 用户交了什么、怎样展示结果 |
| `submission_execution` | executionStatus、judgeSpecHash、acceptedAt | 当前状态与判题依据是什么 |
| 同上 | dispatchGeneration/eventId | 哪一代派发仍有效 |
| 同上 | activeAttempt、executionToken、leaseUntil | 当前由谁执行、有效到何时 |
| 同上 | maxAttempts/maxDispatches/recoveryDeadlineAt | 自动恢复何时必须停止 |
| `judge_attempt` | attemptNo、token、state、deadlineAt | 每一次尝试发生了什么 |
| `reliable_outbox` / `publish_attempt` | event、publishState / confirmState | 想发什么、发送结果是否确定 |

受理刚结束时还没有 judge_attempt，创建时机是 `claim`。数据库兼容 status 不能替代新执行记录。

## 7. 题目服务为什么还负责领取、续租、完成

判题服务承担运行工作，题目服务保管执行状态与结果。打开 [QuestionFeignClient](../../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/service/QuestionFeignClient.java)，再定位 [QuestionInnerController](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/controller/inner/QuestionInnerController.java) 和 [ExecutionCommands](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)。

| 命令 | 本地事务中的变化 |
| --- | --- |
| `claim` | 锁执行记录，校验消息与预算，QUEUED → RUNNING，创建 token/attempt |
| `heartbeat` | 只为有效 owner 续租，不能超过尝试期限 |
| `complete` | 校验结果与 owner，保存 COMPLETED、兼容结果、结果事件 |
| `fail` | 保存平台错误，进入 RETRY_WAIT 或 NEEDS_ATTENTION |
| `recover` | 重新检查时间与预算，必要时创建新派发事件 |
| `manualRetry` | 校验管理员、状态版本、原因和有限预算后重派 |

领取通过 `ExecutionRepository.find(id, true)` 执行 `SELECT ... FOR UPDATE`；保存又带 `stateVersion` 条件。理解当前并发控制时，要把行锁与版本检查一起说清，不能只贴“CAS”标签。

旧的 `updateQuestionSubmitById` 内部接口会拒绝直接修改新版可靠提交，防止绕开执行命令。数据库持久状态是跨 worker 共享的依据，本地 Semaphore 只限制单个 worker 的并发。

## 8. 查询结果和脱敏怎样收尾

[SubmissionStatusController.get](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionStatusController.java) 检查本人或管理员，再通过 `getQuestionSubmitVO` 补充 executionStatus、acceptedAt、activeAttempt。旧提交没有 sidecar 记录时仍保留兼容语义。

提交列表还可能展示他人的提交元信息，代码字段按本人/管理员做脱敏。因此“返回了一个提交记录”和“返回了此人的源代码”也不是同一权限。

比赛受理由 [ContestTransactions.submit](../../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java) 增加资格、比赛状态、时间和快照检查，然后复用 `write`。赛事、报名、榜单虽然也在题目服务内，但有独立业务记录，继续读[赛事](07-赛事与报名.md)和[榜单](08-榜单与结算.md)。

## 9. 自测与核对

1. **同 key 两个并发请求如何保证只受理一次？** 先查只能优化常见重试；唯一约束兜底，冲突事务回滚后回读并核对内容。
2. **Outbox 插入失败，用户提交会留下吗？** 同事务回滚，不应留下只有代码、没有派发依据的新受理记录。
3. **受理后改题，worker 用什么？** 执行记录指向的固定 judge_spec，不重新读取最新用例。
4. **数据库改为 RUNNING 后旧消息又来，能否再执行？** `claim` 在锁内检查当前状态与派发身份，不能重复领取。
5. **为什么把事务方法拆为独立 Bean？** 外层重试重新进入代理事务，失败回滚后再重试，不在失败事务内继续执行。

通过标准：能画受理事务的数据图，指出唯一约束、固定规格和领取 SQL，并解释查询 VO。测试对照：[ReliableExecutionTest](../../../codeoj-backend/codeoj-backend-question-service/src/test/java/com/codeoj/codeojbackendquestionservice/submission/ReliableExecutionTest.java)。继续读[判题与 MQ](04-判题服务与消息队列.md)。
