# 运行与验证：把读懂的源码变成可观察的流程

本篇帮助你选择学习运行入口、找到配置，并用请求与记录核对理解。执行环境可能需要下载依赖、编译或启动临时服务，具体前提与参数始终以[完整本机启动](../../contest/local-startup.md)和[脚本索引](../../../scripts/README.md)为准。

阅读源码不要求立刻启动全部环境。可以先读本篇第 5 节的测试，再决定是否运行。

## 1. 先选择你想观察的范围

| 学习目的 | 仓库根目录入口 | 能观察什么 | 不能据此证明什么 |
| --- | --- | --- | --- |
| 理解 Java 编译/运行与判定 | `./scripts/demo-local-judge.sh` | 可信 native 的 AC/WA/CE/TLE/OUTPUT_LIMIT 样例 | 隔离安全、MQ 交付和真实 DB |
| 理解赛事业务收敛 | `./scripts/demo-local-contest.sh` | H2、可信 Java 与手动事件分发的报名/提交/结算 | 真实 Redis/MQ/HTTP 跨进程链 |
| 从页面走完整当前业务 | `./scripts/local-stack.sh serve` | 私有真实依赖、业务服务、前端、Linux 隔离判题；就绪后保持运行 | 生产部署、压测与长期稳定性 |
| 启动并自动验证后清理 | `./scripts/local-stack.sh verify` | 同类环境的启动 smoke 与退出清理 | 全部 JV 和全面故障矩阵 |
| 专门读/跑报名回归 | `./scripts/test-registration-local.sh` | 真实 Redis、H2 及组件回归 | 真实 MySQL/MQ 完整服务链 |

你想一边读源码一边点页面时选 serve。verify 退出就清理环境，不能拿它输出过的地址继续访问。不要把脚本名字中的 native、历史日志标签与当轮实际 mode 混用。

## 2. 当前完整本机环境是怎样组织的

```text
Mac：前端静态页面/代理 + gateway/user/question/judge/sandbox 管理器
   + 私有 MySQL/Redis/RabbitMQ
Linux 临时 VM：专用 Docker/cgroup v2，实际执行用户容器
```

实现从 [local-stack.sh](../../../scripts/local-stack.sh) 进入 [start-stack.py](../../../scripts/local/start-stack.py)，复用 [run-native-stack.py](../../../scripts/local/run-native-stack.py) 编排业务与依赖，通过 [private-isolation.py](../../../scripts/local/private-isolation.py) 管理隔离环境。

所需环境包括 Mac arm64、Python 3.11+、Java 8 JDK、Maven、Node/npm、编译工具和临时空间等。首次准备较重，先读启动文档。脚本使用专属临时实例、随机回环端口、静态服务发现，不依赖真实 Nacos；不应照抄仓库旧 Compose 的端口来推断当前地址。

serve 就绪后，从 `LOCAL_STACK_READY` 事件取得页面地址和私有 access.json 路径。演示账号与随机密码在该私有文件中，不在学习文档固定写死。Ctrl+C 进入所属环境清理。

## 3. 沿配置追一次调用

| 连接 | 核对的配置或文件 | 配错后常见现象 |
| --- | --- | --- |
| 页面 → Gateway | `OpenAPI.ts`、`VUE_APP_API_BASE_URL`、同源代理 | 请求错地址、跨域或拿不到 Cookie |
| Gateway → 业务服务 | Gateway routes、context-path、服务发现实例 | 404、无可用实例 |
| 业务服务 → 会话 | Spring Session、Redis 地址/编号、Cookie path | 同一浏览器跨服务识别失败 |
| Feign → 内部 API | 服务地址、`INNER_AUTH_SECRET` | 内部接口 403 或调用不可用 |
| 判题 → 沙箱 | `codesandbox.remote.url/auth-secret` | 远程鉴权或传输失败 |
| 沙箱 → 执行环境 | mode、Docker endpoint、镜像、state-directory | 隔离启动失败或容量/登记冲突 |
| 发布器/消费者 → MQ | 凭据、交换机/队列、confirm/return/ack | 发布未知、不可路由或无消费 |

这些是定位方向，不是错误发生时机械重试的清单。先判断请求停在哪一层，再查相应日志与状态。

## 4. 一次页面学习应该观察什么

完整环境就绪后，围绕一个提交 ID 做记录：

1. 登录后打开题目，确认详情不含隐藏测试答案。
2. 交一份可信求和程序，观察提交接口的 key、202 和 ID。
3. 查询该 ID，观察执行状态和 judgeInfo；任务很快时可能看不到中间状态，不能据此认定没有 QUEUED/RUNNING。
4. 再观察 WA、CE 等样例，说明它们为何仍可 COMPLETED。
5. 比赛中观察 PROCESSING/CONFIRMED、快照 ID/发布版本、结果与榜单更新。

不要为了“看到中间态”随意修改业务表或删除锁文件。并发、宕机和 Lua 部分写入场景优先读已有测试和专项脚本，完整故障复验另有专属入口。

如果查询数据库，只读追踪该提交的 question_submit、submission_execution、judge_attempt、reliable_outbox 与 publish_attempt；不要把代码、隐藏用例、密钥、Cookie 粘入公共日志。

## 6. 怎么介绍已经验证的程度

当前证据集中在[项目状态](../../status.md)，那里区分旧版本完整本机验收、后续报名修复回归与尚未覆盖的环境。不要把历史完整验收数字加到当前测试数字里，也不要把本轮文档链接检查说成后端重测。

真实 Nacos、目标环境部署、压测、长期稳定性和多宿主容量等，按状态页的未验收范围表达。没有当前测量就不提供 QPS 或响应时间结论。

## 7. 自测与核对

1. **想保持页面运行，使用哪个入口？** serve；verify 结束后临时服务已清理。
2. **某接口 403，先判断什么？** 用户业务权限、内部密钥还是沙箱 auth，三种检查不能混查。
3. **看到端口监听能证明业务可用吗？** 不能，还要真实登录、报名、提交、结果与榜单的请求证据。
4. **单元测试通过能否宣称真实隔离环境通过？** 不能，要看真实 Linux/cgroup/进程回收收据与对应版本。

通过标准：选对运行入口、能找出一条配置链、能从测试断言解释一个故障，并准确表达验证边界。下一步进入[面试篇](../04-面试.md)。
