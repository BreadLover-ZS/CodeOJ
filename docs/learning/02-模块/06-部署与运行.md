# 02 模块 · 部署与运行

> 阅读范围：[建表脚本](../../../codeoj-backend/mysql-init/create_table.sql)、[基础设施 Compose](../../../codeoj-backend/docker-compose.env.yml)、[业务服务 Compose](../../../codeoj-backend/docker-compose.service.yml) 和各服务 `application.yml`。具体复现步骤与前置条件以仓库 [README](../../../README.md) 为准。

部署篇回答三件事：数据落在哪、进程如何互通、启动前怎样发现配置不一致。它不是运行成功报告；本篇结论来自配置和代码阅读。

## 1. 数据表与判题数据

| 表 | 关键内容 | 对判题链的作用 |
| --- | --- | --- |
| `user` | 账号、密码哈希、角色 | 用户注册登录；新注册使用 BCrypt，历史固定盐 MD5 由登录逻辑兼容并尝试升级 |
| `question` | 题面、答案、`judgeCase`、`judgeConfig`、统计数 | `judgeCase` 与 `judgeConfig` 是文本中的 JSON，消费时再解析 |
| `question_submit` | 用户代码、语言、`status`、`judgeInfo`、用户/题目 ID | 持久化任务状态与结果，MQ 消息只携带其 ID |
| `post` 等 | 论坛相关数据 | 非本轮判题学习主线 |

`question_submit` 有 `idx_questionId_status` 和 `idx_user_question` 等索引。它**没有**当前设计中的 Outbox、执行租约或 worker 版本字段，不能从索引存在推断已有原子抢占与恢复。题目用例在判题时读取的是当前 `question` 数据；若要保证按提交时版本判题，需要额外快照/版本设计。

## 2. 两套 Compose 的职责

| 文件 | 服务 | 当前暴露情况 |
| --- | --- | --- |
| `docker-compose.env.yml` | MySQL、Redis、RabbitMQ、Nacos | 模板中将 3306、6379、5672、8848、9848、9849 映射到宿主机；Nacos 鉴权配置为关闭 |
| `docker-compose.service.yml` | Gateway、用户、题目、判题、沙箱 | Gateway 发布 8101；其余业务服务与沙箱只声明 `expose`，在 Compose 网络内互通 |

业务服务经 Nacos 注册/发现；Gateway 把公开 HTTP 请求按前缀路由到用户、题目和判题服务。判题服务经 Feign 调题目服务内部接口，经 HTTP 调沙箱。沙箱执行用户代码，即使它的 8090 端口没有发布到宿主机，也不等于每份提交有独立进程/容器资源隔离。

基础设施 Compose 的端口映射服务于本地开发调试；如果换到其他主机或部署环境，应逐项检查实际网络暴露、密钥、Nacos 鉴权与访问控制。不要把本地模板直接描述为生产安全配置。

## 3. 启动依赖与配置对照

常规复现顺序是：确定 Java/Maven、Docker 和前端工具链 → 启动基础设施 → 初始化数据库与 MQ 拓扑 → 构建并启动业务服务 → 启动前端 → 做登录、提交、结果查询的最小验证。具体命令及已知环境门槛见 README；`depends_on` 只描述容器启动依赖，不能证明 MySQL、Nacos、RabbitMQ 已经可用。

配置检查尤其要沿“Compose 环境变量 → application.yml 占位符 → Java 注入字段”逐层核对：

1. `INNER_AUTH_SECRET` 需要在 Gateway 和业务服务一致；Feign 发出的 `X-Inner-Secret` 应能被服务端过滤器验证。
2. `CODESANDBOX_URL`/`CODESANDBOX_SECRET` 在 Compose 中映射为判题服务的 `CODESANDBOX_REMOTE_URL`/`CODESANDBOX_REMOTE_AUTH_SECRET`；沙箱服务也读取 `CODESANDBOX_REMOTE_AUTH_SECRET`。
3. `codesandbox.type` 当前配置默认 `remote`；实际请求地址还取决于本机运行还是 Compose 网络。
4. RabbitMQ 拓扑由 `InitRabbitMqBean#init` 尝试声明，但它只设置 host，创建原生连接时未读 Compose 配置的 RabbitMQ 用户名/密码，异常仅记日志。使用非 guest 凭据时，应实测交换机、队列和绑定是否真的创建；不能只凭服务启动日志推断 MQ 可用。
5. `MYSQL_ROOT_PASSWORD`、`REDIS_PASSWORD`、`RABBITMQ_USERNAME/PASSWORD` 和 CORS 来源需要与实际环境一致；模板默认值仅用于本地复现。

## 4. 最小运行验证应看到什么

登录请求返回会话 Cookie；带 Cookie 的提交请求返回记录 ID；数据库出现 WAITING 记录；RabbitMQ 中可观察到对应路由/消费；判题记录最终变为 SUCCEED 或 FAILED；提交记录页展示状态和 `JudgeInfo`。其中每一步都要有真实环境证据。若只完成 Maven 构建或代码阅读，只能说构建/静态检查通过。

## 关键问题

1. 哪些数据在 MySQL，哪些状态只由 RabbitMQ 传递？消息丢失后数据库可能留下什么？
2. 两套 Compose 各发布了哪些宿主机端口？`expose` 与 `ports` 在这份配置中如何使用？
3. `InitRabbitMqBean` 在非 guest 凭据下为何可能声明失败？怎样验证实际拓扑？
4. 仅看到服务容器启动，能否证明完成了一次真实判题？还缺哪些观察点？
