# 运行与配置：先选模式，再启动

**阅读目标：** 读完应能选择运行入口，找到新链路的开关与迁移，并判断启动检查究竟验证了什么。

本篇只说明运行结构。具体前提、命令参数和清理规则以[完整本机启动](../../contest/local-startup.md)为准，实际验证结果查[项目状态](../../status.md)。

## 1. 三种入口不要混用

| 目的 | 入口 | 使用条件 |
| --- | --- | --- |
| 演示可信 Java 判题/赛事样例 | `scripts/demo-local-judge.sh`、`scripts/demo-local-contest.sh` | 显式 native；赛事样例使用 H2 和手动事件分发 |
| 启动完整本机业务并验证后清理 | `scripts/local-stack.sh verify` | 私有 MySQL/Redis/MQ、业务服务、前端及临时 Linux 隔离环境 |
| 保持前台演示 | `scripts/local-stack.sh serve` | 启动检查后保持运行，Ctrl+C 清理；地址与账号按就绪事件查找 |

完整启动使用随机回环端口和静态服务发现，不借用已有业务数据库。`verify` 退出后环境已清理，不能再使用其页面地址。

## 2. 开关与迁移

| 配置 | 控制内容 |
| --- | --- |
| `RELIABLE_JUDGE_ENABLED` | 可靠受理、Outbox、执行权威与可靠消费者 |
| `ASYNC_REGISTRATION_ENABLED` | 异步报名消息与恢复；单场还要切换报名模式 |
| `SCOREBOARD_ENABLED` | 成绩投影、缓存和最终结算 |
| 沙箱执行模式 | 默认 isolated；native 需显式指定 |

三个业务开关默认关闭；异步报名和榜单依赖可靠判题。迁移按 [V001—V005](../../../codeoj-backend/mysql-init/migrations) 顺序应用，分别补齐可靠判题、赛事、异步报名、榜单和报名序号约束。

旧判题队列先排空，再切换新链路；旧报名写入者先停止，旧账本经关闸核对后升级，不能让两种写入协议并行分配同一活动。操作细节见[交接](../../contest/handoff.md)。

## 3. 沿配置追一次调用

先读 [local-stack.sh](../../../scripts/local-stack.sh) 如何进入 [start-stack.py](../../../scripts/local/start-stack.py)，再看它加载的 [run-native-stack.py](../../../scripts/local/run-native-stack.py) 与 [private-isolation.py](../../../scripts/local/private-isolation.py)：前者编排业务和数据服务，后者管理临时 Linux 隔离环境。


1. 前端 API 地址与 Gateway 实际端口一致，或使用同源代理。
2. Feign 服务地址指向本轮业务实例；Gateway 与业务服务内部密钥一致。
3. 判题端沙箱 URL、鉴权值与沙箱端匹配。
4. 数据库迁移、Redis 数据库编号、MQ 凭据和拓扑与本轮环境一致。
5. isolated 模式具备 Linux/cgroup v2、固定镜像和专用持久目录；条件不足时拒绝启动，不自动降级为 native。

旧 Compose 文件可用于阅读服务划分，但不能视为当前 Mac 启动方式，也不能替代目标环境部署验证。

## 4. 启动成功要看什么

不只看端口和进程。至少验证：登录与共享会话、报名 PROCESSING → CONFIRMED、Java 提交与结果、榜单更新；隔离检查还要看运行模式、资源与清理收据。

启动 smoke、完整 JV、压测是不同范围。选择入口和查看输出文件见[脚本索引](../../../scripts/README.md)。

## 5. 自测

1. `verify` 正常退出后，为什么不能继续访问它打印的页面地址？想持续演示应选哪个命令？
2. 端口已监听，但 Redis 使用了错误的数据库编号，是否算业务启动成功？

通过标准：找到临时环境生命周期，选对 verify/serve，并用登录、报名、判题和榜单检查业务就绪。
