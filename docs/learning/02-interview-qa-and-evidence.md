# CodeOJ 高频面试问答与证据边界

先遮住答案口述，再用源码核对。回答结构统一为：**当前实现 → 存在的问题 → 我的改造方向 → 如何验证**。

## 1. 项目与架构

### 1. 请用 30 秒介绍项目

CodeOJ 是一个 Spring Cloud 微服务在线判题项目。用户提交代码后，Question Service 先保存提交记录，再通过 RabbitMQ 异步通知 Judge Service；Judge Service 远程调用 Java 代码沙箱执行测试用例，使用判题策略比对输出并回写结果。我正在基于现有项目做可靠性与安全方向的二次开发，当前完成了源码审计和改造设计，重点是结果契约、消息可靠性、幂等消费、任务恢复和沙箱边界。

### 2. 为什么不在提交接口里同步判题？

编译和执行用户代码耗时长且波动大，同步处理会长期占用 Web 线程，流量高时容易拖垮接口。RabbitMQ 把快速接收提交与慢速判题解耦，还能通过队列深度形成削峰缓冲。但异步化只改变执行方式，不自动带来消息不丢、幂等和故障恢复。

### 3. RabbitMQ 为什么只传 submissionId？

数据库是业务事实来源，消息只传 ID 可以减小消息体并让消费端按最新状态做幂等判断。问题是消费端会重新读取题目和用例；如果题目被修改，旧提交可能按新用例判题。需要题目版本、不可变用例快照或提交时绑定版本来冻结语义。

## 2. 消息可靠性

### 4. 数据库成功、MQ 发送失败怎么办？

当前代码先 `save` 再 `convertAndSend`，二者不原子，进程崩溃会留下永久 `WAITING`。我的方向是 Transactional Outbox：提交记录和发布意图写入同一数据库事务，后台发布器重试发送，并用 Confirm/Return 更新发布证据。Outbox 可能重复发布，因此消费端仍要幂等。

### 5. Confirm、Return、Consumer ACK 有什么区别？

Confirm 说明 Broker 是否接收发布，Return 用于发现消息无法路由，Consumer ACK 说明消费端已处理本次投递、Broker 可以删除消息。它们处在不同链路，彼此不能替代，也不能替代数据库业务状态。

### 6. 手动 ACK 为什么仍然会丢消息？

手动 ACK 只让应用决定何时确认。当前异常分支使用 `basicNack(requeue=false)`，而项目没有 DLQ/重放闭环，失败投递可能直接丢弃；生产端也没有完整的发布确认和补偿。可靠性需要发布、路由、消费、业务状态和失败通道共同闭环。

### 7. RabbitMQ 会重复投递吗？如何幂等？

消费者完成业务写回但 ACK 前宕机，Broker 会重投。当前 `WAITING` 先查后改存在竞态，两个消费者可能同时执行。应使用数据库条件更新抢占执行权，终态消息直接按幂等成功处理；关键写回还要带 worker/version 条件，避免旧结果覆盖。

## 3. 状态机与恢复

### 8. 为什么 CAS 比分布式锁更适合这里？

任务状态本来就在数据库中，`update ... where status=WAITING` 可以同时完成状态校验和所有权竞争，影响行数就是抢占结果。分布式锁会额外引入锁过期、续租和数据库提交不一致问题。只有跨多种资源且无法用状态约束表达时，才进一步考虑锁。

### 9. 有 CAS 为什么还需要租约？

CAS 只保证同一时刻一个 worker 从 WAITING 进入 RUNNING。如果 worker 随后宕机，记录会永久 RUNNING。租约让恢复任务识别过期执行，重新调度；结果写回还要校验 workerId/version，避免原 worker 恢复后覆盖新结果。

### 10. SUCCEED 是否代表代码 Accepted？

不是。`question_submit.status` 表示任务生命周期，SUCCEED 应表示判题流程正常完成；Accepted、Wrong Answer、Compile Error 等属于 `judgeInfo.message`。沙箱的 `ExecuteCodeResponse.status` 又是第三层调用状态，三者不能混用。

## 4. 判题与沙箱

### 11. 当前 CE、RE、TLE 为什么可能变成 FAILED？

沙箱失败时返回 `status=2` 和空 `judgeInfo`，判题服务没有先分支处理，就把它交给策略读取内存和时间，可能触发空指针。异常最后被消费者捕获并写任务 FAILED。因此第一项二开应先冻结结果契约，为用户错误和系统错误建立明确映射。

### 12. 当前 TLE 和 MLE 为什么不可信？

MLE 不可信是因为沙箱固定返回 `memory=0L`。TLE 一方面在策略中用“耗时减 10 秒”判断，另一方面沙箱先同步读 stdout、后执行带超时 `waitFor`，持续输出可能使读流先阻塞。必须先修复执行与采集机制，再用恶意样例验证。

### 13. 为什么当前沙箱不能称为生产级？

共享密钥只控制谁能调用接口，不限制用户代码能做什么。当前代码作为宿主机子进程执行，没有提交级 CPU、内存、PID、网络和文件系统隔离，也缺少完整的进程树回收。准确说法是“本地/内网演示级进程执行器”，容器或更强沙箱隔离需要另做实现和攻击样例验证。

### 14. 项目是否支持 Java、C++、Go？

请求枚举允许三种语言，但当前沙箱始终用 `javac/java`，所以只能确认 Java 主链。除非为不同语言实现编译运行器并完成 E2E 测试，否则不能说三种语言均已支持。

## 5. 性能与验证

### 15. 提交接口 QPS 为什么不等于判题吞吐？

提交接口主要执行鉴权、短数据库写入和入队；真实判题包含编译、启动进程、多个测试用例和资源隔离，成本高得多。只压提交 API 可能得到很高 QPS，却只是把压力转成队列积压。报告必须分别给出提交吞吐、队列等待和每秒完成判题数。

### 16. 你准备怎样验证可靠性改造？

至少覆盖：数据库事务回滚、发布前杀进程、Broker NACK、错误 routing key、同一 ID 并发投递、结果写回后 ACK 前宕机、RUNNING 后宕机、连续依赖失败进入 DLQ。单元测试只能证明局部分支，中间件语义要用真实 RabbitMQ/MySQL 集成或故障注入验证。

## 6. 个人工作与证据边界

### 17. 到目前为止你具体做了什么？

准确回答：

> 我先对现有异步判题链做了源码审计，定位了结果契约、DB 与 MQ 非原子、消费抢占竞态、RUNNING 无恢复以及沙箱隔离不足等问题，并形成了按结果契约、CAS、租约恢复、Outbox/DLQ、沙箱安全推进的二开方案。目前这些属于静态审计和设计，后续会以代码、自动化测试、故障注入和压测逐项形成证据。

如果后续只完成其中一部分，就只把已实现且已验证的部分改成完成时。

### 18. 为什么选择这条二开主线？

在线判题的核心不只是 CRUD，而是异步任务在重复投递、进程崩溃和不可信代码执行下仍能得到明确、可恢复的结果。这条主线能同时体现 Spring/RabbitMQ/数据库并发控制、状态机、故障恢复和安全意识，也比重复做普通管理接口更有区分度。
