# 链路五：从一份判题结果到最终比赛榜单

前面的链路已完成合法比赛提交，得到持久判定。本链继续追结果事件如何成为成绩，用户怎样查榜，以及比赛到时后为什么还要等待、核对和重建。

## 全局位置：判题完成以后还有一段业务

```text
题目服务 complete：结果与 JUDGE_RESULT 同事务
  → 结果发布器 → MQ → ScoreboardConsumer
  → 校验原事实 → 同事务更新投影与业务回执
  → 查询 DB 元数据、Redis 页缓存 → 显示排名
比赛到结束时间 → FINALIZING
  → 等待判题/报名收敛 → 关闸对账 → 从事实重建并核对 → FINISHED
```

实时投影与最终结算不是一次动作。比赛需要可靠判题和资格事实，也要允许合法提交的结果迟到。Redis 缓存页面 entries，主体排名与版本在数据库，不能按常见教程直接介绍成 ZSet 排名。

| 数据层 | 这里保存什么 |
| --- | --- |
| 提交/执行/资格/快照事实 | 哪位选手何时提交哪道题，规则和判定是否有效 |
| contest_score_problem | 每用户每题最早 AC 的受理时间 |
| contest_score_user | 解题数与达到该成绩的时间 |
| scoreboard_result_receipt | 已持久处理的结果事件 |
| contest_scoreboard_state / contest_scoreboard_version | 当前启用版本、修订/缓存代次、最终版本与摘要 |
| Redis entries | 特定版本与分页的查询缓存 |

表结构见 [V004](../../codeoj-backend/mysql-init/migrations/V004__contest_scoreboard.sql)。第一遍假设原事实合法，结果正常投影，再完成一次合法结算。

## 第一遍：正常计分、查榜与结算

### 1. 先手算 FIRST_AC_V1

每用户每题取 AC 提交中最早的 acceptedAt。解题数为有 AC 的不同题数，achievedAt 为这些首次 AC 时间的最大值。它表示“何时达到目前解题数”，不是所有时间求和。

先按解题数多者优先，同数按 achievedAt 早者优先；相同并列。名次为严格领先人数加 1，userId 只稳定显示顺序。

| 选手 | A 最早 AC 受理时间 | B 最早 AC 受理时间 | 解题数 / achievedAt | 初始名次 |
| --- | --- | --- | --- | --- |
| U1 | 第 10 分钟 | 第 20 分钟 | 2 / 第 20 分钟 | 1 |
| U2 | 第 15 分钟 | 第 20 分钟 | 2 / 第 20 分钟 | 1 |
| U3 | 第 8 分钟 | 无 | 1 / 第 8 分钟 | 3 |
| U4 | 无 | 无 | 0 / null | 4 |

U4 已确认报名，因此即使没有提交也以零分入榜。这里的时间来自提交受理，不是判题完成或 MQ 消费时间。

### 2. 完成判题怎样产生结果事件

源码：[ExecutionCommands.complete](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)。

**阅读范围：** 只追 JUDGE_RESULT 的 payload、resultVersion、Outbox 插入与结果写入的事务关系；执行权检查已在链路二读过。

判题完成时，结果事实与待投影事件同事务落库。消息主要引用 submissionId/resultVersion，消费者仍须核对数据库原事实，不能相信一个外部请求自称“此人 AC”就加分。

源码：[ScoreboardMessaging.validate](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardMessaging.java)。

**阅读范围：** 看开关依赖、结果拓扑和内部 Relay.tick 中的 recoverPublications/due/claim/publish，不必重复深读链路二的通用传输实现。

结果队列与判题派发队列不同，JUDGE_RESULT 不交给判题 worker 再执行。这个交接把判题与成绩投影在时间上分开，允许暂时延迟。

### 3. Consumer 怎样校验消息与数据库事实

源码：[ScoreboardConsumer.receive](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardConsumer.java)。

**阅读范围：** 读解析、大小/valid 检查、messageId、project 调用与 ACK/拒绝；第一遍先沿合法事件。

源码：[ScoreboardTransactions.project](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

**阅读范围：** 从 eventId/原 Outbox 查询读到执行状态检查、比赛锁、回执判断，再跟 facts/verdict；先走有 contestId 且未处理分支。

消息必须匹配原事件和完成记录。facts/verdict 核验资格、快照、发布版本、受理窗口、固定规格、结果摘要和判定。普通练习没有比赛上下文，只登记处理回执，不改任意比赛成绩。

**当前进度：** MQ 消费只提供处理机会；核验成功的数据库事实才是成绩依据。接下来是本地事务内的投影计算。

### 4. 按每题最早 AC 更新用户成绩

继续在 project 内读 zeros、用户成绩行锁、contest_score_problem 与聚合更新。

**阅读范围：** 找没有该题记录时的插入、acceptedAt 更早时的更新，再看 solvedCount 的 COUNT、achievedAt 的 MAX 和 bump。

首次 AC 新增该题，更早 AC 修正时间，同题更晚 AC 不增加题数。zeros 给确认资格补零分行。非 AC 不加题，仍可完成该结果事件的持久处理。

当前实现有意用比赛锁串行化这一版投影、重建和资格变化，并使用用户成绩锁。它便于保证一致性，也可能成为同场并发限制；不据此推断已验证高吞吐。

### 5. 保存业务回执后结束投递

回到 project 末尾的 scoreboard_result_receipt 插入，再回 Consumer 的 ACK。

成绩变化与回执在同一事务，失败一起回滚。Consumer 不能先把“处理过”单独持久化，再赌成绩更新成功。判题 complete 幂等与成绩 project 幂等分别保护两个动作。

**回到全局：** 此时数据库成绩投影已推进，可以供页面查询；Broker 发布确认还不是业务完成证据，回执才说明此事件已经持久处理。

### 6. 查询为什么先读数据库版本，再读缓存

源码：[ScoreboardPanel.vue](../../codeoj-frontend/src/components/ScoreboardPanel.vue) → [ScoreboardController.page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardController.java) → [ScoreboardService.page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java) → [ScoreboardTransactions.snapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

**阅读范围：** 页面看查询参数与版本显示；service 看 metadata、cache key、命中/回源；snapshot 看排名 SQL、版本和 pending 计数。

数据库先返回当前权威元数据，再使用 contestId、projectionVersion、revision、cacheEpoch、page、pageSize 构造 key。Redis 仅缓存 entries，当前 TTL 15 秒；未命中/不可用回源 DB。缓存命中也不是整个请求零 SQL。

| 标识 | 防止什么混用 |
| --- | --- |
| projectionVersion | 重建前后榜单页混在一起 |
| revision | 同版本更新前后的页面混用 |
| cacheEpoch | 清缓存后继续命中旧命名空间 |
| page/pageSize | 分页内容混用 |

snapshot 的排名 SQL 计算严格领先人数，不按分页下标重新排名。页面 pendingCount 表示判题未完成，projectionPendingCount 表示结果尚无投影回执，两种延迟要分清。

### 7. 比赛到时后怎样进入收敛阶段

源码：[ContestTransactions.finalizeIfDue](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)。

**阅读范围：** 看比赛状态与 endAt 条件，确认它将状态推进到 FINALIZING，最终 FINISHED 还要走成绩命令。

再读 [ScoreboardTransactions.settledFacts](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)：没有未完成提交，没有处理中/人工核查报名，没有未完成同步/回收，资格与容量关系正确；Redis 模式还要在结束后完成关闸对账。

合法受理但结束后才判完的提交仍能计入。判断依据是 acceptedAt 与资格/快照事实，不能到点直接丢弃晚到结果。

### 8. 从全部事实重建，再发布最终版本

源码：[ScoreboardTransactions.rebuild](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

**阅读范围：** 从 settledFacts 读到 authoritative/totals、生成新投影版本、写入明细/汇总、matches 校验与 activeVersion 切换；先走正常重建。

原始完成事实是重算依据，旧榜单只是投影。新版本在事务内生成并核验后切换，旧版本保留。包括确认资格的零分用户；当前重建有 10000 位参与者、50000 份比赛提交等边界。

源码：[ScoreboardTransactions.finish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

**阅读范围：** 看 expected 版本/当前管理员、再次 settledFacts、已重建与事实一致检查，再看 FINAL 与 FINISHED 更新。

最终结算不是“队列为空”或“所有发布 Confirm”。它要求权威事实可判定、投影核对一致。最终版本形成后，比赛才正式 FINISHED。

## 第二遍：迟到、重复和事实不一致

### 9. 更早 AC 晚到为什么会改变名次

回第 1 步例子：U1 一份第 12 分钟受理的 B 提交晚到并 AC，B 最早时间从 20 变成 12，achievedAt 变 12，U1 超过 U2。再来第 25 分钟的 B AC 不多加题，也不改变最早时间。

对照 project 的“更早才改”条件和 COUNT/MAX。若直接收到 AC 就分数加 1，无法处理同题多次与迟到时间。

### 10. 重复事件、回执缺失和重放

回到 project 的回执判断与事务，再读 [ScoreboardTransactions.recoverPublications/replay](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

已经有回执的事件不重复应用。Outbox 已 CONFIRMED 却迟迟没有回执时，可以在有限预算内重开原事件；管理员重放还要当前角色、期望版本、原因和预算。不能删除旧发送历史来伪装全新事件。

### 11. 重建失败或实时投影漂移

读 rebuild 的事务、matches 与版本切换顺序，并比较 [ScoreboardTransactions.finish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

中途异常回滚新版本，旧活动版本继续可查。finish 发现投影与事实不符时拒绝，不能在旧漂移上直接宣告最终结果。重建可以直接从 DB 事实恢复，不要求历史结果消息先按顺序全部消费。

### 12. NEEDS_ATTENTION、未同步报名为什么不能当零分结束

回到 settledFacts 的 pending 与 unresolved 检查。平台未决判题不是 WA，未决预留可能还没形成资格；直接结束会让最终参与者或成绩不完整。因此需要明确处理事实，再重建。

成绩传输延迟、判题未知、资格不一致是不同问题，不能靠统一清缓存解决。

### 13. 最终更正与缓存失效怎样审计

读 [ScoreboardTransactions.rebuild/clearCache](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) 与管理 command/audit。结束后的更正走显式 final revision，保留旧最终版本；清缓存推进 cacheEpoch，不改原始判题事实。

管理操作要当前角色、期望 contest/projection/revision 与原因。版本条件是防旧操作覆盖，不是授权凭据。不能把删除缓存或重建榜单当作修改用户代码判定的入口。
