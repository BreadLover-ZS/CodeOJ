# 链路五：成绩榜单与结算

本篇接着比赛提交 S2 的完成结果，按 **接收结果并计分 → 页面查榜 → 发布最终榜单 → 异常处理 → 纸上推演** 阅读。每段先解释当前步骤需要的概念，再介绍组件职责和源码入口。

假设用户 7 已确认参加比赛 99，第 10 分钟提交题 A，S2 最终得到 AC；这些标识是教学符号。阅读场景开启 `codeoj.reliable-judge.enabled=true` 和 `codeoj.scoreboard.enabled=true`（均默认关闭），报名与提交前置条件见[赛事链路](04-赛事报名与参赛链路.md)。

## 1. 接收判题结果，整理选手成绩

这一阶段把按“提交”保存的判定，整理成按“选手和题目”查询的成绩。这个整理结果称为**成绩投影**：可以从合法完成事实重算，不是另一套用户判定。

### 1.1 保存结果通知，交给成绩端处理

比赛提交完成时，执行控制组件 `ExecutionCommands` 的 `complete` 方法在同一事务里保存判定与 `JUDGE_RESULT` 待发事件。通知引用提交 ID 和结果版本，告诉成绩端“哪份结果已形成”，不直接携带一份可信分数。

结果发布与判题派发分开：`ScoreboardMessaging` 配置榜单专用交换机、队列和发布器，它的内部 `Relay` 周期发送结果事件，判题 worker 不会因此再次运行 S2。通用 Outbox 的领取、确认与补发已在[提交链路](02-提交与判题链路.md)解释，这里只跟结果事件。 Relay 每轮先检查已确认却迟迟没有业务回执的旧事件，按预算安排补发，再扫描本轮待发事件。首次阅读先跟 S2 的新事件，缺回执的恢复条件在第 4 章展开。

**现在读：**

| 方法或组件 | 作用与阅读范围 |
| --- | --- |
| [ExecutionCommands.complete](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java) | 定点看判定、resultVersion 与 JUDGE_RESULT 插入的事务关系 |
| [ScoreboardMessaging](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardMessaging.java) | 看 validate 的可靠判题依赖、结果拓扑，以及内部 Relay.tick 的 recoverPublications → due/claim → publish |
| [ScoreboardConsumer.receive](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardConsumer.java) | 解析消息、校验大小与结构，把 messageId 和结果引用交给投影事务；先停在 project 调用 |

Consumer 不是直接收到 AC 就加分。接下来先理解成绩规则和事件去重，再进入它调用的投影事务。

### 1.2 按不同题的首次通过计算成绩

本项目的 `FIRST_AC_V1` 规则是：对每位选手、每道题，取所有 AC 提交中**最早的受理时间 acceptedAt**。解题数是通过的不同题数，达成时间 achievedAt 是这些首次 AC 时间的最大值，表示“何时达到目前解题数”。它不使用程序跑完或消息抵达的时间，也不把各题时间相加。

例如 S2 是用户 7 第一道通过的题，受理时间为第 10 分钟，则解题数为 1、达成时间为第 10 分钟。再通过同一道题不会加成 2 题；一份更早受理的 AC 晚到，则可能把该题最早时间往前修正。

数据库因此分别保存：

| 表 | 保存什么 |
| --- | --- |
| `contest_score_problem` | 某选手某题的最早 AC 受理时间 |
| `contest_score_user` | 该选手的解题数与达成时间 |
| `scoreboard_result_receipt` | 哪个结果事件已经持久处理 |

报名已确认但没解题的用户也应入榜，成绩为 0、达成时间为 null。确认资格时，成绩事务组件 `ScoreboardTransactions` 的 `qualificationConfirmed` 会补零分行，后续投影和查询也会检查补齐。表结构见 [V004](../../codeoj-backend/mysql-init/migrations/V004__contest_scoreboard.sql)。

### 1.3 核对原事实，更新成绩并保存回执

题目服务的 `ScoreboardTransactions` 负责成绩数据库事务。它的 `project` 方法先按事件 ID、提交 ID 和结果版本核对原 Outbox、完成记录，再核验比赛资格、题目快照、发布版本、受理窗口、固定规格与结果摘要，避免凭消息自报 AC 就计分。

同一事件可能重投，因此需要业务回执。**成绩变更和回执在同一事务里提交**，失败一起回滚；否则可能先记“处理过”，成绩却没更新。回执挡同一事件的重复处理，每题最早 AC 规则则处理不同提交落到同一道题，二者用途不同。

当前事务采用 READ_COMMITTED（读已提交），并在处理比赛成绩时取得比赛行锁，再锁用户成绩行，协调投影、资格变化与重建；隔离级别本身不能替代这些业务锁。这样便于保证一致性，代价是同场竞争操作会等待。

**现在读：** [ScoreboardTransactions.project](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)，按以下顺序跟一份合法比赛事件：

1. 核对事件、结果版本和 COMPLETED；普通练习只记回执，不进入比赛成绩。
2. lock 取得比赛与活动投影版本，检查该事件是否已有回执。
3. zeros 补参与者；facts/verdict 校验原事实。
4. AC 分支新增该题，或仅在 acceptedAt 更早时修正时间；用 COUNT/MAX 更新用户汇总。
5. bump 推进修订号，写业务回执后提交；非 AC 不加题，也可以完成持久处理。

零分起点定点看同文件的 qualificationConfirmed / zeros。完成事务后回 [ScoreboardConsumer.receive](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardConsumer.java)：project 返回 true 才 ACK；false 或事实冲突则拒绝，运行时服务异常退避后 NACK 重投。发布 Confirm 只涉及消息交付，不能替代投影回执。

比赛已 FINISHED 或 CANCELLED 时，合法事件仍可补处理回执，但不会继续改成绩。结束后更正走第 4 章的显式管理命令。

## 2. 查询榜单，正确使用版本与缓存

成绩整理好后，页面通过题目服务的榜单接口查询。Redis 缓存的是某一版本、修订和分页的 `entries`，不是这套规则的唯一排名依据。

### 2.1 先确定版本，再读取页面

榜单查询入口是 `ScoreboardController.page`，协调服务 `ScoreboardService.page` 先向数据库取元数据，再按它确定的标识查询 Redis。需要先认识三个字段：

| 字段 | 用途 |
| --- | --- |
| projectionVersion | 选择整套成绩投影；重建时建立新版本 |
| revision | 标记当前投影的修订；结果或参与者变化会推进 |
| cacheEpoch | 管理清缓存时推进的命名空间，不修改成绩事实 |

缓存 key 还包含比赛 ID、page、pageSize。命中时把该 entries 装进本次数据库元数据；未命中或 Redis 不可用，则再取完整数据库页，并用完整快照返回的版本写缓存，TTL 为 15 秒。成绩修订后 key 随 revision 改变，不必等旧缓存过期才能读到新修订。

**缓存命中仍访问数据库。** 底层 `ScoreboardTransactions.snapshot` 会锁比赛行，检查当前账号、版本和进度，也可能补零分行。Redis 主要省重复的页面排名读取；未命中路径有两次快照，不能据此介绍成所有请求都由 Redis 独立回答。

**现在读：** [ScoreboardController.page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardController.java) → [ScoreboardService.page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java) → [ScoreboardTransactions.snapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。先跟 metadata 与 key，再看命中、完整回源和缓存异常分支；注意 Redis 网络调用在数据库事务之外。

### 2.2 排名、分页和两类进度怎样显示

排名先按解题数降序，同数按达成时间升序；相同成绩并列。SQL 计算的是“严格领先人数 + 1”，userId 只稳定显示次序，分页下标不能用作名次。例如两人并列第一，下一个人是第三，不是第二。

查询还返回两类进度：`pendingCount` 是尚未 COMPLETED 的判题数量，`projectionPendingCount` 是尚无结果回执的事件数量。前者包括平台未决任务，后者是成绩处理延迟；不能只看队列是否为空。

**现在读：** 继续在 [ScoreboardTransactions.snapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) 中看 withRows 分支的排名 SQL、selectedVersion 与 pending/lag 计数。核对同名次跨页时仍使用全局领先人数，以及零分选手的并列关系。

## 3. 等待事实收敛，发布最终榜单

到结束时间后停止接收新的比赛提交，与生成最终成绩是两件事。窗口内合法受理的 S2 可以在结束后才完成，仍应按它的 acceptedAt 计分。

### 3.1 到期后进入收敛阶段

比赛生命周期组件 `ContestLifecycle` 由调度器周期调用 `tick`，扫描到期比赛，再进入 `ContestTransactions.finalizeIfDue`。它把持久状态从 PUBLISHED 推进为 FINALIZING，表示等待判题、报名及相关核对完成，不会自动重建或结束比赛。

页面的 phase 可以先按当前时间显示 FINALIZING，而数据库 status 尚等扫描推进，阅读时应区分计算阶段与持久状态。

**现在读：** [ContestLifecycle.tick](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestLifecycle.java) → [ContestTransactions.finalizeIfDue](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)，先看 endAt 检查与状态变化；页面阶段定点看同文件的 view。

### 3.2 确认哪些数据已经可以结算

最终榜单需要可核对的完整事实。`ScoreboardTransactions` 中的 `settledFacts` 检查：

- 已过结束时间，比赛处于 FINALIZING 或 FINISHED，报名 ready。
- 没有未完成判题，也没有处理中、人工核查或未完成同步/回收的报名请求。
- 确认资格人数、去重人数、容量占用一致，资格能对应当前发布版本的确认请求。
- Redis 报名模式已关闸对账，处于 REDIS_READY，且对账时间不早于比赛结束。
- 当前同步重建上限为 10000 位参与者、50000 份比赛提交。

这里**没有要求所有结果事件都已有回执**。若权威判定和资格事实已完整，重建可以直接读数据库，不必等待历史消息全部消费；仍有 NEEDS_ATTENTION 的执行则不算完成，不能偷偷当成 WA 或零分结束。

**现在读：** [ScoreboardTransactions.settledFacts](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)，区分 pending、unresolved、资格/容量、Redis 结束后对账与数量边界。随后进入下面的重建入口，观察这些检查怎样成为管理命令的前置条件。

### 3.3 从原事实重建，再切换活动版本

管理员通过 `ScoreboardController.rebuild` 发起重建。命令携带刚读到的比赛版本、投影版本、revision 与原因，事务再核对当前管理员和期望值，防旧管理页面覆盖新状态。

事务组件的 `rebuild` 从合法完成事实重新求每人每题的最早 AC，汇总包括零分参与者的成绩，写入**新投影版本**，校验完整后再切活动入口。与原地清空、跨事务回填相比，中途失败会回滚本次新版本，旧活动榜仍可读取；代价是多版本存储、有限全量重算和同场锁等待。

**现在读：** [ScoreboardController.rebuild](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardController.java) → [ScoreboardTransactions.rebuild](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。辅助方法按用途读：

| 方法 | 作用与阅读范围 |
| --- | --- |
| authoritative | 从已完成合法事实求每用户每题最早 AC |
| totals | 将每题时间聚合到确认参与者，保留零分用户 |
| matches | 比较每题明细、用户汇总是否与重算结果一致 |

沿 command → settledFacts → authoritative/totals → 新版本写入 → matches → activeVersion 切换读。先假设当前 LIVE v1，首次重建成功后得到活动 REBUILT v2，比赛仍为 FINALIZING。

### 3.4 再次核验，正式结束比赛

重建解决“重新算一份一致的成绩”，最终发布还要确认这份活动榜在当前事实下仍有效。因此管理员重新读取版本后，通过 `ScoreboardController.finish` 发起结束命令。

`ScoreboardTransactions.finish` 再检查管理员、期望版本、事实收敛与投影一致，并要求已经重建；通过后把当前活动版本标 FINAL，记录 finalVersion，比赛改 FINISHED。它把 v2 变为最终版，不另建 v3；版本变化或事实不一致时则明确拒绝。

**现在读：** [ScoreboardController.finish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardController.java) → [ScoreboardTransactions.finish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。分别找到管理条件、已重建要求、matches 和 FINAL/FINISHED 更新。

| 触发动作 | 比赛状态 | 榜单版本 |
| --- | --- | --- |
| 定时器确认结束时间已到 | PUBLISHED → FINALIZING | 仍是原活动版本 |
| 管理员重建 | 保持 FINALIZING | 新建 REBUILT 版本并切换 |
| 管理员结束 | FINALIZING → FINISHED | 当前活动版本标 FINAL |

只等待定时器不会自动走完后两行。

## 4. 处理延迟、漂移与最终更正

### 4.1 发布已确认，为什么还要补发

结果事件 Confirm 成功后，消费者可能尚未形成业务回执。发布器每轮先调用成绩事务组件的 `recoverPublications`，检查已确认且超过等待窗口仍缺回执的结果事件，在剩余发布预算内重开原事件；耗尽转 ATTENTION。

管理员也可通过 `replay` 有限重放缺回执事件，要检查当前角色、期望版本、原因及追加预算，并审计。已经有回执的不重复应用，不删除旧发送历史伪装全新事件；FINISHED/CANCELLED 不走普通重放。

**现在读：** [ScoreboardTransactions.recoverPublications/replay](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)，再回 `ScoreboardMessaging` 的 Relay.tick。`recoverPublications` 自动补偿等待过久的发布，`replay` 是显式管理命令；Relay.tick 周期触发前者。

### 4.2 投影漂移或重建失败怎样处理

每题最早 AC 和用户汇总都是投影，出问题时要从原事实重算。重建中途异常不会切活动版本；finish 若发现当前投影与事实不符会拒绝，不能直接把漂移的成绩发布成最终版。

**现在读：** 回 [ScoreboardTransactions.rebuild](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) 的事务与切换顺序，结合 finish 的 matches。测试 [ScoreboardTest.midRebuildFailureRollsBackNewRowsAndKeepsReadVersion](../../codeoj-backend/codeoj-backend-question-service/src/test/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTest.java) 注入中途失败，核对新行回滚、旧读取版本不变。

### 4.3 最终更正与清缓存各改变什么

比赛已 FINISHED 后，普通迟到消息不再改最终投影。确需更正时，管理员走 `revise` 接口，调用 `rebuild` 的显式最终修订分支：创建新 FINAL 版本，切活动入口与 finalVersion，保留旧 FINAL，并记录原因、版本和审计。

清缓存则调用 `clearCache`，只推进 cacheEpoch，让后续查询使用新缓存命名空间，不修改用户判定或成绩。两类命令都需当前管理员和匹配的期望版本；版本条件防旧操作，不能替代授权。

**现在读：** [ScoreboardController](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardController.java) 的 revise/clear → [ScoreboardTransactions.rebuild/clearCache](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) 的 revision 分支、command 与 audit。需要查看处理记录时读同文件 operations。

## 5. 纸上推演与测试定位

### 5.1 手算并列与更早结果迟到

沿用比赛 99，以比赛开始为第 0 分钟。U1 为用户 7，其他选手为教学比较对象；均已确认资格。

| 选手 | A 最早 AC 受理时间 | B 最早 AC 受理时间 | 解题数 / 达成时间 | 初始名次 |
| --- | --- | --- | --- | --- |
| U1 | 10 | 20 | 2 / 20 | 1 |
| U2 | 15 | 20 | 2 / 20 | 1 |
| U3 | 8 | 无 | 1 / 8 | 3 |
| U4 | 无 | 无 | 0 / null | 4 |

先预测三件事：U1 的 B=12 分钟 AC 晚到；这条事件重复；又来 U1 的 B=25 分钟 AC。

核对：第一件把 B 的时间 20→12，题数仍为 2，达成时间变 max(10,12)=12，名次变 1、2、3、4；第二件由回执挡住；第三件不改该题最早时间，也不增加题数。事件去重与同题规则分别发挥作用。

### 5.2 手推到期、重建与最终发布

从 PUBLISHED、活动 LIVE v1 开始。假设执行管理命令时事实已收敛，每次使用刚读到的有效期望版本：写出“到期未扫描 → tick → 继续等待 → rebuild → 重新读版本后 finish”五行。

核对：到期时页面 phase 可先 FINALIZING，持久 status 尚为 PUBLISHED；tick 后持久状态 FINALIZING；继续等待不自动结束；首次重建切到 REBUILT v2；finish 将 v2 标 FINAL、比赛改 FINISHED。任一事实条件未满足，都不能套用成功路径。
