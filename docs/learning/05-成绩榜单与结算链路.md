## 首次场景：S2 的 AC 怎样成为一道解题成绩

用户 7 已确认参加比赛 99，在第 10 分钟提交题 A 的求和程序 P，提交记为 S2。它正常得到 AC；后台完成这份判定后，成绩端才有可处理的结果。

| 时点 | 业务事实或榜单怎样变化 | 首次先理解什么 |
| --- | --- | --- |
| 已有资格，尚未解题 | 用户 7 以 0 题在榜单参与者中 | 没提交不等于没参赛 |
| S2 完成，结果事件到达成绩端 | 核对它确属本场题 A、合法资格和窗口内提交 | 收到消息后仍查原事实，不直接相信自报 AC |
| 首次 AC 投影成功 | 题 A 记首次 AC 受理时间=第 10 分钟；用户解题数 0→1 | 取提交受理时间，不取消息抵达或程序跑完时间 |
| 页面查榜 | 显示 1 题及达成时间第 10 分钟 | 排名还取决于其他选手，不能凭一份 AC 就断言第 1 名 |
| 比赛到结束时间 | 等判题与报名收敛，重建核对后才能正式结束 | 到点停止新提交，与发布最终成绩是两个动作 |

这里的“投影”先理解为适合查榜的成绩整理结果：原提交 S2 保存判定，成绩表另存“用户解过哪些题、何时达到这个题数”。完整 SQL、回执和版本切换在后面展开。

源码先定位 [ScoreboardTransactions.project](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) 的 AC 分支、每题记录与 COUNT/MAX，再回 [ScoreboardService.page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java)。暂时只有一人一道题，理解后再看多选手并列。

## 全局位置：判题完成以后还有一段业务

```text
题目服务 complete：结果与 JUDGE_RESULT 同事务
  → 结果发布器 → MQ → ScoreboardConsumer
  → 校验原事实 → 同事务更新投影与业务回执
  → 查询 DB 元数据、Redis 页缓存 → 显示排名
比赛到结束时间 → FINALIZING
  → 等待判题/报名收敛 → 关闸对账 → 从事实重建并核对 → FINISHED
```

实时投影与最终结算不是一次动作。比赛需要可靠判题和资格事实，也要允许合法提交的结果迟到。Redis 缓存页面 entries，主体排名与版本在数据库，不能按常见教程直接介绍成 ZSet 排名。

| 数据层 | 这里保存什么 |
| --- | --- |
| 提交/执行/资格/快照事实 | 哪位选手何时提交哪道题，规则和判定是否有效 |
| contest_score_problem | 每用户每题最早 AC 的受理时间 |
| contest_score_user | 解题数与达到该成绩的时间 |
| scoreboard_result_receipt | 已持久处理的结果事件 |
| contest_scoreboard_state / contest_scoreboard_version | 当前启用版本、修订/缓存代次、最终版本与摘要 |
| Redis entries | 特定版本与分页的查询缓存 |

表结构见 [V004](../../codeoj-backend/mysql-init/migrations/V004__contest_scoreboard.sql)。第一遍假设原事实合法，结果正常投影，再完成一次合法结算。

## 必要机制：事实、事件、投影、缓存分别是什么

| 对象 | 具体例子 | 能否由其他数据重建 |
| --- | --- | --- |
| 业务事实 | 某人在比赛窗口受理的提交，最终得到 AC | 不能把原始判定当作缓存随意丢弃 |
| 结果事件 | 提醒成绩端“这份结果已形成” | 可按原事件与回执情况有限重放 |
| 成绩投影 | 每题最早 AC、每人题数和达成时间 | 可从完整合法事实重新计算 |
| 页面缓存 | 某版本第 1 页 entries | 可重新查投影生成 |

**为什么多存一层投影？** 页面需要按用户排名，原结果却是按提交保存。每次展示都全量扫描所有代码提交，查询和规则解释会更复杂；投影预先整理出适合排名的结构。

这不是在原事实之外创造新的判定。投影必须可解释地对应原事实，重建时再次核验来源。

### 这些类怎样分工

| 类 | 所处环节 | 为什么单独存在 |
| --- | --- | --- |
| ScoreboardMessaging | 传输 | 声明结果队列、发布器和监听器配置 |
| ScoreboardConsumer | 消费入口 | 识别消息、调用业务事务、控制 ACK/拒绝/重投 |
| ScoreboardTransactions | 数据库权威 | 把事实校验、投影、回执、版本变化放在本地事务 |
| ScoreboardService | 查询协调 | 在数据库事务外读写 Redis 页面缓存 |
| ScoreboardController | HTTP 入口 | 接收分页/管理命令、解析当前用户并包装返回 |

Transactions 类配置 READ_COMMITTED，并用比赛行锁串行化关键操作；隔离级别本身不等于完整业务互斥。Redis 网络不放进这个数据库事务，避免把查询缓存失败变成事实更新失败。

## 第一遍：正常计分、查榜与结算

### 1. 先手算 FIRST_AC_V1

沿用比赛 99，下面让其他选手参加并增加题 B 来展开排序；U1 就是用户 7，A 仍是求和题。U2—U4 是教学比较对象，不是测试夹具 ID。S2 是 U1 在第 10 分钟受理并通过题 A 的那份提交。

每用户每题取 AC 提交中最早的 acceptedAt。解题数为有 AC 的不同题数，achievedAt 为这些首次 AC 时间的最大值。它表示“何时达到目前解题数”，不是所有时间求和。

先按解题数多者优先，同数按 achievedAt 早者优先；相同并列。名次为严格领先人数加 1，userId 只稳定显示顺序。

| 选手 | A 最早 AC 受理时间 | B 最早 AC 受理时间 | 解题数 / achievedAt | 初始名次 |
| --- | --- | --- | --- | --- |
| U1 | 第 10 分钟 | 第 20 分钟 | 2 / 第 20 分钟 | 1 |
| U2 | 第 15 分钟 | 第 20 分钟 | 2 / 第 20 分钟 | 1 |
| U3 | 第 8 分钟 | 无 | 1 / 第 8 分钟 | 3 |
| U4 | 无 | 无 | 0 / null | 4 |

U4 已确认报名，因此即使没有提交也以零分入榜。这里的时间来自提交受理，不是判题完成或 MQ 消费时间。

ScoreResultEvent 是“哪份提交、哪个结果版本已形成”的内部通知，不携带可以直接信任的完整榜单。Map / entries 则是页面查询结果，来自整理后的成绩数据；二者用途不同。

**先认识本步方法：**

| 方法与源码 | 这个方法负责什么 | 接收什么 → 返回或改变什么 |
| --- | --- | --- |
| [complete](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)<br>ExecutionCommands | 核验 owner，原子保存结果及结果事件 | 带 token 的判定 → 是否接受完成 |
| [validate](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardMessaging.java)<br>ScoreboardMessaging | 启动时确认榜单依赖可靠判题 | 配置注入 → 合法启动或异常 |

**阅读范围：** 只追 JUDGE_RESULT 的 payload、resultVersion、Outbox 插入与结果写入的事务关系；执行权检查已在链路二读过。

判题完成时，结果事实与待投影事件同事务落库。消息主要引用 submissionId/resultVersion，消费者仍须核对数据库原事实，不能相信一个外部请求自称“此人 AC”就加分。

**阅读范围：** 看开关依赖、结果拓扑和内部 Relay.tick 中的 recoverPublications/due/claim/publish，不必重复深读链路二的通用传输实现。

**阅读范围：** 读解析、大小/valid 检查、messageId、project 调用与 ACK/拒绝；第一遍先沿合法事件。

**阅读范围：** 从 eventId/原 Outbox 查询读到执行状态检查、比赛锁、回执判断，再跟 facts/verdict；先走有 contestId 且未处理分支。

**当前进度：** MQ 消费只提供处理机会；核验成功的数据库事实才是成绩依据。接下来是本地事务内的投影计算。

### 计分不是简单“收到 AC 加一”

把一次 AC 分成两层：先确定**这道题的最早 AC**，再从所有题聚合**这个用户的成绩**。

| SQL 对象 | 本次变化 | 解决什么问题 |
| --- | --- | --- |
| contest_score_problem 的用户/题目记录 | 新题插入；更早 acceptedAt 才替换 | 同题多 AC 不重复算题，晚到更早 AC 能修正 |
| solvedCount 的 COUNT | 统计当前用户有 AC 的不同题记录 | 多题结果并发后不依赖盲目累加 |
| achievedAt 的 MAX | 取各题首次 AC 时间中最晚一个 | 表示何时达到当前解题数 |
| zeros 的资格查询 | 给确认选手补零分行 | 没提交的人也在榜单参与者集合中 |

先用表格例子手算，再打开 SQL 对应列和 WHERE 条件；不要从一整条长 SQL 开始猜规则。

### 4. 按每题最早 AC 更新用户成绩

继续在 project 内读 zeros、用户成绩行锁、contest_score_problem 与聚合更新。

**阅读范围：** 找没有该题记录时的插入、acceptedAt 更早时的更新，再看 solvedCount 的 COUNT、achievedAt 的 MAX 和 bump。

首次 AC 新增该题，更早 AC 修正时间，同题更晚 AC 不增加题数。zeros 给确认资格补零分行。非 AC 不加题，仍可完成该结果事件的持久处理。

当前实现有意用比赛锁串行化这一版投影、重建和资格变化，并使用用户成绩锁。它便于保证一致性，也可能成为同场并发限制；不据此推断已验证高吞吐。

### 5. 保存业务回执后结束投递

回到 project 末尾的 scoreboard_result_receipt 插入，再回 Consumer 的 ACK。

成绩变化与回执在同一事务，失败一起回滚。Consumer 不能先把“处理过”单独持久化，再赌成绩更新成功。判题 complete 幂等与成绩 project 幂等分别保护两个动作。

**回到全局：** 此时数据库成绩投影已推进，可以供页面查询；Broker 发布确认还不是业务完成证据，回执才说明此事件已经持久处理。

### 排名 SQL 与页面位置为什么不是一回事

| 排序/计数条件 | 业务解释 |
| --- | --- |
| solvedCount 更大 | 严格领先 |
| 相同题数且达成时间更早 | 严格领先 |
| 两项相同 | 并列，不因 userId 不同就改变名次 |
| 1 + 严格领先人数 | 本人的业务名次 |
| ORDER BY 最后加 userId | 同名次显示顺序稳定，方便分页 |

阅读 snapshot 的相关 COUNT 子查询：它计算整个版本中领先本人的人数，而不是“本页下标 + 1”。因此跨页不会重新从第 1 名开始。

### 缓存只负责加速页面数据

ScoreboardService.page 是缓存查询协调层，snapshot 是数据库查询事务。先读元数据，再按同一组标识取 entries，是为了避免把旧内容配上新版本标签。

- **缓存命中：** 在本次 DB 元数据上装入对应 entries。
- **缓存未命中：** 再取完整数据库页，并按返回的版本信息缓存。
- **缓存异常：** 回源数据库；不是重算用户判定，也不是清空成绩。

这属于读缓存/未命中回源的查询模式，但当前仍先访问数据库元数据，不能介绍为全部请求都由 Redis 独立回答。

### 6. 查询为什么先读数据库版本，再读缓存

**先认识本步方法：**

| 方法与源码 | 这个方法负责什么 | 接收什么 → 返回或改变什么 |
| --- | --- | --- |
| [page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardController.java)<br>ScoreboardController | 接收榜单分页与版本查询 | 比赛、页码/大小/版本、当前用户 → 页面响应 |
| [page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java)<br>ScoreboardService | 协调权威元数据、缓存读取与 DB 回源 | 比赛、分页、版本、actor → 榜单 Map |
| [snapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)<br>ScoreboardTransactions | 按指定版本读取排名与当前进度元数据 | 比赛、分页、版本、actor、withRows → Map |

**阅读范围：** 页面看查询参数与版本显示；service 看 metadata、cache key、命中/回源；snapshot 看排名 SQL、版本和 pending 计数。

数据库先返回当前权威元数据，再使用 contestId、projectionVersion、revision、cacheEpoch、page、pageSize 构造 key。Redis 仅缓存 entries，当前 TTL 15 秒；未命中/不可用回源 DB。

缓存命中也不是整个请求零 SQL。

| 标识 | 防止什么混用 |
| --- | --- |
| projectionVersion | 重建前后榜单页混在一起 |
| revision | 同版本更新前后的页面混用 |
| cacheEpoch | 清缓存后继续命中旧命名空间 |
| page/pageSize | 分页内容混用 |

snapshot 的排名 SQL 计算严格领先人数，不按分页下标重新排名。页面 pendingCount 表示判题未完成，projectionPendingCount 表示结果尚无投影回执，两种延迟要分清。

### 重建用版本切换，为什么不直接清空当前榜

| 方式 | 中途失败会怎样 |
| --- | --- |
| 原地清空后跨事务逐条回填 | 读者可能在批次间看到空榜或部分结果；缺少独立版本作为核对对象 |
| 当前实现：事务内写新版本，校验后切换 | 失败回滚新版本，旧活动版本仍是读取入口 |

rebuild 需要读懂三组辅助方法：

| 辅助方法 | 作用 | 输入 → 结果 |
| --- | --- | --- |
| authoritative | 从合法完成事实求每用户每题最早 AC | 比赛 State → 按用户/题索引的时间集合 |
| totals | 将每题事实聚合成参与者成绩，包括零分用户 | State、最早 AC 集合 → 用户与时间列表 |
| matches | 比较当前选中投影与重算事实是否一致 | State、权威集合 → boolean |

继续打开 [ScoreboardTransactions](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) 的这些方法。

先搞清集合里存的是什么，再读循环和 INSERT；不需要逐行背 Map 操作。

| [rebuild](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)<br>ScoreboardTransactions | 从权威事实构建并切换新投影版本 | 比赛、命令、actor、更正标志 → 新版本/摘要 |
| [finish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)<br>ScoreboardTransactions | 核对已重建投影与事实后生成最终版本 | 比赛、命令、actor → FINAL 与 FINISHED |

**阅读范围：** 从 settledFacts 读到 authoritative/totals、生成新投影版本、写入明细/汇总、matches 校验与 activeVersion 切换；先走正常重建。

原始完成事实是重算依据，旧榜单只是投影。新版本在事务内生成并核验后切换，旧版本保留。包括确认资格的零分用户；当前重建有 10000 位参与者、50000 份比赛提交等边界。

**阅读范围：** 看 expected 版本/当前管理员、再次 settledFacts、已重建与事实一致检查，再看 FINAL 与 FINISHED 更新。

最终结算不是“队列为空”或“所有发布 Confirm”。它要求权威事实可判定、投影核对一致。最终版本形成后，比赛才正式 FINISHED。

## 第二遍：迟到、重复和事实不一致

### 比赛状态与榜单版本：切换的是哪一个对象

| 触发动作 | 比赛 status 怎样变 | 榜单版本怎样变 | 后续该看什么 |
| --- | --- | --- | --- |
| 首次初始化榜单 | 不因初始化而结束比赛 | 建 LIVE v1；activeVersion=1 | lock、qualificationConfirmed 与 zeros |
| project 接受合法结果，比赛未取消/结束 | 不因一条结果直接变 FINISHED | 更新当前活动版本的成绩和 revision；不每条结果建新 projectionVersion | project 的明细、汇总、bump |
| 到结束时间，finalizeIfDue | PUBLISHED → FINALIZING | 暂不因此新建榜单版本 | 等判题、报名与适用的结束后对账收敛 |
| rebuild，事实已收敛 | 保持 FINALIZING | 新建 REBUILT 版本，切 activeVersion；旧非 FINAL 版本变 RETIRED | authoritative/totals/matches |
| finish，已重建且再次核对通过 | FINALIZING → FINISHED | 将当前活动版本标 FINAL，记录 finalVersion；不是另起一个新版本 | 后续普通迟到事件只记回执，不改成绩 |
| 显式最终更正 rebuild(revision=true) | 保持 FINISHED | 新建 FINAL 版本并切换；旧 FINAL 保留 | 管理版本、原因、审计 |
| clearCache | 不改变比赛状态或成绩事实 | cacheEpoch 前进；不靠它制造新判题结果 | 下次按新命名空间查询 |

依据：[ContestTransactions.finalizeIfDue](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java) 与 [ScoreboardTransactions.rebuild](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)、finish、clearCache。LIVE/REBUILT/FINAL/RETIRED 属于榜单版本，PUBLISHED/FINALIZING/FINISHED 属于比赛；不能画成同一列状态。

再分清三个数字：projectionVersion 选择整套投影，revision 标记其中的修订，cacheEpoch 控制缓存命名空间。报名中的 RegistrationSettings.revision 来自 contest.version，与榜单 revision 不是同一个字段。

### 9. 更早 AC 晚到为什么会改变名次

回第 1 步例子：U1 一份第 12 分钟受理的 B 提交晚到并 AC，B 最早时间从 20 变成 12，achievedAt 变 12，U1 超过 U2。再来第 25 分钟的 B AC 不多加题，也不改变最早时间。

对照 project 的“更早才改”条件和 COUNT/MAX。若直接收到 AC 就分数加 1，无法处理同题多次与迟到时间。

### 跟一份迟到结果，看两张表各改什么

对照 [ScoreboardTransactions.project](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)，使用前文 U1 的 A=10 分钟、B=20 分钟作为初始状态。

| 到来的事实 | 每题明细怎样变 | 用户汇总怎样变 | 为什么 |
| --- | --- | --- | --- |
| B 在第 12 分钟受理的提交，较晚完成并 AC | B 的最早 AC 20→12 | solved 仍为 2；achievedAt=max(10,12)=12 | 新事实更早，不能按消费顺序保留 20 |
| B 在第 25 分钟受理的另一份 AC | 不变，仍为 12 | 不变 | 同题不会多解一道，也没有更早 |
| 第一条事件重复投递 | 回执判断后不再应用 | 不变 | eventId 回执解决重复处理 |
| A 的一份 WA | 不增加 AC 明细 | 不加分 | 结果有效不等于结果为 AC |

区分两重保护：**回执挡住同一事件重复处理，最早 AC 规则处理不同提交落到同一题。** 只做其中一种都不够。

#### 这次更新后，缓存为什么不必等 15 秒

跟 [ScoreboardTransactions.bump](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java) 再回 [ScoreboardService.page](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardService.java)：成绩变化推进 revision。下一次查询先从 DB 读取版本元数据，构造包含 projectionVersion/revision/cacheEpoch 的缓存 key，因此不会拿旧 revision 的 entries 充当新修订页面。

缓存没命中时再取完整 DB 快照，写入该快照自己的 key；15 秒 TTL 主要限制旧缓存保留时间，不是“成绩固定延迟 15 秒更新”。并发发生的更新仍可能晚于本次快照，不能把这个查询流程说成永远展示请求结束瞬间的最新值。

### 11. 重建失败或实时投影漂移

读 rebuild 的事务、matches 与版本切换顺序，并比较 [ScoreboardTransactions.finish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/scoreboard/ScoreboardTransactions.java)。

中途异常回滚新版本，旧活动版本继续可查。finish 发现投影与事实不符时拒绝，不能在旧漂移上直接宣告最终结果。重建可以直接从 DB 事实恢复，不要求历史结果消息先按顺序全部消费。

### 12. NEEDS_ATTENTION、未同步报名为什么不能当零分结束

回到 settledFacts 的 pending 与 unresolved 检查。平台未决判题不是 WA，未决预留可能还没形成资格；直接结束会让最终参与者或成绩不完整。因此需要明确处理事实，再重建。

成绩传输延迟、判题未知、资格不一致是不同问题，不能靠统一清缓存解决。

### 判题完成、投影跟上、允许结束是三种不同判断

| 观察到什么 | 说明什么 | 接下来读哪里 |
| --- | --- | --- |
| pendingCount > 0 | 存在尚未 COMPLETED 的执行，包括待处理平台问题 | settledFacts 如何拒绝结算 |
| pendingCount=0，projectionPendingCount > 0 | 判题事实已完成，但部分结果还没有业务回执 | recoverPublications/replay 与 rebuild |
| 消息队列暂时为空 | 仅是某个传输观察 | 不能替代 DB 事实和资格核对 |
| settledFacts 通过 | 判题、资格、容量及适用的结束后对账已满足条件 | authoritative/totals/matches，再看 finish |

**结果回执没有全部补齐，能不能重建？** 当前 settledFacts 没有要求 projectionPendingCount=0。只要全部权威事实已完成且其他收敛条件满足，rebuild 可以直接从数据库重算，finish 再验证所选投影与事实一致；不能把“所有历史消息必须先消费完”写成不存在的前提。

比赛 FINISHED 后才到达的合法结果事件，project 仍可记录处理回执，但不会继续改最终成绩投影。需要更正时走显式最终修订命令，不靠一条迟到消息暗中改榜。
