# CodeOJ 学习手册 · 00 总览与阅读顺序

> 本系列是面向学习的代码导读，帮助你从零快速消化 CodeOJ 这个项目。
> 配套的《01-architecture-and-judge-call-chain.md》是静态审计向材料，侧重于发现问题和风险，建议学完本系列后再读。

## 1. 这个项目是什么

CodeOJ 是一个**前后端分离的微服务在线判题（OJ）系统**，核心业务只有两件事：

1. **管理内容**：题目（含测试用例、判题限制）、用户、提交记录。
2. **执行判题**：用户提交代码 → 放进消息队列 → 判题服务取走 → 调用代码沙箱执行 → 比对输出 → 回写结果。

## 2. 技术栈速览

| 层     | 技术                                                      | 在这个项目里承担的角色                               |
| ----- | ------------------------------------------------------- | ----------------------------------------- |
| 网关    | Spring Cloud Gateway（Spring Cloud Alibaba + Nacos）      | 统一入口 8101，路由分发、CORS、拦截 `/inner/**` 内部接口   |
| 服务注册  | Nacos                                                   | 服务发现，网关按 `lb://服务名` 转发                    |
| 业务服务  | Spring Boot + MyBatis-Plus                              | 用户 / 题目 / 判题三个服务                          |
| 登录态   | Redis + Spring Session                                  | 各服务共享同一个 Session（登录一次，处处可用）               |
| 判题异步  | RabbitMQ（direct exchange）                               | 提交后发消息，判题服务异步消费，避免同步阻塞                    |
| 服务间调用 | OpenFeign                                               | 用户/题目/判题服务之间互相查询（`QuestionFeignClient` 等） |
| 代码沙箱  | 独立 Spring Boot 服务（进程级隔离）                                | 编译并运行用户代码，带鉴权与超时防护                        |
| 前端    | Vue 3 + TypeScript + Arco Design + Vuex + Monaco Editor | 题库、做题、提交记录、管理端页面                          |

## 3. 项目地图（先记住这张图）

```text
Vue 前端 :8000
    |
    | HTTP  /api/**
    v
GateWay :8101  (路由 + CORS + inner 拦截)
    |-- /api/user/**     -> User Service :8102      (注册/登录/用户信息)
    |-- /api/question/** -> Question Service :8103  (题目 CRUD、提交记录)
    `-- /api/judge/**    -> Judge Service :8104

Question Service                        Judge Service
   |  保存提交记录、发 MQ                   |  消费 MQ、编排判题
   |-------------------------------------->|
   | RabbitMQ: code_exchange -> code_queue  |
   |    (消息体只装 questionSubmitId)        |
   |                                      |
   |                 OpenFeign (inner 接口, 带 X-Inner-Secret 头)
   |<-------------------------------------|
   |                                      | HTTP + auth 请求头
   |                                      v
   |                               Code Sandbox :8090 (编译+运行用户代码)

MySQL: user / question / question_submit / post
Redis: Spring Session 登录态
Nacos: 服务注册与发现
```

## 5. 推荐阅读顺序（分 5 站）

学习路径遵循"**先外围、后核心；先单服务、后跨服务**"的原则。每一站的"通关问题"能独立回答就说明这一站消化了。

### 第 1 站：公共层（半天）

读 `codeoj-backend-common` + `codeoj-backend-model` 全部类。

- 目标：搞懂全项目的"通用语言"——统一响应结构、错误码、业务异常、实体字段、枚举。
- 通关问题：
  - `BaseResponse` 的字段有哪些？为什么每个接口都返回它？
  - `ErrorCode` 和 `BusinessException`、`GlobalExceptionHandler` 是什么关系？
  - `QuestionSubmit` 的 `status` 字段有哪几个取值，分别代表什么？

### 第 2 站：用户服务 + 登录态（1 天）

读 `codeoj-backend-user-service` 的 `UserController` / `UserServiceImpl`，再看 `UserInnerController` 和 `AuthInterceptor`。

- 目标：搞懂登录、注册、会话、权限切面。
- 通关问题：
  - 密码是用什么算法存储的？为什么不能是 MD5 直存？
  - 登录成功后登录态存在哪里？为什么其他服务（如题目服务）也能拿到当前用户？
  - `@AuthCheck(mustRole = x)` 是谁在处理？切面里怎么拿 session 里的用户？
  - 封号（ban）用户会受到什么限制？

### 第 3 站：网关（0.5 天）

读 `codeoj-backend-gateway` 的 `application.yml`、`GlobalAuthFilter`、`CorsConfig`，配合 `service-client` 里的 `InnerApiAuthFilter` / `FeignInnerAuthConfig`。

- 目标：搞懂统一入口和内部接口的双层防护。
- 通关问题：
  - 为什么业务服务端口不能直接暴露到外网？
  - `/inner/**` 接口被谁拦了两层？每层校验什么？
  - CORS 白名单配置在哪？为什么不能 `*` 加 `credentials` 同时用？

### 第 4 站：核心判题链路（2 天，重点）

按下面这个顺序读，读完后你应该能画出一张完整的时序图：

1. `QuestionController#doQuestionSubmit` —— 提交入口
2. `QuestionSubmitServiceImpl#doQuestionSubmit` —— 保存记录 + 发消息
3. `MyMessageProducer` / `InitRabbitMqBean`（判题服务）/ `MyMessageConsumer` —— MQ 三件套
4. `JudgeServiceImpl#doJudge` —— 判题编排（读 3 遍）
5. `QuestionFeignClient` / `QuestionInnerController` —— 内部数据获取
6. `CodeSandboxFactory` / `RemoteCodeSandbox` / `ExecuteCodeController` / `JavaNativeCodeSandbox` —— 沙箱
7. `JudgeManager` / `DefaultJudgeStrategy` / `JavaLanguageJudgeStrategy` —— 判题策略

通关问题（全部能回答，核心链路才算真懂）：

- 为什么 MQ 消息体只放一个 `questionSubmitId`？省了什么、代价是什么？
- `WAITING -> RUNNING -> SUCCEED/FAILED` 的状态迁移发生在代码里的哪几行？
- 「判题完成」为什么不等于「答案正确」？正确答案藏在哪里？
- 沙箱的 `auth` 请求头是谁加的？谁校验的？
- 判题策略用的是哪个设计模式？加一种语言要改哪些地方？

### 第 5 站：前端 + 部署（1 天）

读 `codeoj-frontend/src` 的 `router/routes.ts`、`access/`、`store/user.ts`、`plugins/axios.ts`，然后打开 `ViewQuestionView.vue` 等页面看提交流程；最后看 `docker-compose.*.yml` 和 `mysql-init/create_table.sql`。

通关问题：

- 前端路由权限守卫逻辑在哪？`needAccess` 和 `checkAccess` 怎么配合？
- 页面提交代码时掉哪个接口？返回的是什么（提交记录的 id 还是判题结果）？
- 前端怎么看到判题结果？（轮询提交列表接口）
- 生产环境哪些配置必须用环境变量覆盖？

## 6. 三条"别踩"的坑（来自项目修复经验）

1. **判题状态回滚**：消费消息失败时，如果记录还是「判题中」，必须显式更新为「失败」，否则记录永远卡在 RUNNING（见 `MyMessageConsumer` 的 catch 分支）。
2. **内部接口双防护**：网关挡 `/inner/**` 还不够，业务服务内的 `InnerApiAuthFilter` 必须二次校验 `X-Inner-Secret`，防绕过网关直连。
3. **`@AuthCheck` 同 Bean 自调用**：AOP 切面只对代理对象生效，同类内部调用 `this.xxx()` 会绕过拦截，务必通过注入其它 Bean 调用。
