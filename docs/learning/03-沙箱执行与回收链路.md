# 链路三：从执行请求到用户程序停止与资源回收

上条链的 worker 已领取 S1，持有代码、测试输入、资源限制、token T1 与期限。本链展开它调用沙箱后的内部过程，最后把运行输出和资源结果交回判题端，同时解释物理执行如何收尾。


**本篇导航：** [全局](#全局位置数据库执行权之外还有真实进程) → [执行机制](#必要机制代码怎样从字符串变成真实进程) → [正常执行](#第一遍正常执行) → [故障与回收](#第二遍运行和管理器出问题时) → [检查理解](#阅读成果与测试)

## 全局位置：数据库执行权之外，还有真实进程

```text
判题 worker → HTTP → 沙箱 Controller / 执行管理器
  → 登记 T1、申请物理 slot
  → 编译容器 → 只读 class 产物
  → case-0 新容器 → case-1 新容器 → …
  → 收集输出与受信结果 → 清理容器/卷 → 持久结果与 slot 状态
  ← 返回 ExecuteCodeResponse → 判题策略比较答案 → 题目服务保存判定
```

沙箱不是在业务 JVM 内简单调用用户方法。管理器编排隔离进程，监督器在容器内执行期限与收据控制，用户程序以受限身份运行。题目服务的 token 管结果生效，监督器管程序停止，registry 管物理对象与容量。

| 配置或数据 | 先理解它的职责 |
| --- | --- |
| 判题端 type=remote | HTTP 调用方式 |
| 沙箱端 mode=isolated | 容器执行方式，默认模式；与 remote 可同时成立 |
| ExecuteCodeRequest | 代码、语言、inputList、资源限制、T1、绝对期限 |
| ExecuteCodeResponse | outcome/status、outputList、judgeInfo 与诊断 |
| slot | 沙箱物理并发名额，不是 worker 的本地 Semaphore |
| 持久登记 | token/hash/期限/slot/状态/响应，供重复请求与管理器恢复 |

协议类型对照：[ExecuteCodeRequest](../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/codesandbox/ExecuteCodeRequest.java) 与 [ExecuteCodeResponse](../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/codesandbox/ExecuteCodeResponse.java)；先把 worker 构造值与执行端读取值一一对应。

第一遍假设请求合法、资源够、两个用例正常结束、清理成功。期望输出不传给沙箱，答案比较仍在链路二。

## 必要机制：代码怎样从字符串变成真实进程

### 两个接口、两处选择：先选调用方式，再选执行方式

| 位置 | 接口或配置 | 这里的选择是什么 |
| --- | --- | --- |
| 判题服务 | [CodeSandbox](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandbox.java) | 供 worker 调用的沙箱客户端抽象 |
| 判题服务 | [CodeSandboxFactory.newInstance](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxFactory.java) | 根据 type 选择客户端；当前仅支持 remote，其他值明确拒绝 |
| 沙箱服务 | [CodeSandboxService](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/CodeSandboxService.java) | HTTP 入口委托的执行服务，包含鉴权与执行能力 |
| 沙箱服务 | JavaIsolatedCodeSandbox 的 ConditionalOnProperty | mode=isolated 或未指定 mode 时启用隔离实现 |
| 沙箱服务 | JavaNativeCodeSandbox 的 ConditionalOnProperty | 只有显式 mode=native 才启用本机实现 |

因此 remote + isolated 是完整的一条路径：判题端远程调用，服务端用容器执行。不能把 remote/native/isolated 当成同一个枚举的三个可互换值。

读工厂后回到 worker 的 executeCode 调用；到达服务端后再看条件 Bean。NativeCompiler 虽然名字含 Native，也被隔离实现放进编译容器使用，不能根据类名推断用户程序一定在宿主机运行。

### 三个执行者处在不同层

| 对象 | 运行在哪里 | 能控制什么 |
| --- | --- | --- |
| Java 沙箱管理器 | 后端沙箱服务进程 | 登记、调用 Docker CLI、收集与清理 |
| 容器内 supervisor | 受信隔离控制进程 | 降权启动、期限、收据与后代清理 |
| 用户 JVM | 受限运行环境 | 执行参赛者 main，读写标准流 |

管理器通过 ProcessBuilder 启动 Docker CLI，是在控制执行环境；用户 JVM 在容器内运行，不会把用户类加载到业务服务 JVM 里。

### 编译、入口和运行为什么拆开

| 辅助程序 | 作用 | 输入 → 产出 |
| --- | --- | --- |
| [main](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/nativejava/NativeCompiler.java)<br>NativeCompiler | 编译 Java 并识别可运行入口 | 源文件、产物/收据路径、nonce → class 与入口收据 |
| [NativeReceipt](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/nativejava/NativeReceipt.java) | 核验编译器给管理器的控制结果 | 收据、nonce → 结果或异常 |
| [main](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/nativejava/IsolatedLauncher.java)<br>IsolatedLauncher | 在独立用户 JVM 加载入口并调用 main | class 目录、入口名 → 退出状态 |

**为什么不靠正则寻找 public class？** 注释、字符串和嵌套类型会干扰文本猜测。NativeCompiler 调用 JavaCompiler，再按 class 元数据选入口；识别阶段加载类时不初始化它，避免提前执行用户静态代码。

IsolatedLauncher 把用户 main 与加载失败区分为可观测退出状态，最终由监督器和管理器解释，不能直接当成 AC。

### 三根标准流为什么要并发处理

先读 [BoundedProcessRunner](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/BoundedProcessRunner.java) 的 run、read、await 和 finally。

- 用户持续写 stderr，若管理器只读 stdout，另一管道可能写满，程序被阻塞。
- 用户不读 stdin，管理器写输入也可能阻塞。
- 当前实现分别调度写输入、读 stdout、读 stderr，共享输出预算和期限。
- 超限后仍要结束进程并回收线程，不能无限等待 EOF。

BoundedProcessRunner.Result 是管理器观察子进程的本地结果，ExecuteCodeResponse 是沙箱 HTTP 协议，两者不是同一层对象。

### 为什么执行器之外还要有 registry

执行器会编译运行，但还需要有人判断“这个 token 执行过吗、是否还有容量、上次管理器退出后留下了什么”。

| registry 保存什么 | 只放内存会缺少什么 |
| --- | --- |
| token 与 hash | 无法识别重复请求与内容冲突 |
| slot 占用 | 重启后计数归零，旧容器却可能还在 |
| deadline / state | 后继管理器不知道期限和待清理阶段 |
| response | 无法向同一身份回放已有结果 |

JavaIsolatedCodeSandbox 将 executeOnce 作为 Work 回调交给 registry。**传回调不等于立即执行**：registry 先校验、占位和登记，之后才调用 Work。

**当前进度：** 数据库已授予逻辑执行权，沙箱又确认执行身份并保留物理名额；接下来才真正启动编译和用户进程。

**先认识本步方法：**

| 方法与源码 | 这个方法负责什么 | 接收什么 → 返回或改变什么 |
| --- | --- | --- |
| [executeOnce](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java)<br>JavaIsolatedCodeSandbox | 编排一次编译及多个独立用例运行 | ExecuteCodeRequest → 汇总执行结果 |

**阅读范围：** 先从 token 工作目录、Submission.java 写入读到编译容器创建、upload/start、trustedResult 和 NativeReceipt；暂时停在用例循环之前。

管理器将代码写入 T1 专属工作目录，创建编译相关卷与容器，调用受信 NativeCompiler。编译产物与入口收据是后续运行依据，随机 nonce 用于核验编译收据。

编译成功不等于答案正确，只表示可以进入运行。明确用户语法错误是 CE；编译基础设施或阶段预算异常不能一概当成 CE。

### Docker 的不同机制分别保护什么

| 机制 | 要解决的问题 | 在本项目中读什么 |
| --- | --- | --- |
| namespace | 隔开运行视图和进程环境 | 容器、禁网与后代清理 |
| cgroup | 限制整组进程资源 | memory、cpus、pids 参数 |
| 挂载与只读 | 限定可见/可写文件 | artifact、source、receipt、tmpfs |
| UID/GID 与 capabilities | 降低用户程序权限 | supervisor 降权、cap-drop 等参数 |

read-only 不限制内存，-Xmx 不限制整个容器；每类参数保护的对象不同。

编译阶段要生成 class，运行阶段只读使用 class；用户输出和受信收据也有不同用途。读卷挂载时，先标明“谁写、谁读、何时只读”。

### 5. 谁运行程序、计时、清理后代并生成结果

源码：[supervisor.py](../../codeoj-backend/codeoj-backend-codesandbox/isolation/supervisor.py) 的 unprivileged、main。

**阅读范围：** 从阶段预算/绝对期限取较早值读起，跟到降 UID/GID、Popen、wait、后代清理、cgroup 指标与私有结果文件。先走正常退出分支。

监督器与用户程序在同一隔离环境中，但承担不同职责。用户 Java 降为 UID/GID 10000，控制收据由受信监督器生成；stdout 是答案数据，不能靠用户打印 JSON 来宣布“已经安全结束”。

| 风险 | 具体阅读位置与控制 |
| --- | --- |
| 网络访问 | engine.create 的 network none |
| 写宿主或产物 | 挂载范围、read-only、只读运行产物 |
| 内存/CPU/PID | cgroup memory/cpus/pids 参数与观测 |
| 临时文件和描述符 | tmpfs 与 ulimit |
| 输出无界 | BoundedProcessRunner 的双流读取与输出预算 |
| 死循环与后代逃逸运行 | supervisor 的期限和 namespace 后代清理 |

容器中的受信部分与用户降权进程应分开理解。当前机制不等于完成内核逃逸认证。

### 6. 管理器怎样判断一次用例的结果

**先认识本步方法：**

| 方法与源码 | 这个方法负责什么 | 接收什么 → 返回或改变什么 |
| --- | --- | --- |
| [trustedResult](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java)<br>JavaIsolatedCodeSandbox | 核对进程/容器与私有控制收据 | 容器、运行结果、目标文件 → 可信 JSON 结果 |

**阅读范围：** 先看 trustedResult 如何核验进程/容器状态和私有收据，再回用例循环的 end 分支及指标汇总。

多个用例的 time、memory 按当前实现取观测最大值。时间包含 JVM 启动；内存是用例 cgroup 的观测，包含 JVM、监督器和后代，不等于 Java 堆大小。

正常完成后带 outputList 与资源指标回到 registry。标准答案仍在 worker 领取的固定规格中，下一步交给链路二的策略比较。

### 数据库 token、文件锁与持久日志怎样配合

| 机制 | 保护什么 | 不能说明什么 |
| --- | --- | --- |
| executionToken | 哪次结果能被业务库接受 | 不能直接停止远端进程 |
| 文件锁 | 谁可操作本地 slot/登记 | 锁释放不等于容器已删除 |
| slot 日志 | 重启后仍能找到未收回占用 | 文件存在不等于用户仍在运行 |
| Docker labels | 按 pool/token 找所属物理对象 | 不能授予数据库执行权 |
| REAP_PENDING | 清理尚未确认 | 不代表可归还名额 |

registry 先保存 slot/token 登记再创建对象，恢复还要处理两份日志只写完一份的窗口。**锁管互斥，日志管跨重启记忆，实际删除才收回物理资源。**

**先认识本步方法：**

| --- | --- | --- |

**阅读范围：** 跟 work.execute 返回后 engine.removeExecution、登记 response/state 和 slot 记录删除；先沿 cleaned=true。

**阅读范围：** 按 token 的 label 定位所属容器与卷，跟踪实际删除及失败传播。

## 第二遍：运行和管理器出问题时

### 8. HTTP 超时是否就是用户 TLE

回到 RemoteCodeSandbox 的总调用期限与取消，再对照 executeOnce/supervisor 的用例期限。HTTP 超时只说明调用方没有拿到可信响应，远端可能还在运行；用户 TLE 需要执行层明确超限依据。

不能在 HTTP 客户端透明换 token 再执行一次。数据库恢复状态机决定新尝试，旧物理执行还需监督器和回收管理。

### 用一张预算表区分四种“超时”

以下是源码默认值的教学对照，实际启动配置可以覆盖它们。

| 限制 | 默认或计算方式 | 控制什么 | 不能据此推断什么 |
| --- | --- | --- | --- |
| 业务领取租约 | 15 秒，可续租；单次尝试最多 60 秒且受全局恢复期限约束 | 当前 worker 是否仍有资格提交结果 | 租约失效不等于容器已删除 |
| 沙箱尝试总期限 | 到达时刻 + 30 秒，与请求绝对期限取较早值 | 编译和所有用例共用的总预算 | 每个用例都能再获得完整 30 秒 |
| 编译阶段 | 15 秒，仍受尝试总期限约束 | 编译及阶段等待 | 编译平台故障可以当成用户 CE |
| 单用例运行 | 使用请求的 runTimeLimitMs；未给时回退 5 秒 | 一份输入对应的用户程序 | 所有用例耗时之和就是上报 time |
| 客户端 HTTP | 连接 2 秒、读取 35 秒、总调用 38 秒 | 网络调用等待 | 请求超时就证明用户 TLE |

对照 [JavaIsolatedCodeSandbox.executeOnce](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java) 的 deadline、compileDeadline、caseLimit，再看 [RemoteCodeSandbox.executeCode](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/impl/RemoteCodeSandbox.java) 的 HTTP 等待。

例如题目每用例 2 秒，共 3 个用例，每个都耗时 1.5 秒，全部运行可能花 4.5 秒加编译/编排开销；上报 time 取用例耗时最大值，而不是 4.5 秒。总尝试预算还要容纳这些阶段。

进入某用例前，若剩余总预算不足 caseLimit + 250 毫秒，当前实现返回平台预算不足；它不能证明用户在独立、完整的 2 秒窗口里超时。valid 也会拒绝大于沙箱配置上限的请求时限，不能假设题目任意限制都可执行。

### 9. 同 token 重复请求会怎样

回到 registry.execute 的 existing 分支：同 T1 同摘要可以在有限保留窗口内等待或回放；同 token 换内容拒绝。身份过期且没有可回放记录时，不新建执行。

按原 token 登记和本地恢复是沙箱的有限保证，不是对任意历史 token 永久提供 exactly-once。记录保留与 registry 容量也有明确边界。

### 10. 管理器被杀，谁让用户程序停下来

**先认识本步方法：**

| 方法与源码 | 这个方法负责什么 | 接收什么 → 返回或改变什么 |
| --- | --- | --- |
| [recoverExecutions](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java)<br>JavaIsolatedCodeSandbox | 定时触发持久登记恢复与残留清理 | 调度触发 → registry.recover |

监督器独立执行阶段预算与总期限，即使管理器或 HTTP 调用方退出，也不能把用户进程的停止完全寄托在客户端超时。

**阅读范围：** 从定时入口跟到 registry.recover；再看 recover/reap 如何取得 slot 锁并清理旧对象。

持久登记让后继管理器知道 T1 的物理对象与占用。新管理器取得恢复权后清理，不能仅因数据库租约过期就假设容器已经停止或名额空闲。

### 11. 删除失败为什么必须继续占名额

回到 registry.run 的 cleaned=false 与 reap：保存 REAP_PENDING 和持久 slot，返回清理待完成的平台结果，后续重试清理。

假设总容量 2，T1 的结果已算出但删除失败，另一个名额空闲，此时可用只有 1。归还逻辑执行权、本地 Semaphore、沙箱 slot 的时机不同。

### 用 T1 推演一次“程序结束，但删除失败”

继续读 [DurableExecutionRegistry.run](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java) → [DurableExecutionRegistry.recover](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java) → reap，逐格核对写日志与删除顺序。

| 时刻 | 已发生什么 | 记录和响应 | 容量能否安全复用 |
| --- | --- | --- | --- |
| 1 | Work 跑完，暂得 EXECUTED | 尚未完成 registry 收尾 | 仍占用 |
| 2 | removeExecution 删除失败 | 响应改为平台错误 EXECUTION_CLEANUP_PENDING；保存 REAP_PENDING | slot 日志保留 |
| 3 | 当前调用返回并释放文件锁 | 物理对象可能仍存在 | 其他调用须先清理旧对象，不能只见锁空闲就直接启动 |
| 4 | 后续 recover 获得锁并成功删除旧对象 | 保留原平台错误响应，状态改 COMPLETED，删除 slot 日志 | 才能继续复用 |

**注意返回结果没有“自动变 AC”。** reap 关闭的是物理生命周期，不会重新判题；若已有 response，就保留它。若管理器死在尚无 response 的阶段，清理后生成 EXECUTION_OWNER_LOST 平台响应。

因此 registry.COMPLETED 表示该登记已完成收尾，业务 submission_execution.COMPLETED 表示持久判定已完成，AC 又是其中一种用户判定。这三个词处于不同层。

此外，slot 数限制正在占用的物理执行，登记数上限 64 限制保留的 token 记录。已完成记录要过 deadline + 60 秒才由 collect 清除；“没有运行中的容器”并不必然意味着登记容量充足。

### 12. 多管理器与共享范围有什么限制

读 registry 构造时的配置校验、共享文件通道、锁获取、slot 日志、损坏处理与 collect。多个管理器共享容量要求同一 daemon、同一持久本地目录和一致策略；损坏登记保守处理，不随意释放容量。

不能删除活跃锁文件来“重置”；不能把这个池外推为任意多宿主机的全局调度。宿主断电恢复等也按证据边界表达。
