# 链路三：沙箱执行与资源回收

接[提交与判题链路](02-提交与判题链路.md)：判题服务已领取 S1，拿到代码、用例、执行凭证 T1 和期限。本篇按 **接收登记 → 编译运行 → 收集清理 → 故障恢复** 跟读；概念在对应方法之前解释，方法名只用于定位。

阅读场景是判题端 `type=remote`、沙箱端 `mode=isolated`（默认）。继续用求和程序 P、输入 `1 2` 和 `2 5` 推演；标识和输出均为教学假设。

## 1. 接收执行请求，登记本次运行

### 1.1 从判题服务进入沙箱服务

remote 表示通过 HTTP 调用沙箱，isolated 表示沙箱内部使用 Linux 容器执行，两者可以同时成立。判题端的 `CodeSandbox` 是调用抽象，由工厂选择 remote 客户端；服务端的 `CodeSandboxService` 则是 Controller 委托的执行能力。

请求包含语言、代码、输入列表、资源限制、T1 和绝对期限；响应返回实际输出、运行 outcome 和资源信息。标准输出留在判题服务比较，沙箱不负责判 AC。

执行入口使用 `auth` 请求头鉴权；它与业务服务的内部鉴权头、用户 Cookie 用途不同。HTTP 客户端限制调用并发、等待时间和响应大小，不会自动重试用户程序。

### 1.2 校验请求，先登记再运行

沙箱服务中的隔离执行组件是 `JavaIsolatedCodeSandbox`。它再次检查语言、代码与输入大小、用例数量和资源限制；题库材料合法，不代表执行端可以省略策略检查。

执行前还要知道：T1 是否处理过，是否有空闲物理名额，管理器重启后留下了什么。这些由持久登记组件 `DurableExecutionRegistry` 管理。它将 token 与完整请求摘要绑定，并占用一个 slot（沙箱物理并发名额），与判题 worker 的 Semaphore 不同。

隔离组件将“怎样编译运行”作为 Work 回调交给登记组件。传入回调不会立即执行：登记组件先校验身份、申请 slot、保存日志，才调用 Work。否则容器已经创建、登记尚未保存时管理器退出，后继管理器便缺少恢复依据。

每次占位保存 token 日志与 slot 日志。全局登记锁保护短暂的占位操作，slot 锁跟随本次物理占用；全局锁不包住整段用户运行。持久日志使管理器退出后仍能知道哪个名额未收尾。

**现在读：** [JavaIsolatedCodeSandbox.executeCode](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java) 和 valid → [DurableExecutionRegistry.execute](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java)。先跟首次合法请求：身份/期限、摘要、空位、两份日志、run。看到 Work 调用后，下一章进入实际编译运行。

## 2. 编译程序，逐个运行测试用例

### 2.1 编译一次，保存产物与入口

隔离组件的 `executeOnce` 负责编排一次编译和多次用例运行。它把源码写入 T1 的工作目录，创建源代码卷、编译产物卷和收据卷，再启动编译容器。

编译容器运行受信辅助程序 `NativeCompiler`，把源码编译成 class，并写出入口收据。收据包含本次随机 nonce，读取组件会核对格式与 nonce，避免把任意文本当成本次编译结论。用户语法错误可以形成 CE；编译预算或基础设施异常则是平台失败。 隔离组件先用 `trustedResult` 核验容器和监督器的执行证据，再由 `NativeReceipt` 核对带 nonce 的编译入口收据，两类结果不能混用。

`NativeCompiler` 名字中的 Native 不表示这里在宿主机执行用户代码：隔离组件把它放进编译容器运行。后续用例复用编译产物，不重新编译整份源码。

**现在读：** [JavaIsolatedCodeSandbox.executeOnce](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java) 从工作目录、源码写入，到卷/编译容器、upload/start、trustedResult 和入口收据；停在 inputList 循环前。编译细节定点看 [NativeCompiler](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/nativejava/NativeCompiler.java)、[NativeReceipt.read](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/nativejava/NativeReceipt.java)。

### 2.2 每个用例使用新的运行环境

编译结束后，执行器为每组输入创建新运行容器。编译产物只读挂载，可写空间不在用例间复用，避免上一个用例的文件、静态状态或残留进程污染下一个用例。

例如 case-0 输入 `1 2`，收集 `3`；case-1 使用新容器输入 `2 5`，收集 `7`。标准输入 stdin 传给程序，标准输出 stdout 作为待比较答案，标准错误 stderr 作为有限诊断。

隔离参数各管一类边界：

| 边界 | 当前控制 |
| --- | --- |
| 网络与权限 | 禁网、用户进程降至 UID/GID 10000、限制 capabilities |
| 文件 | 限定卷挂载、运行产物只读、临时目录与文件/描述符限制 |
| 资源 | cgroup 限制内存、CPU、PID；内存限制覆盖整个用例环境，不只 Java 堆 |
| 控制面 | 用户容器不挂 Docker socket、业务凭据或宿主业务目录 |

Docker 调用由沙箱管理器中的 `DockerIsolationEngine` 完成。它控制容器，并不把用户类加载到业务服务 JVM。用户 JVM 的入口由隔离辅助程序 `IsolatedLauncher` 调用。

**现在读：** 回 executeOnce 的 inputList 循环，跟 case 期限、收据卷、容器与输入；再读 [DockerIsolationEngine.create](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DockerIsolationEngine.java) 的挂载/身份/资源参数 → [DockerIsolationEngine.start](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DockerIsolationEngine.java)。程序入口定点看 [IsolatedLauncher](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/nativejava/IsolatedLauncher.java)。

### 2.3 同时处理标准流，让监督器控制期限

管理器要边写 stdin，边读 stdout、stderr。若先等待程序退出、再读输出，程序可能因输出管道写满而阻塞；若用户不读输入，写入方也可能阻塞。进程调用组件用三个 I/O 任务并发处理，并限制输出总量和等待时间。

容器内还运行受信监督器 `supervisor.py`。它计算阶段预算与绝对期限中的较早值，降权启动用户 JVM，等待退出或超时，再清理 namespace 内的后代进程，采集资源信息并写私有收据。用户打印 JSON 只能改变 stdout，不能代替受信控制结果。

三类数据各有生产者：用户 stdout/stderr 是答案与诊断，NativeCompiler 写编译入口收据，监督器写退出/超限/资源收据。分开这些通道，管理器才能区分用户输出和执行控制证据。

**现在读：** [BoundedProcessRunner.run](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/BoundedProcessRunner.java) 的三路 I/O、输出预算与 finally 清理；再读 [supervisor.py](../../codeoj-backend/codeoj-backend-codesandbox/isolation/supervisor.py) 的 unprivileged、main，跟期限、Popen、wait、后代清理及结果文件。容器边界和这些控制不能据此宣称绝对安全，实际验证范围见[隔离说明](../contest/isolated-sandbox.md)。

## 3. 收集运行结果，清理后返回

### 3.1 核验收据，汇总用例输出与资源

管理器不能仅凭“Docker 命令退出了”就相信用户程序正常结束。隔离组件的 `trustedResult` 结合调用结束方式、容器 OOM/运行状态和私有收据，确认结果来源，再由用例循环解释为 MLE、TLE、OUTPUT_LIMIT、RE 或 EXECUTED。未知执行状态按平台失败处理；正常执行缺必要指标也不能继续判 AC，但已有明确 OOM 或输出超限证据时，可以形成 MLE 或 OUTPUT_LIMIT，不要求先补齐正常执行指标。

多个用例的 time、memory 取观测最大值，而非求和。时间包含 JVM 启动；内存来自用例 cgroup，包含 JVM、监督器和后代。比如三个用例各耗时 1.5 秒，上报 time 约为单用例最大值，整次运行仍要容纳三个用例和编译开销。

**现在读：** [JavaIsolatedCodeSandbox.trustedResult](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java)，再回 executeOnce 的 end 分支、指标校验、outputs.add 与汇总返回。正常执行缺指标不能补成 0 继续判 AC。

### 3.2 确认物理对象删除，才归还名额

Work 返回后，控制回到持久登记组件的 `run`。它调用删除引擎，按池标签和 T1 删除容器、卷及工作目录，确认删除成功才把登记标为 COMPLETED、删除 slot 日志并返回响应。

COMPLETED 在这里表示执行登记已收尾，保存的响应可能是 EXECUTED，也可能是平台错误；它不等于题目服务中的判题完成，更不等于 AC。释放文件锁也不等于资源已删除，日志与物理对象必须一起收尾。

**现在读：** [DurableExecutionRegistry.run](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java) 的 Work 返回 → removeExecution → response/state 保存 → slot 日志删除；再读 [DockerIsolationEngine.removeExecution](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DockerIsolationEngine.java) 按池/token 过滤、删除与再次检查的过程。

沙箱正常响应回到判题端后，标准答案才参与比较。接回 [ReliableJudgeWorker.process](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/ReliableJudgeWorker.java) → [SandboxResultMapper.userVerdict](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/SandboxResultMapper.java) → [JavaLanguageJudgeStrategy.doJudge](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/strategy/JavaLanguageJudgeStrategy.java)：EXECUTED 继续比较答案，资源完整且两组输出匹配时才形成 AC。具体写回见[链路二](02-提交与判题链路.md)。

## 4. 管理器或网络出错后，怎样停止并恢复清理

### 4.1 区分调用超时、执行期限和数据库失权

HTTP 超时只表示客户端没有按时获得可信响应，远端可能仍在运行；用户 TLE 要有执行层的超限依据。客户端不会自动换 token 重跑，重新尝试由题目服务的恢复状态机安排。

| 期限 | 当前默认值或计算方式 | 负责什么 |
| --- | --- | --- |
| 数据库执行权 | 租约 15 秒，可续；一次尝试最多 60 秒，受总恢复期限约束 | 结果能否被题目服务接受，不负责删除容器 |
| 沙箱整次执行 | 到达时刻 + 30 秒，与请求绝对期限取较早值 | 编译及所有用例共用的预算 |
| 编译阶段 | 15 秒，仍受整次执行期限约束 | 编译阶段预算；耗尽不能一概算 CE |
| 单个用例 | 请求的 runTimeLimitMs，未给时回退 5 秒 | 当前用例的程序执行期限 |
| 客户端 HTTP | 连接 2 秒、读取 35 秒、总调用 38 秒 | 网络等待，不直接生成用户 TLE |

表中数据库租约和尝试期限是当前执行命令的固定规则；沙箱与 HTTP 阈值来自配置，表中列的是默认值。进入某用例前，剩余总预算不足 caseLimit + 250 毫秒时返回平台预算不足；valid 也拒绝超过沙箱配置上限的用例时限，不能假设所有题目限制都可执行。

**现在读：** executeOnce 的 deadline、compileDeadline、caseLimit、remaining；对照 RemoteCodeSandbox 的超时。监督器仍有独立期限，管理器消失后不会因为无人等待 HTTP 就无限保留用户进程。

### 4.2 重复请求如何回放，失联执行如何收尾

登记组件用 token 和请求摘要判断重复：同 T1、不同内容拒绝；同内容且已有响应则回放；原执行仍持有 slot 锁时等待，达到请求期限仍无结果则返回执行中。未找到旧记录的新请求，若期限已过则拒绝执行。

管理器被杀后，操作系统释放文件锁，slot/token 日志与 Docker 对象仍可能存在。后继管理器取得遗留 slot 锁，再按日志删除旧对象。已有响应保持原响应；若此前没有响应，清理后保存 EXECUTION_OWNER_LOST，不重跑旧 token。

恢复在沙箱启动时执行，也由隔离组件的定时任务每 3 秒触发；申请新 slot 前还会检查旧占用。删除失败则保留日志，不能把这个 slot 直接交给新执行。

**现在读：** [DurableExecutionRegistry.execute](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java) 的 existing 分支 → [DurableExecutionRegistry.recover](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/DurableExecutionRegistry.java) / reap；定时入口看 [JavaIsolatedCodeSandbox.recoverExecutions](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaIsolatedCodeSandbox.java)。

### 4.3 删除失败后，为什么继续占用名额

若 Work 已返回，物理删除却失败，`run` 保存 REAP_PENDING、保留 slot 日志，并返回 EXECUTION_CLEANUP_PENDING 平台响应。名额暂未释放，后续 recover/reap 重试删除；成功后登记转 COMPLETED，但原平台响应不改成运行成功。

把 registry 与题目服务状态分开看。假设 T1 仍有效、worker 未 lost、fail RPC 成功且预算充足：

| 时点 | 沙箱登记与物理名额 | 题目服务执行记录 |
| --- | --- | --- |
| Work 跑完，删除失败 | REAP_PENDING，slot 占用，保存平台响应 | 暂仍 RUNNING |
| worker 报告平台失败 | 仍待物理清理 | RETRY_WAIT，本次 attempt 为 FAILED |
| 后续物理删除成功 | COMPLETED，释放 slot，保留原平台响应 | 不因清理成功自动改变 |
| 业务恢复到期并允许重试 | 旧 T1 不重跑 | QUEUED、新派发事件；下次领取才产生新 token |

fail RPC 抛异常时不能把第二行当成已完成；明确拒绝则看数据库当前身份和状态，不能统一推断 NACK。物理收尾和业务恢复没有共同事务。

**现在读：** run 的 cleaned=false → reap；跨回题目服务看 [ExecutionCommands.fail](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java) 与 recover，确认物理清理不写业务判定。

### 4.4 多个管理器共享到哪里

共享容量要求同一 Docker daemon、同一持久本地状态目录及一致策略。登记组件构造时校验策略，文件锁与 slot 日志协调占用；损坏日志保守拒绝，不随意释放容量，也不能删除活跃锁文件来“重置”。这套池不能直接外推到多宿主全局调度。

物理 slots 与保留的 token 登记数又是两类限制：登记上限为 64，完成记录要过 deadline + 60 秒才由 collect 清除。因此没有运行容器，也可能暂时没有新的登记容量。

显式 `mode=native` 是可信样例模式，保留有界 I/O，但没有 isolated 的容器边界；隔离条件不足时拒绝启动，不自动降级。

**现在读：** registry 构造、gate/lock、read、collect。需要对照本机执行时，再看 [JavaNativeCodeSandbox.executeCode](../../codeoj-backend/codeoj-backend-codesandbox/src/main/java/com/codeoj/codeojbackendcodesandbox/service/impl/JavaNativeCodeSandbox.java)，用于理解编译文件和标准流；不要混入 isolated 主链。
