# 链路四：从发布比赛到确认资格与比赛提交

你已了解常见秒杀，本链沿“发布 → 预留 → 持久请求 → 确认资格 → 比赛提交”读当前实现。先讲正常流程，再解释相比常见秒杀新增的身份账本、未知恢复、修复与对账版本。


**本篇导航：** [全局](#全局位置赛事在可靠判题前增加上下文) → [机制与状态](#必要机制这里有两个分配阶段和两类-api) → [正常报名](#第一遍正常流程) → [恢复推演](#第二遍未知结果与恢复) → [检查理解](#阅读成果与测试)

## 全局位置：赛事在可靠判题前增加上下文

```text
管理员创建草稿 → 发布固定题目快照
用户报名 → Redis 原子预留 → 请求与 Outbox 同事务落库 → PROCESSING
  → MQ → 数据库确认资格 → 维护器同步 Redis 标记
用户在比赛窗口提交 → 检查当前账号/资格/快照 → 复用可靠受理
  → 链路二判题、链路三执行 → 链路五计分
```

报名消费者完成的是数据库确认；Redis 标记由维护器等协调路径同步，不能把它们读成一个跨 Redis/DB 事务。普通练习没有比赛资格和发布版本，比赛提交则带着这些上下文进入同一个判题底座。

| 对象 | 全局中的含义 |
| --- | --- |
| contest | 时间、容量、状态、管理版本、发布版本、报名模式 |
| contest_problem_snapshot | 发布时固定的题目内容与判题规格引用 |
| Redis reservation | 某用户已经预留一份名额的原身份 |
| contest_registration_request | 原报名请求及确认、回收、恢复状态 |
| contest_registration | 最终参赛资格 |
| submission_execution 比赛字段 | 判题事实属于哪场、哪道快照、哪个发布版本 |

表与迁移见 [V002](../../codeoj-backend/mysql-init/migrations/V002__contest_core.sql)、[V003](../../codeoj-backend/mysql-init/migrations/V003__async_registration.sql)、[V005](../../codeoj-backend/mysql-init/migrations/V005__registration_recovery_fence.sql)。

## 必要机制：这里有两个分配阶段和两类 API

### 页面接口与管理接口不是同一种能力

| 调用者 | 请求意图 | 后端入口 |
| --- | --- | --- |
| 参赛用户 | 发起/查询本人报名 | ContestController 的 registrations 接口 |
| 参赛用户 | 在比赛窗口提交代码 | ContestController 的 submissions 接口 |
| 管理员 | 准备 Redis 模式、关闸对账 | RegistrationAdminController 的 prepare / reconcile |
| 管理员 | 明确继续或终止未决请求 | RegistrationAdminController 的 requests/id/review |

源码：[ContestController](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestController.java)、[RegistrationAdminController](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationAdminController.java)。

公开路径经 Gateway 重写到题目服务，Controller 内路径还要加 /api/question context-path。

**管理接口不是服务内部接口的同义词。** 这里管理员仍来自当前登录用户；不是拿一个内部密钥就能跳过角色和管理版本检查。

### 为什么 Redis 预留不能直接成为参赛资格

| 阶段 | 保证什么 | 不能保证什么 |
| --- | --- | --- |
| Redis 预留 | 在当前账本中占住一份名额，保存原身份 | 不表示关系库资格已生成 |
| DB 保存请求 | 受理身份与确认事件已经持久化 | 不表示消费者已执行确认 |
| DB 确认资格 | 条件扣容量、唯一资格与请求状态一起更新 | 不表示 Redis 标记已同步 |
| 标记同步 | 两侧处理状态收敛 | 不替代比赛提交时的重新检查 |

这是异步协调的中间状态，不是一个跨 Redis/MySQL 的 ACID 事务。PROCESSING 让用户看到“已受理但待确认”，不是糊成成功或失败。

### 当前版本字段各保护什么

| 字段 | 用途 | 典型检查 |
| --- | --- | --- |
| publishedVersion | 固定本场题目发布内容 | 提交不能指向其他发布版本 |
| registrationEpoch | 区分本场 Redis 账本代次 | 原预留不能跨代次混入新账本 |
| contest.version / revision | 给一次管理操作排序 | 旧对账不能覆盖更新状态 |
| request.stateVersion | 控制单请求管理处理 | 旧页面不能终止已变化的请求 |
| reservationSequence | 为账本身份分配可持久核验的序号 | 旧快照不能重用已持久序号绑定新人 |

不要把它们统称“乐观锁”就结束：有的表示内容，有的表示管理次序，有的表示账本身份。

### 同一场比赛有几组状态，不能只盯一个 CONFIRMED

| 状态轴 | 典型字段 | 回答的问题 |
| --- | --- | --- |
| 比赛持久状态 | contest.status | 草稿、已发布、收敛中、已结束还是取消 |
| 当前时间阶段 | 响应 phase | 当前处于报名前、报名中、等待开赛还是比赛中 |
| 报名通道 | registrationMode、registrationReady、issue | 当前 DB/Redis 路径是否可以接受新请求 |
| 某次请求 | request.status、reclaimState | 请求有没有确认，Redis 标记/释放有没有收尾 |
| 用户资格 | qualificationValid | 持久资格结合当前比赛状态是否仍有效 |

打开 [ContestTransactions.view](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java) 看 phase 的计算，再看 registrationView 对 qualificationValid 的组合判断。phase 是按数据库当前时间派生的；例如比赛刚到结束时间，页面可以显示 FINALIZING，而持久 status 还在等待 finalizeIfDue 推进。

confirmed 请求与资格记录在取消后仍可作为历史保留，但 qualificationValid 会失效。反过来，资格有效也不表示“现在可提交”：还需处在比赛提交窗口、发布版本匹配、快照归属正确且当前账号有效。

#### 用一条时间轴理解接口门槛

下面时间均为教学示例的同一天 UTC：报名 09:50–10:00，比赛 10:10–10:40；左闭右开。

| 数据库时间 | PUBLISHED 时计算出的 phase | 新报名 | 新比赛提交 |
| --- | --- | --- | --- |
| 09:49 | BEFORE_REGISTRATION | 不可 | 不可 |
| 09:55 | REGISTRATION_OPEN | 通道健康且有容量才可 | 不可 |
| 10:05 | WAITING_START | 不可 | 不可 |
| 10:20 | RUNNING | 不可 | 已确认资格等条件满足才可 |
| 10:40 | FINALIZING | 不可 | 不可；已受理提交继续判题与计分 |

注意：09:59:58 已合法预留的原请求，在 10:00:01 才消费时，不等同于 10:00:01 新发起报名。confirm 检查原身份、请求状态、有效期限和当前比赛条件，不能简单拿消费时刻重复套“新报名窗口”。这也不意味着可以无限延期；恢复预算、取消与通道异常仍会阻止确认。

### Java 是怎样调用 Lua 的

先读 [RedisRegistrationLedger](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RedisRegistrationLedger.java) 的构造方法、keys、call，再进入 reserve。

它们承担不同的桥接职责：

| 位置 | 作用 | 需要看懂的数据 |
| --- | --- | --- |
| 构造方法 | 从 classpath 加载脚本并声明 String 返回类型 | lua/contest-registration.lua |
| keys | 为本场构造固定顺序的 5 个 key | meta、stock、users、ledger、pending |
| call | 通过 StringRedisTemplate 执行脚本，解析 JSON 与业务码 | 操作名、参数列表、code/reservation |
| reserve / finish / repair 等方法 | 为具体操作按约定组装参数 | 哪些身份与时间传给哪种操作 |

Lua 中 KEYS 是 key 列表，ARGV 是参数列表。ARGV 第一项决定 reserve/finish/repair 等分支，其余参数含版本、用户、原事件与时间。

**为什么不能随意改列表顺序？** Java 包装层和 Lua 按位置解释同一份协议。读 reserve 时，先把 Java 每个参数和 Lua 的 ARGV 位置对上，再读脚本判断。

hash tag 中的比赛 ID 让相关 key 属于同一逻辑槽位，但这只是 key 设计；当前本机证据不因此变成 Redis Cluster 验收。脚本会阻塞执行期间的其他活动，所以也要保留工作量边界。

机制参见 [Redis Lua 说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

### 5. 数据库保存请求与待确认事件

**先认识本步方法：**

| [persist](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)<br>RegistrationTransactions | 将原 Redis 身份变成 DB 请求和事件 | RegistrationReservation → RegistrationRequest |

**阅读范围：** 从原身份与上下文核验读到状态选择、请求 INSERT 和 event；第一遍沿账号有效、窗口合法、预算内的 PROCESSING 路径。

事务保存 request 与 REGISTRATION_CONFIRM Outbox。恢复期限以原预留时间为基准，不因晚补建就重新获得一整段自动预算。若已有同身份记录，则核对后回读，不能只按数量忽略身份差异。

协调层拿到持久请求后返回本人报名视图，此时正常是 PROCESSING。Redis 预留与 DB 持久化之间没有共同事务，这个空窗要靠原身份与恢复路径收敛。

### 预留后为什么仍需要关系库约束

| 控制 | 防什么问题 | 读哪个位置 |
| --- | --- | --- |
| 比赛行锁 | 确认、取消、提交竞争同场状态 | ContestTransactions.load 的 lock 参数 |
| 条件更新 | 容量不足时不能继续扣减 | confirmRegistration 的 remainingCapacity 条件 |
| 唯一约束 | 同一人或原请求不能重复生成资格 | V002 的 request / registration 索引 |
| 同事务 | 扣容量成功但资格没保存时回滚 | confirmRegistration 的调用事务 |

Redis 提前挡住大量无效准入，DB 仍要核对最终业务事实。不能因为 Lua 成功就去掉数据库防线，也不能用 DB 余量重新卖出已经在途预留的名额。

## 第二遍：未知结果与恢复

### 9. 两个名额为什么会有两种剩余数字

总容量 2，A Redis 预留未落 DB，B 已确认：Redis stock=0，DB remainingCapacity=1，页面已确认 1/2。C 不能看到 DB 的 1 就再抢一次，因为它已被 A 的在途预留占用。

A 的恢复应以原 request/event/key 补建，再确认 DB 容量。MySQL 条件扣减与唯一资格仍是最终防线；Redis 的高速预留不能替代它们。

### mutation 是恢复意图，不是自动事务回滚

| 时刻 | 已保存的东西 | 恢复时怎么判断 |
| --- | --- | --- |
| 复合变更之前 | 原身份、原 stock/计数、目标状态 | 知道本次操作打算完成什么 |
| 变更做到一半 | 某些值已改变，mutation 仍在 | 检查观测值是否属于允许的前/后值 |
| 确认完成 | 全部目标值到位、清除 mutation | 后续按已完成结果继续 |

repair 不凭“出现异常”推断该退库，而是把允许的中间状态推进到**确定目标值**。

Lua 原子执行与 MySQL 异常回滚的语义不同，参见 [Redis 的回滚解释](https://redis.io/blog/you-dont-need-transaction-rollbacks-in-redis/)。

### 将库存例子继续读到每个恢复动作

沿用容量 2 的例子：A 占了一份 Redis 名额但 DB 尚无请求，B 已完整确认。此时 stock=0、remainingCapacity=1。

| 恢复步骤 | 读哪个对象 | 正确动作 | 为什么不能另造请求 |
| --- | --- | --- | --- |
| maintain 扫到 A 的原预留 | Redis 账本的原 request/event/key、epoch、sequence | persist 补建对应 DB 请求和原待确认事件 | 新 key 会破坏这份在途预留的身份 |
| confirm 处理 A | DB 请求与比赛锁 | 原请求确认一次，DB remainingCapacity 1→0 | 不能再次扣 Redis，因为已预留 |
| synchronize 收尾 | DB CONFIRMED 与原 Redis 身份 | finish 标记 CONFIRMED，移除 pending，再更新 DB 同步标记 | 确认不是释放，stock 仍为 0 |
| 同一事件再次到达 | 已 CONFIRMED 的请求 | 识别已处理，不再次扣容量 | 消息重投并不代表又一位用户 |

对照 [RegistrationMaintenance.maintain](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationMaintenance.java) 的 persist/recover/synchronize 调用，再回 [RegistrationTransactions.confirm](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。辅助方法读完后，应能回到这张表判断“现在补的是落库、资格，还是同步标记”。

如果 Lua 在 stock 已从 2 改成 1 后报错，而 mutation 还在，repair 要把该次动作的目标值补齐为 1，而不是再减成 0。这里依靠原身份、原值与目标动作恢复，不能把“再执行一次扣减”当幂等。

### 11. 预留未落库、确认未到、同步失败各由谁处理

回到 RegistrationMaintenance.maintain、RegistrationTransactions.recover、RegistrationService.synchronize。

| 故障窗口 | 恢复依据 |
| --- | --- |
| Lua 响应丢失 | repair + 原用户映射回查 |
| 预留已保存，DB 未写 | pending 身份补建原 request 与 Outbox |
| 发布已确认，但没有资格确认 | 原事件在有限预算内继续发布/确认 |
| DB 已确认，Redis 标记失败 | 重放 CONFIRMED，不退款 |
| DB 已失败/取消，释放失败 | 按原身份重放 RELEASED，不重复退 |
| 自动次数/期限耗尽 | MANUAL_REVIEW，管理员明确决定继续或终止 |

status 与 reclaimState 是两条轴。例如 FAILED/RELEASE_PENDING 表示已决定失败但物理名额尚未收回。不能只看一个状态就认定可以最终结算。
