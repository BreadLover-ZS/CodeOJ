# 链路四：赛事报名与参赛

本篇按 **发布比赛 → 接收报名 → 确认资格 → 比赛提交** 跟读源码，再看故障恢复。每段先解释当前步骤需要的概念，介绍负责它的组件，再给方法定位。

沿用教学例子：管理员把公共题目 42 发布为比赛 99 的题 A；用户 7 报名后，在比赛窗口提交程序，形成新的比赛提交 S2。可靠判题开启，本场报名以已准备好的 Redis 模式为主；全局报名开关 `codeoj.registration.enabled` 默认关闭，单场仍有 DB_SYNC 分支。

## 1. 发布比赛，准备报名通道

### 1.1 从可编辑草稿生成固定比赛内容

草稿包含报名窗口、比赛窗口、容量和题目。`PUBLIC_TRAINING` 只选公共题库 ID，发布时复制源题；`PRIVATE` 直接提供私有题干、限制和用例。发布后参赛者应使用同一版题目，不能因管理员后来改题库而改变判题依据。

题目服务的 `ContestController` 接收页面请求，赛事事务组件 `ContestTransactions` 负责草稿校验、当前管理员检查和发布。`expectedVersion` 是管理页面读到的版本，更新时必须仍匹配，防止旧页面覆盖新状态。

发布事务复制题干为 `contest_problem_snapshot`，调用可靠受理组件保存固定判题规格，并记录 `publishedVersion`。`problemSnapshotId` 表示本场哪道题，发布版本表示哪版内容，规格摘要表示具体用例与限制；三者用途不同。普通练习在受理时固定规则，比赛在发布时固定。

### 1.2 确定本场使用哪一种报名路径

全局开关打开不会自动把每场比赛改成 Redis 分配。`registrationMode` 决定本场路径：

| 模式 | 如何生成资格 | 适用的阅读分支 |
| --- | --- | --- |
| DB_SYNC | 在一个 MySQL 事务里创建请求、扣容量、生成资格 | 直接跟赛事事务中的 register、confirmRegistration |
| REDIS_READY | 先在 Redis 预留，再持久请求，后台确认 MySQL 资格 | 本篇第二章主线 |
| REDIS_PAUSED / REDIS_RECONCILING | 暂停新准入，等待准备或对账完成 | 第四章恢复与管理分支 |

Redis 在资格事务前拦住无库存和重复占位，但每份最终资格仍要落库，也仍会争用比赛行锁。代价是出现 Redis 与数据库之间的空窗，需要保存原身份和恢复状态；它不是数据库失败时可随意切换的透明降级。

切换由报名协调组件 `RegistrationService` 发起，数据库状态变更由报名事务组件 `RegistrationTransactions` 执行。管理员先暂停并建立账本代次，再关闸初始化、对账，成功后恢复 ready。`registrationEpoch` 区分哪一代账本；`contest.version`（协调中称 revision）标识哪次管理操作。后续 Redis 操作和数据库提交都带这些条件，避免旧操作作用于新状态。

## 2. 接收报名，确认参赛资格

本章跟已就绪的 Redis 路径。**预留名额、保存请求、确认资格、同步标记是四个时点**，没有一个事务跨越 Redis、MySQL 和 MQ。

### 2.1 用原请求身份发起报名

报名也需要幂等 key：响应丢失后沿用原 key，后端才能继续原请求。本项目一场比赛同一用户已有请求时，要求原 key 并回读；换 key 不会再获得一个名额。当前账号仍由后端检查。

公开入口 `ContestController.register` 取得用户和 header key，再交给协调组件 `RegistrationService.register`。后者先回读已有数据库请求，Redis 路径才继续核查账本及预留。

**现在读：** [ContestDetailView.vue](../../codeoj-frontend/src/views/contest/ContestDetailView.vue) 的 load/register → [api/contest.ts](../../codeoj-frontend/src/api/contest.ts) 的 stableKey、contestRequest → [ContestController.register](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestController.java)。再进入 [RegistrationService.register](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)，先读原请求回读和分支选择，停在账本操作处。

### 2.2 预留一份名额，同时保存可恢复的身份

Redis 适配组件 `RedisRegistrationLedger` 负责调用 Lua：Java 把命令、key 和参数交给 `StringRedisTemplate.execute`，Redis 执行脚本，再将 JSON 结果转换为预留对象。Java 的参数顺序和 Lua 的 KEYS/ARGV 必须一致。

脚本检查窗口、闸门、库存和用户映射，成功时不仅减库存，还保存这次预留的完整身份：比赛、发布版本、账本代次、用户、requestId、eventId、key、内容摘要、原预留时间及 sequence。sequence 是本代账本的稳定序号，后续落库保存它，便于发现旧快照和身份重绑。脚本用 Redis TIME 取原预留时间，并与数据库观测时间比较；偏差超限会关闸，避免继续用不可信时间判定窗口。

| 同场 Redis key | 保存什么 |
| --- | --- |
| meta Hash | 发布/账本/管理版本、闸门、窗口、计数与 mutation 意图 |
| stock String | 当前仍可预留的名额 |
| users Hash | 用户 → 原 eventId，防重复占位 |
| ledger Hash | eventId → 完整身份与当前账本状态 |
| pending ZSet | 待落库或待同步的身份 |

这些 key 使用同一比赛 hash tag。脚本执行时不被其他命令穿插，但运行时报错不会回滚之前的写入；因此复合变更前先保存 `mutation` 意图，供后续按原身份和目标值修复，第四章展开失败例子。

**现在读：** [RegistrationService.register](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) 中的 ledger.repair/check → ledger.user → gateOpen → reserve；再读 [RedisRegistrationLedger.reserve](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RedisRegistrationLedger.java) 及 keys、call，进入 [contest-registration.lua](../../codeoj-backend/codeoj-backend-question-service/src/main/resources/lua/contest-registration.lua) 的 user、reserve 分支。核对传入的版本、时间与序号高水位，再看原身份如何生成和保存。

### 2.3 将原预留保存成数据库请求和确认事件

`RegistrationReservation` 表示 Redis 原预留，`RegistrationRequest` 表示 MySQL 已保存的请求。它们都还不是 `contest_registration` 中的最终资格。

协调组件拿到预留后，调用数据库事务组件 `RegistrationTransactions.persist`：先核对原身份、发布/账本上下文和账号，再保存请求与 REGISTRATION_CONFIRM Outbox。正常状态为 PROCESSING（等待确认），`reclaimState=RESERVED` 表示 Redis 名额仍待收尾。

这两个状态字段分别回答“业务请求到哪一步”和“Redis 标记/释放是否完成”。确认期限从原预留时间起算，晚补建不能重新获得一整段恢复预算。证据非法、取消、账号失效或期限耗尽时，persist 也可能建立人工核查或失败状态，不能认为补建必然成功。

**现在读：** [RegistrationService.persist](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) → [RegistrationTransactions.persist](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。跟上下文与 same 身份检查、原 reservedAt、状态选择、请求 INSERT、event 写入，再按原路返回本人报名视图。这里保存了请求与通知，尚未生成资格。

### 2.4 消费通知，在 MySQL 中确认资格

请求持久化后，报名发布组件 `RegistrationMessaging.Relay` 周期扫描 REGISTRATION_CONFIRM，复用 Outbox 发布器发送到报名队列。消费者 `RegistrationConsumer` 收到通知，再交给 `RegistrationTransactions.confirm` 决定是否确认。

确认事务先锁比赛，再核对事件和请求身份、账号、请求状态及期限。有效请求才进入赛事组件的 `confirmRegistration`：条件扣减 `remainingCapacity>0` 的数据库容量，插入唯一资格，将请求改为 CONFIRMED。重复事件识别已处理请求，不重复扣容量。

比赛行锁协调同场操作，条件更新防止容量不足时继续扣减，唯一约束防止重复资格，同事务保证容量与资格一起提交。Redis 提前预留不能代替这些数据库条件。

### 2.5 同步确认标记，查询本人状态

数据库已确认后，协调组件的 `synchronize` 才把原 Redis 账本标为 CONFIRMED，移出 pending，再将数据库 `reclaimState` 更新为 COMPLETE。**这是确认标记，不是释放名额**，Redis stock 不增加。

同步通常由后台维护组件 `RegistrationMaintenance` 接手：Spring 每轮调度 tick，按场次执行 maintain，检查账本、补建缺失请求、恢复到期动作并同步终态。它调用 persist 只会补请求和事件，PROCESSING 时 synchronize 不会替消费者确认资格。

**现在读：** [RegistrationMaintenance.tick](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationMaintenance.java) → [RegistrationMaintenance.maintain](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationMaintenance.java)，先跟已有 CONFIRMED 请求的同步；再读 [RegistrationService.synchronize](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) 的 CONFIRMED 分支 → ledger.finish → [RegistrationTransactions.marked](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。

## 3. 取得资格后，提交比赛程序

### 3.1 区分报名成功、当前可参赛和可提交时点

CONFIRMED 表示数据库有资格，但提交还受当前比赛、账号、ready 和时间限制。`ContestTransactions` 根据数据库时间派生页面 phase；phase 与持久 status 不是同一个字段。

例如报名 09:50–10:00、比赛 10:10–10:40（教学 UTC，左闭右开）：09:55 可报名但不可提交；10:05 已关闭报名、尚未开赛；10:20 有资格才可提交；10:40 不再接收新提交，已受理任务继续判题。

合法预留在报名结束后才被消费，不等于结束后新发报名：确认要看原预留证据和恢复期限。取消后已确认历史可保留，但不能继续作为有效比赛使用。

**现在读：** [ContestTransactions.view](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java) 的 phase 计算、registrationView 的 qualificationValid，再跟 detail 的题目可见性。准备就绪标记、已确认资格和 RUNNING 时间阶段分别检查，不能只看其中一个。

### 3.2 校验本场快照，接回可靠判题

比赛程序请求 `ContestSubmission` 携带 problemSnapshotId、publishedVersion、语言、代码和 key。报名 key 标识报名请求，这里的 key 标识一次代码提交；受理后产生新的 S2，普通练习 S1 不会自动转成比赛提交。

公开入口 `ContestController.submit` 委托协调组件 `ContestService`，再进入 `ContestTransactions.submit`。事务依次处理同 key 回放、当前账号、已确认资格、PUBLISHED/ready、发布版本、快照归属与比赛窗口；通过后复用可靠受理组件的 write 保存代码和执行记录，并附上 contestId、快照及发布版本。

后续 MQ、worker、沙箱复用[提交判题链路](02-提交与判题链路.md)与[沙箱链路](03-沙箱执行与回收链路.md)，比赛结果交给[榜单链路](05-成绩榜单与结算链路.md)。

页面 pending 在当前内存中保留原 body/key，未知响应后重试原内容；sessionStorage 只留指纹/key，不存源码，刷新不能只凭 key 恢复丢失的程序。

**现在读：** [ContestDetailView.vue](../../codeoj-frontend/src/views/contest/ContestDetailView.vue) 的 submit/sendPending → [ContestController.submit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestController.java) → [ContestService.submit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestService.java) → [ContestTransactions.submit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)。看事务外重试与冲突回读，再按事务内检查顺序跟到 SubmissionAcceptance.write；不重读链路二的全部判题实现。

## 4. 结果未知或状态不一致时，沿原身份恢复

### 4.1 修复中途写入，先判断原操作发生了什么

Lua 的原子执行只阻止命令穿插，不提供异常回滚。假设原 stock=2、预留目标=1，已写为 1 后脚本报错：找不到完整用户映射，也不能证明没有扣库存。

脚本在复合写前保存 mutation，包含原身份、原库存/计数和目标状态。repair 校验当前值属于允许的前/后状态，再补齐确定目标值 1，不会重复扣成 0；释放也写确定目标，避免重复加库。证据矛盾则暂停核查，不重置库存掩盖问题。

协调组件的 `recoverUnknown` 在响应未知后先 repair/check，再按用户查原身份，匹配原 key 与内容摘要后补落库。

**现在读：** [RegistrationService.recoverUnknown](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) → [contest-registration.lua](../../codeoj-backend/codeoj-backend-question-service/src/main/resources/lua/contest-registration.lua) 的 apply、repair；对照每个写入前保存的意图和允许中间值，再回 register 的 unknown catch。

### 4.2 分清补建请求、确认资格和同步标记

容量 2，A 已占 Redis 名额但未落 DB，B 已确认：Redis stock=0，DB remainingCapacity=1，页面显示已确认 1/2。C 不能用数据库的 1 再抢，因为这份容量已被 A 的在途预留占用。

假设原身份/版本有效、账号正常、比赛未取消、通道可用且预算充足，后台按下列步骤继续 A：

| 完成的步骤 | 请求 status / reclaimState | 资格和后续动作 |
| --- | --- | --- |
| maintain 找到原预留，persist 补建 | PROCESSING / RESERVED | 资格仍为 0；原确认事件等待 Relay 发布 |
| Consumer 经 confirmRegistration 确认 | CONFIRMED / RESERVED | 资格为 1；DB remainingCapacity 从 1 到 0 |
| synchronize 完成 Redis 标记 | CONFIRMED / COMPLETE | 资格仍为 1，stock 仍为 0，不退款 |

维护器不会在一次 persist → synchronize 中直接完成资格确认。若事件已被 Broker 确认却迟迟未生成资格，recover 可按预算重开原事件，再经 Relay、Consumer 继续。

**现在读：** [RegistrationMaintenance.maintain](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationMaintenance.java) 的两轮扫描 → [RegistrationTransactions.recover](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java) → RegistrationMessaging.Relay.tick → RegistrationConsumer.receive。核对补建沿用原 requestId/eventId/key，恢复不再扣一次 Redis。

### 4.3 先持久终态，再释放；确认后只补标记

超时是结果未知，不能统一退款。明确失败或取消先在数据库保存可回收终态，再由 synchronize 按原身份释放，最后记 RELEASED。CONFIRMED 请求同步失败只补确认标记，不释放，也不重复扣数据库容量。

自动期限或发布预算耗尽转 MANUAL_REVIEW，保留未决预留；它表示等待管理员决定，不代表后台已确认失败。管理命令还要核对请求 `stateVersion`，防止旧页面覆盖更新结果。

管理员 `CONTINUE` 只继续原请求/原事件，并要求有效的有限预算；`FAIL` 只允许终止 PROCESSING/MANUAL_REVIEW，不能把已确认资格退成可售库存。比赛取消会停止新准入和新提交，已确认历史保留。

**现在读：** [RegistrationTransactions.recover](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)、[RegistrationTransactions.review](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)，再看 [RegistrationService.synchronize](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) 的终态释放分支与 marked。状态迁移同时观察 status、reclaimState，不能把 FAILED/RELEASE_PENDING 当作已经释放完成。

### 4.4 关闸核验完整身份，防止旧快照重新分配容量

Redis 丢了 B、又出现 C，条数可能仍与 DB 相等，所以对账不能只比数量。必须核对原 request/event/key、用户、发布版本、账本代次、预留时间、sequence 和状态，再核验资格与容量关系。

事务组件的 settings 返回已落库 sequence 高水位；Lua check/gate 用它发现账本回退。[V005](../../codeoj-backend/mysql-init/migrations/V005__registration_recovery_fence.sql) 还以“比赛 + epoch + sequence”唯一约束防止已持久序号重绑新人。高水位不能证明所有未落库身份都安全，因此不能只按 DB 余量覆盖 Redis 库存。

对账先关闸，再扫描完整 ledger 与用户映射，补落原身份、同步已有终态，最后锁比赛核验并恢复 ready。旧格式必须在关闸和完整身份/容量核验后分配稳定序号再升级。当前容量和累计账本都限 10000；已释放身份也占累计账本，不能随意删幂等记录换取无限准入。

**现在读：** [RegistrationService.reconcile](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) → [RegistrationTransactions.beginReconcile](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java) → [RedisRegistrationLedger.snapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RedisRegistrationLedger.java) → [RegistrationTransactions.verifySnapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java) / [RegistrationTransactions.finishReconcile](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。旧格式分支看 assignLegacySequences、ledger.upgrade；检查关闸、逐条身份和两套容量公式。

### 4.5 让迟到的旧管理操作失效

一次对账持有自己的 epoch/revision。假如 R10 的 Redis 操作晚报错，R11 已恢复成功，R10 不能再读取最新 revision，借 R11 的身份将通道暂停。

协调组件在本次操作中保存 ownedRevision，事务组件的 `issueIfCurrent` 只在原 epoch/revision 仍是当前版本时记问题和暂停。成功后返回的新版本也只用于本次后续操作；这仍是带条件的协调，不是跨 Redis/DB 事务。

**现在读：** [RegistrationService.reconcile](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java) 的 beginReconcile、ownedRevision、finishReconcile、catch → [RegistrationTransactions.issueIfCurrent](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。操作边界继续见[报名恢复](../contest/registration-recovery.md)。
