# 链路四：从发布比赛到确认资格与比赛提交

你已了解常见秒杀，本链沿“发布 → 预留 → 持久请求 → 确认资格 → 比赛提交”读当前实现。先讲正常流程，再解释相比常见秒杀新增的身份账本、未知恢复、修复与对账版本。

## 全局位置：赛事在可靠判题前增加上下文

```text
管理员创建草稿 → 发布固定题目快照
用户报名 → Redis 原子预留 → 请求与 Outbox 同事务落库 → PROCESSING
  → MQ → 数据库确认资格 → 维护器同步 Redis 标记
用户在比赛窗口提交 → 检查当前账号/资格/快照 → 复用可靠受理
  → 链路二判题、链路三执行 → 链路五计分
```

报名消费者完成的是数据库确认；Redis 标记由维护器等协调路径同步，不能把它们读成一个跨 Redis/DB 事务。普通练习没有比赛资格和发布版本，比赛提交则带着这些上下文进入同一个判题底座。

| 对象 | 全局中的含义 |
| --- | --- |
| contest | 时间、容量、状态、管理版本、发布版本、报名模式 |
| contest_problem_snapshot | 发布时固定的题目内容与判题规格引用 |
| Redis reservation | 某用户已经预留一份名额的原身份 |
| contest_registration_request | 原报名请求及确认、回收、恢复状态 |
| contest_registration | 最终参赛资格 |
| submission_execution 比赛字段 | 判题事实属于哪场、哪道快照、哪个发布版本 |

表与迁移见 [V002](../../codeoj-backend/mysql-init/migrations/V002__contest_core.sql)、[V003](../../codeoj-backend/mysql-init/migrations/V003__async_registration.sql)、[V005](../../codeoj-backend/mysql-init/migrations/V005__registration_recovery_fence.sql)。

## 第一遍：正常流程

### 1. 从管理页面创建草稿并发布

源码：[ManageContestsView.vue](../../codeoj-frontend/src/views/contest/ManageContestsView.vue) → [ContestController.create/update/publish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestController.java) → [ContestTransactions.create/update/publish](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)。

**阅读范围：** 页面读提交草稿/发布请求，Controller 看用户解析与委托；事务层先读 validate、expected，再读发布时生成快照与状态更新。

草稿包含报名窗口、比赛窗口、容量、题目与类型。validate 要求时间顺序与题目合法，expected 控制旧管理页面不能覆盖新结果，当前管理员在事务里检查。

PUBLIC_TRAINING 草稿只选公共题库 ID，发布时复制源题；PRIVATE 直接提供私有题干、限制和用例，不关联公共源题。publish 调用 freezeSpec，保存题干快照与规格引用，固定 publishedVersion。

**回到全局：** 题库管理员以后改源题，已发布比赛仍引用自己的快照。题目快照固定时点是发布，普通练习规格固定时点是受理。

### 2. 先分清本场报名走 DB 还是 Redis

源码：[RegistrationService.register](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)。

**阅读范围：** 先读 byUser 回读与 c.mode 分流，再看 DB_SYNC 分支和 Redis settings；第一遍沿已准备就绪的 Redis 模式。

单场 DB_SYNC 会进入 [ContestTransactions.register/confirmRegistration](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)，在数据库事务内创建请求并确认资格。全局异步报名开关打开，不表示所有场次自动改成 Redis 分配。

管理员 prepare/reconcile 通过 [RegistrationAdminController](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationAdminController.java)、[RegistrationTransactions.prepare/beginReconcile/finishReconcile](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java) 切换本场，状态可为 REDIS_PAUSED、REDIS_RECONCILING、REDIS_READY。首次准备以已确认资格与当前 DB 余量核验后初始化，不能让旧 DB 分配器与 Redis 分配器并行分配同一容量。

### 3. 页面使用稳定 key 发起报名

源码：[ContestDetailView.vue](../../codeoj-frontend/src/views/contest/ContestDetailView.vue) 的 load/register、[api/contest.ts](../../codeoj-frontend/src/api/contest.ts) 的 stableKey/contestRequest、[ContestController.register](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestController.java)。

**阅读范围：** 查本场详情和本人状态，再跟 POST registrations 的 key、响应和后续刷新，不读样式。

客户端保留原请求身份，后端先检查当前账号和 key。已存在原请求时要求原 key 并回读；不会因为多点一次按钮就换一个资格。PROCESSING 表示确认中，CONFIRMED 才能作为提交资格。

### 4. Redis Lua 预留名额并保存原身份

源码：[RegistrationService.register](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)。

**阅读范围：** 读 ledger.repair/check、ledger.user、gateOpen、reserve 和 persist；再进入 RedisRegistrationLedger。

源码：[RedisRegistrationLedger.reserve](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RedisRegistrationLedger.java)。

**阅读范围：** 对照 keys 和 call，核对比赛/发布/账本版本、用户、requestId、eventId、key、hash 与数据库观测时间怎样送入脚本。

源码：[contest-registration.lua](../../codeoj-backend/codeoj-backend-question-service/src/main/resources/lua/contest-registration.lua)，先读 reserve、user；第一遍把 apply 看成一次完成写入，repair 留到第二遍。

| Redis 结构 | 保存什么 |
| --- | --- |
| meta Hash | 版本、闸门、窗口、计数与 mutation 意图 |
| stock String | 当前可预留库存 |
| users Hash | 用户 ID → 原 eventId |
| ledger Hash | eventId → 完整预留身份与状态 |
| pending ZSet | 待检查或标记同步的身份 |

五个 key 使用同一 hash tag。reserve 检查类型/完整性、版本、窗口、库存与用户映射，生成带原预留时间和 sequence 的记录。保存的不只是“库存减 1”，还有后续可以重建同一次请求的身份。

### 5. 数据库保存请求与待确认事件

源码：[RegistrationTransactions.persist](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。

**阅读范围：** 从原身份与上下文核验读到状态选择、请求 INSERT 和 event；第一遍沿账号有效、窗口合法、预算内的 PROCESSING 路径。

事务保存 request 与 REGISTRATION_CONFIRM Outbox。恢复期限以原预留时间为基准，不因晚补建就重新获得一整段自动预算。若已有同身份记录，则核对后回读，不能只按数量忽略身份差异。

协调层拿到持久请求后返回本人报名视图，此时正常是 PROCESSING。Redis 预留与 DB 持久化之间没有共同事务，这个空窗要靠原身份与恢复路径收敛。

### 6. MQ 消费后，由 MySQL 确认资格

源码：[RegistrationMessaging](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationMessaging.java) → [RegistrationConsumer.receive](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationConsumer.java) → [RegistrationTransactions.confirm](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java) → [ContestTransactions.confirmRegistration](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)。

**阅读范围：** Messaging 看事件类型与路由；Consumer 看解析、confirm 与 ACK；事务看事件身份、当前账号、请求状态、期限及最终确认方法。

confirmRegistration 在比赛锁与事务中检查请求归属，条件扣减 remainingCapacity 大于 0 的容量，插入唯一资格并更新请求。重复确认已处理身份不能再扣一次。

Consumer 确认数据库处理后 ACK。这里只确认资格事实，不能从 ACK 推断 Redis 标记已经同步，也不能从发布 Confirm 推断此事务已执行。

### 7. 维护器同步标记，页面查询确认资格

源码：[RegistrationMaintenance.maintain](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationMaintenance.java)。

**阅读范围：** 先读 settings、账本检查和待处理扫描，再跟 service.persist/recover/synchronize；第一遍看已有 DB 确认、Redis 未标记的路径。

源码：[RegistrationService.synchronize](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)。

**阅读范围：** 看 CONFIRMED 对应 ledger.finish 与 marked；明确调用发生在持久 DB 状态之后。

同步成功后更新 COMPLETE 等回收/同步状态；前端 load 查询后显示 CONFIRMED。页面人数是 capacity - remainingCapacity，即已确认人数，不是 Redis 可抢库存。

**全局交接：** 报名链已形成资格，比赛提交还会检查当前账号、比赛状态、窗口与快照，不能因为页面按钮可点就跳过后端校验。

### 8. 比赛提交怎样接回可靠判题

源码：ContestDetailView 的 submit/sendPending → [ContestController.submit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestController.java) → [ContestService.submit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestService.java) → [ContestTransactions.submit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/ContestTransactions.java)。

**阅读范围：** 页面看 body/key/pending；Service 看事务外重试与冲突回读；事务从幂等判断读到比赛锁、账号、资格、ready/发布版本、快照归属和时间检查，最后跟 write。

参数包含 problemSnapshotId、publishedVersion、language、code 与 key。通过确认资格和合法比赛窗口后，复用 SubmissionAcceptance.write，给 S1 保存 contestId、快照与发布版本。后面的 MQ、worker、沙箱就是链路二、三。

页面 pending 保存原 body 与原 key；响应未知后即使编辑器变化，重试原请求仍发原内容。sessionStorage 只留指纹/key，不存源码，刷新不能只凭 key 恢复丢失的程序。

## 第二遍：未知结果与恢复

### 9. 两个名额为什么会有两种剩余数字

总容量 2，A Redis 预留未落 DB，B 已确认：Redis stock=0，DB remainingCapacity=1，页面已确认 1/2。C 不能看到 DB 的 1 就再抢一次，因为它已被 A 的在途预留占用。

A 的恢复应以原 request/event/key 补建，再确认 DB 容量。MySQL 条件扣减与唯一资格仍是最终防线；Redis 的高速预留不能替代它们。

### 10. Lua 报错为什么不能立即退款

回到脚本 apply/repair，以及 [RegistrationService.recoverUnknown](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)。

**阅读范围：** 先找复合变更前 mutation 保存了什么，再对照 reserve/finish 的写入顺序与 repair 的允许值校验。

Lua 不被其他命令穿插，不等于运行时报错会撤销已执行写入。原 stock=2、预留目标=1，若已写 1 后中断，repair 校验原身份与允许中间值，再写确定目标 1，不再 DECR。释放也避免重复 INCR。

查不到映射不能证明没扣库存；HTTP/Redis 超时也只是结果未知。证据矛盾时保留暂停/人工核查，不重置库存掩盖问题。

### 11. 预留未落库、确认未到、同步失败各由谁处理

回到 RegistrationMaintenance.maintain、RegistrationTransactions.recover、RegistrationService.synchronize。

| 故障窗口 | 恢复依据 |
| --- | --- |
| Lua 响应丢失 | repair + 原用户映射回查 |
| 预留已保存，DB 未写 | pending 身份补建原 request 与 Outbox |
| 发布已确认，但没有资格确认 | 原事件在有限预算内继续发布/确认 |
| DB 已确认，Redis 标记失败 | 重放 CONFIRMED，不退款 |
| DB 已失败/取消，释放失败 | 按原身份重放 RELEASED，不重复退 |
| 自动次数/期限耗尽 | MANUAL_REVIEW，管理员明确决定继续或终止 |

status 与 reclaimState 是两条轴。例如 FAILED/RELEASE_PENDING 表示已决定失败但物理名额尚未收回。不能只看一个状态就认定可以最终结算。

### 12. 超时、失败和取消为什么不能一律补库存

源码：[RegistrationTransactions.review/recover](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。

**阅读范围：** 对照 CONTINUE/FAIL 的允许状态、版本、原因和有限扩展，再看取消转终态的顺序。

明确失败或取消先提交可回收数据库终态，再释放；未知操作可能已确认，不能直接退款。已确认资格不能用普通 review FAIL 退成可售库存。迟到消费者也不能重新确认已终止请求。

### 13. Redis 旧快照为什么要核对身份与序号

回到 [RegistrationTransactions.settings/verifySnapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)、[RedisRegistrationLedger.snapshot](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RedisRegistrationLedger.java) 与 V005。

**阅读范围：** settings 看已落库 sequence 高水位，snapshot 看关闸、身份映射与数量检查，verifySnapshot 看逐条原身份和容量关系，V005 看序号唯一键。

DB 有 A、B，Redis 旧快照丢 B 又出现 C，条数仍可相等。对账必须核对具体身份、epoch/发布版本、序号和状态，而不只是 COUNT。高水位与唯一约束进一步限制序号回滚/重绑。

无法验证的丢失不能直接按 DB 余量初始化，因为仍可能有未落库预留。旧格式先关闸、完整核验、分配稳定序号再升级。当前容量与累计账本均限 10000，已释放身份仍计入累计数，不能靠删幂等记录继续无限准入。

### 14. 旧对账晚报错，为什么不能暂停新恢复

源码：[RegistrationService.reconcile](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationService.java)。

**阅读范围：** 跟 beginReconcile、ownedRevision、外部账本操作、finishReconcile 与 catch，再进入 issueIfCurrent。

源码：[RegistrationTransactions.issueIfCurrent](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/contest/RegistrationTransactions.java)。

**阅读范围：** 检查原 epoch/revision 与当前管理状态一致才 issue；注意调用者持有的是哪一次操作的版本。

旧 R10 的 Redis 操作晚报错，而 R11 已恢复成功，旧失败不得借用最新 revision 再暂停 R11。对账保持自己的版本条件，成功后的新版本也要用于对应后续操作。它是一段带条件的协调，不是跨 Redis/DB 大事务。

完整操作入口与边界见[报名恢复](../contest/registration-recovery.md)。比赛结束后的关闸对账还会成为链路五最终结算的前提。
