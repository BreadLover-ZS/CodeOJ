# CodeOJ 证据、压测与简历台账

这份台账用于防止“代码写了”被说成“效果已证明”。项目可以写进简历的内容，必须能追溯到源码、测试或真实运行材料，同时明确这是基于现有项目的二次开发。

## 1. 证据等级

| 等级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| L0 静态审计 | 当前代码、配置和潜在缺陷 | 代码能构建或运行 |
| L1 构建/单测 | 编译通过、局部分支符合预期 | 中间件和跨服务链路正确 |
| L2 集成测试 | 数据库、MQ、HTTP 等局部真实交互 | 完整用户链路可用 |
| L3 E2E | 从 API 到终态的完整业务闭环 | 宕机恢复和容量上限 |
| L4 故障注入 | 指定失败点下的恢复语义 | 生产环境长期稳定性 |
| L5 压测 | 固定环境下的吞吐、时延和瓶颈 | 其他机器或生产流量表现 |
| L6 生产观测 | 实际流量下的指标与事故经验 | 超出观察范围的绝对保证 |

简历表述应与最高证据等级对齐。例如，只有 L1 时可以说“实现并通过单元测试”，不能说“保障高并发下任务不丢”。

## 4. 必做验收用例

### 4.1 判题结果

| 用例 | 期望任务状态 | 期望 verdict | 关键断言 |
|---|---|---|---|
| 正确答案 | FINISHED | Accepted | 输出与资源字段正确 |
| 错误答案 | FINISHED | Wrong Answer | 不进入系统失败 |
| 编译错误 | FINISHED | Compile Error | 保存脱敏编译信息 |
| 非零退出 | FINISHED | Runtime Error | 不自动重试用户代码 |
| 超时 | FINISHED | Time Limit Exceeded | 进程树被回收 |
| 沙箱 HTTP 超时 | RETRY_WAIT/DEAD | System Error | 按策略有界重试 |
| 题目配置损坏 | DEAD | System Error | 可查询且有告警 |

### 4.2 消息可靠性

| 故障 | 期望证据 |
|---|---|
| 数据库事务回滚 | submission 与 Outbox 都不存在 |
| 发布前杀死发布器 | Outbox NEW 保留，恢复后发布 |
| Broker NACK | Outbox 进入 RETRY 并记录原因 |
| routing key 错误 | Return 可观测，不标 SENT |
| 同一 ID 并发投递 10 次 | 仅一个 worker 获得执行权 |
| 结果写回后、ACK 前杀进程 | 重投识别终态并 ACK |
| RUNNING 后杀进程 | 租约过期后恢复并最终完成 |
| 连续依赖失败 | 达上限后 DEAD/DLQ，不无限热重试 |
| 非法消息体 | 进入毒消息通道，不阻塞正常队列 |

### 4.3 权限与信息泄露

- 未登录用户不能提交；
- 普通用户不能调用管理员接口；
- 被封禁用户在所有受保护接口被拒绝；
- 外部请求不能访问 `/inner/**`；
- 非本人不能查看提交源码；
- 日志中不出现 Cookie、密钥、源码和隐藏输入；
- 注册账号在多实例并发下仍由数据库唯一约束保证唯一。

## 5. 压测方案

### 5.1 先固定环境

报告必须包含：

- CPU、内存、磁盘、操作系统；
- JDK、JVM 参数和 GC；
- MySQL、Redis、RabbitMQ、Nacos 和 Docker 版本；
- 各服务实例数、线程池、连接池、RabbitMQ prefetch；
- 题目用例数、用户代码类型和数据规模；
- 压测工具、脚本 commit、并发阶梯、预热与持续时间。

### 5.2 分三层测

#### A. 提交 API

只测鉴权、数据库事务、Outbox 写入和响应：请求吞吐、P50/P95/P99、HTTP 错误率、连接池和事务耗时。这个数字不能叫“判题 QPS”。

#### B. 消息与编排

使用可控的假沙箱或固定延迟沙箱，测发布/消费速率、队列深度、排队时延、重试、DLQ、重复投递和 CAS 冲突。

#### C. 真实 Java 判题

使用固定题目和代码集，测每秒完成判题数、端到端 P50/P95/P99、编译/运行耗时、沙箱资源、队列积压增长与回落、超时和系统失败比例。

真实判题通常受 CPU 和隔离开销限制，不应拿提交 API 的高吞吐替代。

### 5.3 报告结论模板

```text
在 [机器规格]、[服务实例数]、[数据集]、[持续时间] 下，
提交接口在 [并发] 时达到 [吞吐]，P95 为 [时延]，错误率 [比例]；
真实 Java 判题吞吐为 [数值]，端到端 P95 为 [时延]。
瓶颈首先出现在 [CPU/连接池/队列/沙箱]，依据是 [指标]。
本结果未覆盖 [网络抖动/多机/生产流量/某类恶意代码]。
```

必须保存完整并发阶梯和失败拐点，不能只截最高数字。

## 7. 面试问答检查表

### 为什么选择 Outbox，不用数据库事务包住 RabbitMQ？

数据库事务不能原子提交到 RabbitMQ。Outbox 把业务记录和发布意图写入同一本地事务，再异步发布；回调更新失败会造成重复发布，所以仍需要消费者幂等。

### publisher confirm、return 和 consumer ACK 有什么区别？

Confirm 说明 Broker 是否接收发布；Return 识别消息无法路由；consumer ACK 说明消费端何时允许 Broker 删除消息。三者都不能替代数据库业务状态和幂等。

### CAS 已经防重复，为什么还需要租约？

CAS 只决定谁从 WAITING 进入 RUNNING。worker 获得执行权后可能宕机，租约让系统识别过期 RUNNING 并安全恢复；写回还要校验 worker/version，防旧结果覆盖。

### 为什么 CE/RE/TLE 不重试？

它们是同一份用户代码和用例下的确定性业务结果，重试不会修复代码。HTTP 超时、服务发现失败等基础设施异常才可能暂时可恢复。

### 为什么提交接口 QPS 不等于判题吞吐？

提交接口主要做短事务和入队，判题包含编译、启动进程、执行多个用例和资源隔离，成本高得多。高提交 QPS 可能只会扩大队列积压。

### 当前沙箱为什么不安全？

它在长期运行容器内直接启动用户子进程，没有提交级 CPU、内存、PID、网络和文件系统隔离；现有读流顺序还可能让超时失效。共享密钥和 Compose 隔离不能解决恶意代码逃逸与资源耗尽。
