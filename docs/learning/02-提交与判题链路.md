# 链路二：提交与判题

本篇按业务进展组织章节，章内沿源码调用顺序阅读。每段先解释当前步骤需要的概念，再介绍负责它的组件、方法及阅读范围。前三章走正常链，第四章分析恢复，第五章做推演。

阅读时开启 `codeoj.reliable-judge.enabled=true`（默认关闭），只跟可靠分支。假设用户已登录，向题目 42 提交 Java 程序，受理后记为 S1；后续标识均为教学符号。登录细节见[登录链路](01-登录与权限链路.md)，比赛额外检查见[赛事链路](04-赛事报名与参赛链路.md)。

## 1. 接收提交，保存判题任务

这一阶段在题目服务中完成：接收用户请求，在事务中保存本次判题所需的数据，再返回提交 ID。

### 1.1 接收请求，识别同一次提交

题目服务的公开入口由 `QuestionController.doQuestionSubmit` 负责，整理用户请求后交给提交服务。读它之前，先认识请求中的幂等 key。

`Idempotency-Key` 是前端为一次提交分配的请求标识。假如后端已经保存提交，但响应在途中丢失，前端沿用原 key 重试，后端才能识别这是同一次请求。

后端按“用户 + key”识别请求，并核对内容：同 key、同内容返回原提交 ID；同 key、不同内容报冲突。重新发起一份提交则使用新 key。页面为待确认内容保留 key，内容变化时重新生成，受理成功后清除。

key 可以从请求头 `Idempotency-Key` 或请求体的 `requestKey` 传入。两处同时提供时必须一致，Controller 将请求头的值统一写入 DTO；真正的判重在后面的受理事务中完成。请求 DTO 还携带题目 ID、语言和代码，用户身份由后端会话解析。

**现在读：** [QuestionController.doQuestionSubmit](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/controller/QuestionController.java)。按以下顺序读完整个方法：

1. 检查 header/body key，统一写入 DTO。
2. 检查请求和题目 ID，通过 getLoginUser 取得当前用户。
3. 调用 questionSubmitService.doQuestionSubmit，取得提交 ID。
4. 可靠分支返回 HTTP 202，表示已受理；返回值是 S1，并非判题结果。

前端对应 [ViewQuestionView.vue](../../codeoj-frontend/src/views/question/ViewQuestionView.vue) 的 doSubmit：只看指纹与 key 保存、请求发送、成功清理和跳转，不必读页面样式。页面 loading 防连点，后端幂等还要覆盖丢响应和并发。

### 1.2 选择受理分支，协调失败重试

请求从 Controller 进入提交业务入口 `QuestionSubmitServiceImpl.doQuestionSubmit`。可靠开关为 true 时，它转交可靠受理协调组件 `ReliableSubmissionService`；后面的旧写库、直接发 MQ 代码不会执行。

`ReliableSubmissionService` 检查语言、代码和 key，再调用负责受理事务的独立组件 `SubmissionAcceptance`。拆成两层，是为了让事务先结束，外层再决定是否重试：

- 暂态数据库异常：旧事务回滚后，重试整次受理，最多调用三次。
- 唯一约束冲突：旧事务退出后回读同用户、同 key 的记录，核对内容再返回原 ID；不是所有唯一冲突都算成功。
- 其他异常：向调用方报告失败。

**事务如何在这里生效：** 外层调用的是 Spring 管理的事务代理。代理先建立事务，再调用内层业务方法，最后提交或回滚，之后才把结果或异常交回外层。因此重试不会继续使用上一次失败的事务。这个事务只覆盖本地数据库操作，不跨 MQ 或 HTTP。

### 1.3 核对旧请求，准备判题材料

受理组件的事务入口是 `SubmissionAcceptance.accept`：先识别旧请求，再为新请求准备材料和写入记录。

判重需要同时知道“请求身份”和“请求内容”。`requestKey` 标识请求，`requestHash` 是请求类型、题目 ID、语言、代码的内容摘要。事务先按用户和 key 查旧执行记录：存在且摘要一致就返回原 S1；摘要不同则报冲突。

并发时，两个请求可能都查不到旧记录，所以数据库还对 `(userId, requestKey)` 建立唯一约束。只有一份新记录能成功；发生冲突的一方由 1.2 节的外层服务在事务回滚后回读，避免重复创建提交和派发事件。

对于新请求，事务继续检查数据库中的当前账号状态，再读取题目的 `judgeConfig`（资源限制）和 `judgeCase`（输入、标准输出）。接着调用同一组件的 `freezeSpec` 固定判题材料，再由 `write` 保存代码、执行记录和待发事件，最后增加普通题目的提交数。下面两小节继续跟进这两个辅助方法。

**现在读：** [SubmissionAcceptance.accept](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java)，依次定位 requestHash → byKey/replay → requireAccount → 题目材料查询 → freezeSpec → write → submitNum 更新。先看入口如何组织这次事务，再进入下面的辅助方法。

辅助定位：[ExecutionRepository.byKey](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRepository.java)、[ExecutionRepository.requireAccount](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRepository.java)；唯一约束见 [V001 表结构](../../codeoj-backend/mysql-init/migrations/V001__reliable_judging.sql)。

### 1.4 固定本次判题用例和资源限制

提交排队期间，题目的用例可能被修改。若执行时读最新题目，同一提交按什么规则判就取决于修改时机。

固定判题依据由同一受理组件的 `freezeSpec` 方法完成：把本次用例、资源限制、规格版本和比较规则序列化，按内容摘要保存到 `judge_spec`，记为 H1。S1 引用 H1，后台按这份固定依据判题；相同规格可以共用。摘要用于校验内容，含隐藏用例的规格不能返回普通做题页面。

`freezeSpec` 标注 `MANDATORY`：经过事务代理调用时必须已有事务。它与后面负责保存提交的 `write` 都由 `accept` 在同类内调用，沿用入口事务，不会各自再开启事务。

**现在读：** [SubmissionAcceptance.freezeSpec](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java) 及 validateSpec。关注材料校验、version/comparator/limits/cases 组装、摘要生成和按摘要复用；暂不展开文本比较算法，后面读判题策略时再看。

### 1.5 保存代码、执行记录和待发通知

接着仍在受理组件 `SubmissionAcceptance` 内，由 `write` 方法保存提交、执行记录和待发事件。

代码表示用户交了什么；执行记录表示当前是否可执行、归哪次尝试、是否已有结果。只靠旧提交表的 status，不足以记录重新派发、执行凭证和恢复预算。

`Outbox` 是数据库里的待发送事件表。若先提交代码、再直接发 MQ，进程可能在两步之间退出，留下已保存却未发出通知的提交。把“需要通知后台”也写进受理事务，后续发布器便能重新扫描并发送。

本次受理保存以下关联：

| 记录 | 保存什么 |
| --- | --- |
| `question_submit` | S1 的代码、语言、题目和提交者 |
| `judge_spec` | 固定依据 H1，由 freezeSpec 新建或复用 |
| `submission_execution` | S1 引用 H1，初始 QUEUED（等待执行），尚无执行尝试；派发代次 g1、事件 E1 |
| `reliable_outbox` | E1 类型为 JUDGE_DISPATCH，保存待发送的任务引用 |

派发代次表示第几轮安排执行，事件 ID 标识该轮通知；重新派发时才更换。消息保存提交 ID、代次、事件 ID、协议版本与追踪标识，不携带源码或私有输入。

代码、执行记录、事件和提交数一起成功或回滚；本次新建规格也随失败回滚。

**现在读：** [SubmissionAcceptance.write](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/SubmissionAcceptance.java) → [ExecutionRepository.insertDispatch](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRepository.java)。核对插入顺序、字段关联和初始预算：最多 3 次执行尝试、10 个派发代次，总恢复期限 15 分钟。它们用于限制故障后的自动恢复，不是用户程序的运行时限。

回到 accept，再按原路返回 Controller。事务提交成功才能正常返回 S1；到这里原提交 HTTP 请求已经可以结束，代码尚不要求运行完成。

## 2. 后台接收任务，领取执行资格

受理事务提交后，题目服务的发布器从待发事件接手，经 MQ 通知判题服务，后者再向题目服务申请执行资格。

### 2.1 发布判题任务通知

题目服务的后台发布组件是 `OutboxRelay`，Spring 调度器周期调用它的 `tick` 方法，与原提交线程分开。它扫描到期事件，为 E1 领取一次有期限的发布权（发布租约），退出领取事务后再发 MQ，最后记录发送结果。竞争者要等持锁事务完成；持锁事务写入发布 token 和期限并提交后，后来的事务会重新检查租约，尚未到期就不能再次领取。

本项目使用 DirectExchange `codeoj.judge.v1.exchange`，路由键为 `judge`，通过绑定进入 `codeoj.judge.v1.queue`。交换机负责路由、队列保存投递，判题端监听容器再把消息交给 Java 方法。

发布时需要区分两个信号：

| 信号 | 含义与处理 |
| --- | --- |
| Publisher Confirm | Broker 对一次发布给出 ACK/NACK；ACK 不能说明任务已经执行 |
| Return | 发布开启 mandatory 后，无法路由的消息被退回；即使 Confirm 为 ACK，也不能按有效路由成功处理 |

若 Broker 已收到 E1，但确认丢失，平台只能记录结果未知（UNKNOWN），之后可能补发同一个 E1。**Outbox 保留发送意图，不消除重复投递。** 每次网络发送另有发布 token，记录在 `publish_attempt`：旧 token 的迟到失败不能清除新发布权或推翻成功确认；有效迟到 ACK 可以让同一事件收敛。

单次发布领取窗口为 15 秒，派发事件最多尝试发布 20 次，耗尽转 ATTENTION，停止该事件的自动发布。发布状态与执行状态分开：E1 已确认，S1 仍可能是 QUEUED。

### 2.2 接收消息，交给后台处理组件

判题服务的消息接收组件是 `ReliableJudgeConsumer`，它的 `receive` 方法通过 `@RabbitListener` 注册，由监听容器在收到队列消息时触发。手动确认中的 `deliveryTag` 标识当前消费通道（Channel）上的一次投递，用来 ACK/NACK；它与业务事件 ID、执行凭证都不同。

Consumer 先校验消息，再交给执行协调组件 `ReliableJudgeWorker`（下文简称 worker）的 `process` 方法：

- 坏消息：Reject 且不重投，由配置的死信路由进入隔离队列。
- process 正常返回：ACK，结束本次投递。
- 运行时异常到达 Consumer：先退避，再 NACK 请求重投。

ACK 只表示结束此次投递。已完成、旧代次、未到执行时间的任务，也可能让 worker 正常返回；不能据此判断用户代码 AC。

**现在读：** [ReliableJudgeConsumer.receive](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/rabbitmq/ReliableJudgeConsumer.java)，沿反序列化 → valid → process → ACK 跟正常分支，再看消息校验失败和处理异常的分支。

worker 用 Semaphore 限制本机并发名额；取不到名额则请求 deferExecution 持久延后，取到后才调用 claimExecution 领取任务。

接着读 [ReliableJudgeWorker.process](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/ReliableJudgeWorker.java) 的开头，停在 claimExecution；下一小节跨到题目服务继续读，领取返回后再回 worker。

### 2.3 跨服务申请任务

worker 中的 `questions` 是 QuestionFeignClient 的客户端代理。OpenFeign 根据接口的服务名、路径和方法注解，将 claimExecution 的 Java 调用编码为 HTTP POST，发到题目服务的 `/api/question/inner/execution/claim`；响应再转成 JudgeLease，包含是否获权以及获权后的执行材料。

提供方 `QuestionInnerController` 接收 HTTP，将领取请求交给本地执行控制组件 `ExecutionCommands` 的 `claim` 方法。`QuestionInnerController` 实现同一份 Feign 接口，便于对应契约；IDE 跳到实现是在定位接收端，两个进程并没有直接调用同一个 Java 对象。

公开提交接口根据会话处理用户请求；内部接口接受后台领取、续租、写回命令。内部请求由服务凭据头和服务端过滤器保护，任务的状态与执行身份还要由命令检查。旧普通 update 不能绕过可靠任务的执行规则。

**现在读：** [QuestionFeignClient](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/service/QuestionFeignClient.java) 的注解和 claimExecution → [QuestionInnerController.claimExecution](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/controller/inner/QuestionInnerController.java)。认证定点看 [FeignInnerAuthConfig](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/config/FeignInnerAuthConfig.java)、[InnerApiAuthFilter](../../codeoj-backend/codeoj-backend-service-client/src/main/java/com/codeoj/codeojbackendserviceclient/filter/InnerApiAuthFilter.java)；无需从头重读登录链。

### 2.4 领取本次执行资格

领取资格由刚才的 `ExecutionCommands.claim` 决定。消息可能重复或迟到，因此它在事务中锁住 S1，核对当前执行记录：检查事件/代次仍是当前、状态为 QUEUED、已到执行时间、预算剩余、固定规格有效，才授予执行权。

成功领取后，状态变 RUNNING（正在执行），attemptNo 增加到 1，生成本次 `executionToken` T1，创建 judge_attempt。JudgeLease 返回 S1、尝试号、T1、期限以及代码、固定用例和限制。attempt 标识第几次获权尝试，token 用于之后续租与写回时核对身份；它不是发布 E1 时使用的 token。

两个消费者同时领取时，后取得行锁的一方会看到 RUNNING，不能再次授予执行权。锁保护领取事务，事务结束后才远程运行程序，不会持锁等待沙箱。预算或规格校验失败还可能转 NEEDS_ATTENTION，即停止自动推进，等待管理操作。

领取时还会建立两个期限：`leaseUntil` 是可续的租约，初始最多 15 秒；`attemptDeadlineAt` 是本次尝试的绝对期限，最多 60 秒，受总恢复期限约束。续租不能越过尝试期限。这两个字段都在 claim 中创建。

**现在读：** [ExecutionCommands.claim](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java) → [ExecutionRepository.find](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRepository.java)。沿锁行、条件检查、规格与代码查询、attempt/token 创建、保存和返回读；false 表示未授予执行权，部分预算/规格失败分支还会转 NEEDS_ATTENTION，不能理解为一律未改数据库。

返回结构看 [JudgeLease](../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/reliability/JudgeLease.java)；后续命令的公共身份字段看 [ExecutionCommand](../../codeoj-backend/codeoj-backend-model/src/main/java/com/codeoj/codeojbackendmodel/model/reliability/ExecutionCommand.java)。

### 2.5 执行期间维持资格

worker 每 5 秒发心跳请求，把租约延至“数据库当前时间 + 15 秒”与尝试期限中较早的时刻。失联后租约过期，任务才可被恢复器接手。

假设总恢复期限更晚，在 T=0 领取，租约至 T=15；T=5 心跳成功可延到 T=20。若一直续租到 T=55，也最多延至尝试期限 T=60，不能延到 T=70。

题目服务用数据库时间检查：状态仍为 RUNNING，attempt/token 相同，租约、尝试期限及总恢复期限均未过期，才是有效执行者。心跳明确失败会让 worker 标记 lost；网络异常只说明未知，最终仍由数据库写回检查兜底。数据库失权不等于旧沙箱进程已经停止。

**现在读：** [ExecutionCommands.heartbeat](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java) 及 sameToken、owned；再回 [ReliableJudgeWorker.process](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/ReliableJudgeWorker.java)，看心跳任务的创建、lost 标记及 finally 中的取消与名额释放。

## 3. 运行程序，保存并查询判定

领取成功后，回到判题服务继续执行；得到判定后交题目服务保存，页面再独立查询。

### 3.1 调用沙箱运行代码

回到判题服务的 `ReliableJudgeWorker.process`，它从领取材料里提取输入，连同代码、语言、时间/内存限制、T1 和期限构造 ExecuteCodeRequest。标准输出留在判题端，用来和实际输出比较。

这里的工厂选择沙箱调用实现（当前 remote），手写 CodeSandboxProxy 包装调用诊断；它与 2.3 节负责把 Java 调用变成 HTTP 的 Feign 代理用途不同。RemoteCodeSandbox 负责 HTTP 传输、认证、超时和响应大小限制。传输超时只能说明未按时得到响应，不能直接判用户 TLE。

**现在读：** worker 的请求构造 → [CodeSandboxFactory.newInstance](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxFactory.java) → [CodeSandboxProxy.executeCode](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/CodeSandboxProxy.java) → [RemoteCodeSandbox.executeCode](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/codesandbox/impl/RemoteCodeSandbox.java)。沙箱内部编译、运行与回收在[下一篇](03-沙箱执行与回收链路.md)展开，本节读到响应返回即可。

### 3.2 检查资源与比较答案

响应先交给结果映射器 `SandboxResultMapper` 校验；需要比较答案时，由策略选择组件 `JudgeManager` 交给 Java 判题策略。

响应的 outcome 表示沙箱执行结果。合法的 CE、RE、TLE、MLE、OUTPUT_LIMIT 等可以映射为用户判定；EXECUTED 只表示完成运行，还要检查资源和答案。平台错误、协议矛盾、必要指标缺失都属于平台失败，不能补零判 AC 或默认算用户错误。

EXECUTED 进入 Java 策略后，先验证指标、用例数量与限制有效，再依次判断时间超限、内存超限、逐组输出不符；分别形成 TLE、MLE、WA，全部符合才 AC。时间单位是毫秒，内存是 KiB。

文本比较规则 TEXT_V1 将 CRLF 换成 LF，只忽略一个末尾 LF，其余空白保留。例如 `3` 与 `3\n` 匹配，`3 ` 与 `3` 不匹配。JudgeContext 只是把固定用例、限制、实际输出和指标组合成策略的本地入参。

**现在读：**

| 方法 | 作用与阅读范围 |
| --- | --- |
| [SandboxResultMapper.userVerdict](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/SandboxResultMapper.java) | 校验协议；直接形成用户判定，或为 EXECUTED 返回 null，让 worker 进入策略分支 |
| [JudgeManager.doJudge](../../codeoj-backend/codeoj-backend-judge-service/src/main/java/com/codeoj/codeojbackendjudgeservice/judge/JudgeManager.java) | 按语言选择策略；当前仍是语言分支手动创建，不是自动发现插件 |

### 3.3 保存判定，拒绝迟到写回

worker 算出判定后，要带 S1、attemptNo、T1 调用完成命令。题目服务由执行控制组件的 `ExecutionCommands.complete` 再次核对身份与期限，防止旧执行者的迟到结果覆盖新尝试。

完成命令先规范化判定并计算摘要。首次有效完成在一个事务中结束 attempt、更新执行状态为 COMPLETED、保存判定与结果版本、更新兼容查询字段，并写 JUDGE_RESULT 结果事件；普通练习为 AC 时还增加题目通过提交数，统计的是通过提交次数。

若完成响应丢失，同 attempt/token 重放相同结果，按摘要返回成功，不重复增加统计或结果事件；同身份换成不同结果则拒绝并审计。结果事件用于后续计分，与触发执行的派发事件分开处理。

**现在读：** worker 的 completeExecution → [QuestionInnerController.completeExecution](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/controller/inner/QuestionInnerController.java) → [ExecutionCommands.complete](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)。在 complete 中依次跟 canonicalResult、完成回放、owned、finishAttempt 和各项写入。

然后回 Consumer 看 ACK。当前 worker 不会因 completeExecution 或 failExecution 明确返回 false 就统一抛异常，RPC 异常则另走异常处理；不能把源码概括成“写回失败一定 NACK”。内部服务异常如何用非正常 HTTP 状态返回、避免客户端误读为默认 false，定点看 [ExecutionRpcAdvice](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRpcAdvice.java)。

### 3.4 查询当前状态与判定

做题页受理成功后跳到提交列表。列表另发 HTTP 查询，读取当前状态；没有完成时可以显示 QUEUED/RUNNING，结果事务提交后再查才能看到 COMPLETED 与 AC、WA 等判定。原提交请求不会一直等着沙箱返回。

列表先查提交分页，再组装 VO，附加可靠执行状态、受理时间和尝试号，并按当前用户权限决定是否展示代码。可靠模式还会从普通列表排除比赛提交，比赛单提交状态查询在赛事篇阅读。

提交 ID 可能超过 JavaScript Number 的安全整数范围，因此后端将 Long 序列化为字符串，前端应保留原值。

## 4. 平台失败后，任务怎样继续

### 4.1 记录平台失败或容量不足

正常链走完后，再回 worker 的异常分支。已有依据的 CE、WA 等走完成流程；沙箱不可用、协议错误、资源指标缺失则尝试记录平台失败。

平台失败和容量延后仍由题目服务的 `ExecutionCommands` 处理：`fail` 校验执行身份，结束本次 attempt 为 FAILED；预算剩余就转 RETRY_WAIT（等待重试），设置退避时间。`defer` 用于尚未领取时的名额不足，持久延后但不增加 attempt。若错误命令的 RPC 自身抛异常，可能继续传到 Consumer，进入消息重投。

**现在读：** worker 的 catch / lost → [ExecutionCommands.fail](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)、[ExecutionCommands.defer](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)。区分平台失败、失权后跳过操作及容量延后；不要把平台排队当作用户 TLE。

### 4.2 扫描失联任务，重新安排执行

题目服务的执行恢复扫描组件是 `ExecutionRecovery`。调度器周期调用它的 `tick` 方法，扫描候选后逐条交给 `ExecutionCommands.recover`，在事务中重新检查当前时间、状态和预算：

| 状态或条件 | 处理 |
| --- | --- |
| RUNNING，租约有效 | 保留当前执行者 |
| RUNNING，租约过期 | 旧 attempt 标为 EXPIRED，有预算则重新派发 |
| RETRY_WAIT 到期 | 有预算则重新派发 |
| QUEUED 约 30 秒无人领取 | 可以重新派发，即使旧事件已经得到发布确认 |
| 预算或总期限耗尽 | 转 NEEDS_ATTENTION，停止自动推进 |
| COMPLETED / NEEDS_ATTENTION | 自动扫描不重新打开 |

重新派发保持 S1 和 H1，代次 g1 变 g2，事件 E1 变 E2，清除旧 token，回到 QUEUED，并保存新派发事件。下一次领取成功才增加 attempt、生成 T2。旧 E1 被派发身份检查挡住，旧 T1 的迟到结果被执行身份和期限检查挡住。

**现在读：** [ExecutionRecovery.tick](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRecovery.java) → [ExecutionRepository.recoverable](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionRepository.java) → [ExecutionCommands.recover](../../codeoj-backend/codeoj-backend-question-service/src/main/java/com/codeoj/codeojbackendquestionservice/submission/ExecutionCommands.java)，继续跟 requeue、exhausted、attention。数据库拒绝旧结果与沙箱物理回收的区别，继续见[沙箱链路](03-沙箱执行与回收链路.md)。

### 4.3 自动恢复何时停止，管理员怎样介入

自动恢复受执行次数、派发次数和总期限限制，耗尽后转 NEEDS_ATTENTION。用户重试同一 key 不重置预算。管理员若要继续处理，使用执行控制组件的 `manualRetry` 方法，校验当前管理员身份、期望状态版本、原因和有限预算扩展，并保留审计。

**现在读：** 上面同一文件 `ExecutionCommands` 的 manualRetry，重点看预算检查与审计写入。

| --- | --- | --- |
